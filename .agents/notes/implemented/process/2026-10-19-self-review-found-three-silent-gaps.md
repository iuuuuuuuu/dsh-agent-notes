## Problem

Owner 要求「再多自审、跑全流程、确保没问题」。逐条实测后，在三道门禁里
各找到一处**静默失效**——它们的共同特征是：**不报错、退出码合理，
只是没检查到该检查的东西**。

### ① 仓库根目录的源码文件完全不被识别

`detectSourceDirs()` 按「顶层目录」分组，而根目录下的文件不属于任何目录，
被 `slash <= 0` 直接跳过。于是 `index.js` / `main.py` **从不被当作源码**。

实测：在一个只有 `index.js` + `main.py` 的仓库里改 `index.js`，
门禁打印「改动未命中受管路径，无需笔记」并 `exit 0`。

单文件项目（`index.js` + `package.json`）极常见，这个洞的实际覆盖面不小。

### ② supersession 只认一种 markdown 链接写法

原正则 `/\]\(([^)\s]+\.md)(?:#[^)]*)?\)/` 只匹配 `[文字]（相对路径）`。
实测漏掉两种**合法**写法：

| 写法 | 原正则 |
|---|---|
| `[文字]（<含空格的路径>）` 尖括号包裹（路径含空格时必须这样写）| ❌ 漏 |
| `[文字]（路径 "title"）` 带标题 | ❌ 漏 |

后果是「写了链接却被判没有」，而提示让人去加链接——**他明明已经加了**。
这类误报最伤信任：人会开始怀疑门禁在乱报，然后整体无视它。

### ③ `doc-budget --update` 名为放宽、实为收紧

原实现无条件把预算写成当前值：2100 → 2080，**余量归零**。
实测更新后再加一个字就红。

而它的提示写着「放宽预算需要有理由」——叫「放宽」却做「收紧到极限」，
使用者会以为自己在松绑。

## Decision

**① 单独收「根目录源码文件」，按文件而非目录受管。**

```js
function detectRootSourceFiles(trackedFiles) {
  /* 只收根目录的：路径里没有 `/`。 */
  if (path.includes('/')) continue;
  if (SOURCE_EXTENSIONS.includes(ext)) hit.add(path);
}
```

反向也守住：根目录的 `README.md` / `LICENSE` 不该被误判成源码 ——
否则每改一次文档都要写笔记，噪音会让人绕过门禁。

**② 链接正则覆盖三种合法写法。**

```js
/\]\(\s*(?:<([^>]+\.md)(?:#[^>]*)?>|([^)\s]+\.md)(?:#[^)\s]*)?)(?:\s+"[^"]*")?\s*\)/g
```

同时保留外部 URL 过滤（`^[a-z]+:`）—— 一句
`见 [文档](https://example.com/x.md)` 不能充当「查过既有笔记」。

**③ `--update` 只放宽，绝不收紧。**

只有**真正超预算**的文件才被提到当前值；其余原样保留。
在预算内时它打印「无需放宽」并退出 0，不改文件。

**must**：一次放宽不得顺手收紧别的文件。否则「我放宽 A」会意外把 B 的
余量清零，下次改 B 就莫名其妙红了。

## Alternatives considered

- **根目录源码改成「凡是根目录的已知源码后缀都受管」** — 不必枚举实际文件。
  否掉：那会把 `LICENSE`（无后缀）漏掉的同时，把根目录里**未跟踪**的
  临时脚本也算进来；用 `git ls-files` 实际跟踪的文件更准确。
- **链接检测改用 markdown 解析器** — 最可靠。否掉：本项目零依赖
  （`dependencies` 与 `devDependencies` 都是 `{}`），引入 `mdast` 会破坏
  这条硬约束。而链接语法的子集（行内链接）用正则可以覆盖得足够好 ——
  参考链接 `[a][b]` 这种冷门写法没有覆盖，但本仓库的笔记不用它。
- **`--update` 直接删掉，改成只能手改 JSON** — 避免「一条命令放松门禁」。
  否掉：超预算时手工改 JSON 容易写错数字，而脚本能精确写成当前值。
  关键是**它只能放宽**，这个约束保住了它的安全性。
- **`--update` 保留原有余量**（把预算写成 `当前值 + 原余量`）— 语义更一致。
  否掉：需要额外记录「原余量」，而余量本身是预算减去当前值算出来的，
  记录它会产生第二份真源。**只放宽不收紧**已经解决了核心问题，
  放宽后的新余量为 0 是可接受的（下次超预算再放宽一次即可）。
- **三处都不修，只写进笔记的「已知缺口」** — 零风险。否掉：
  前两处是**静默漏检**，正是本套门禁存在的理由所要防的形态；
  把「门禁自己静默漏检」记成已知缺口，等于承认这套东西不可信。

## Consequences

- **收益**：单文件项目（`index.js` 这类）的源码改动第一次被正确拦下。
- **收益**：用 `[文字]（<含空格的路径>）` 或 `[文字]（路径 "title"）` 写链接的人不再被误拒。
  误报少了，门禁的信任度才能维持。
- **收益**：`--update` 不再是一个「叫放宽却收紧」的陷阱。
- **代价**：`detectRootSourceFiles` 多遍历一次 `git ls-files` 的结果。
  与 `detectSourceDirs` 共用同一次输出，成本可忽略。
- **代价**：链接正则变复杂，可读性下降。已在注释里写明三种写法的必要性。
- **已知缺口**：链接检测仍不支持 markdown 的**参考式链接**
  （`[文字][引用]` 加一行引用定义）。本仓库的笔记不用这种写法；
  若将来用，会被判「没有链接」。
  重访信号：有人在笔记里用参考式链接而被门禁拒绝。
- **写这篇笔记时踩到的坑（值得记）**：我最初把链接示例写成真正的
  markdown 链接，结果 **`tree` 门禁把它们当成真实链接**，
  报「target file does not exist」—— 连包在反引号里也一样。
  也就是说：**在笔记里演示链接语法时，不能写出可解析的链接**，
  否则门禁会去解析它。改用 `[文字]（相对路径）` 这种非链接写法才对。
  这不是门禁的 bug（它本来就该检查所有链接），而是写文档时的注意事项。
- **已知缺口**：根目录检测只认 `SOURCE_EXTENSIONS` 里的后缀。
  冷门语言（`.zig`、`.nim`）若不在表里，根目录文件仍会漏。
  这份表是**显式清单**，不是「任意后缀」——因为后者会把
  `.md`、`.json`、`.txt` 也当成源码。重访信号：引入新语言时。
