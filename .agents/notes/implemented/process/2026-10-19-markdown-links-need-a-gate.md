# Agent Note: Markdown 断链是没人管的一类腐坏

Status: implemented

> 同域：与「第三方归属声明」同属**完整分发流程的补齐**。
> 归属声明见
> [2026-10-19-third-party-notices-are-part-of-distribution.md](./2026-10-19-third-party-notices-are-part-of-distribution.md)，
> 笔记之间的关系检查见
> [2026-10-18-notes-supersession-check.md](./2026-10-18-notes-supersession-check.md)。

Independent: 本篇处理的是「指向文件的链接是否可达」，与笔记之间是否同一决定（supersession）以及许可证披露都是不同的失效面。

## Problem

仓库里有 28 个 Markdown 文档、54 条相对链接，它们互相引用：README ↔ README.en、
AGENTS → 笔记、笔记 → 笔记、THIRD_PARTY_NOTICES → LICENSE。而**没有任何门禁
检查这些链接是否还指向存在的文件**：

- 笔记门禁（`verify-agent-note-tree.ts`）只验**笔记之间**的链接；
- `tools/verify-plugin.mjs` 只验双语文档与徽标**存在**，不看它们指向谁。

断链在这两个时刻必然出现，而且都是「改的人当时有别的注意力」：

1. 归档或删除一篇笔记时，入站链接没人修；
2. 重命名文件后，正文里的说法改了，链接忘了改。

它们不会让任何测试变红，只会让后来点开的人撞上 404。

### 这个缺口为什么之前没被发现

它不需要「今天恰好有断链」才成立 —— 需要的是**「一旦有人弄断，谁来发现」**。
我用「当前没断链」当作「不需要检查」，等于把检测能力建立在一个会变化的
事实上。上游 `deepseek-ai/deepseek-harness` 有 `scripts/verify-md-links.ts`
就是为了这件事。

## Decision

新增 `tools/md-links.mjs`，扫描 5 个顶层文档 + `.agents/notes/` 全部笔记，
校验每一处相对链接的目标文件存在。

`must`：链接目标必须**先去掉 fragment 与 query 再解析**。`README.md#命令` 的
目标是 `README.md`，不是字面文件名。

`must`：**必须跳过围栏代码块与行内代码**。文档里常有「链接长这样」的示例
（本仓库笔记里就有）。不跳过会产生大量误报，而误报多的门禁会被绕过 ——
那比没有门禁更糟，因为它训练人忽略红。

`must`：**百分号编码要先解码**。中文文件名可能写成 `%E4%B8%AD`，不解码会
误报「不存在」，而那是个真实存在的文件。

`must`：**越出仓库范围的路径必须拒绝**。`[a](../../../etc/passwd)` 若只做
`existsSync`，在 Linux 上会真的存在并被判合法。文档链接不该指向仓库之外。

`must`：不扫描 `skills/agent-notes/`。那是 vendored 上游副本，本仓库无权修
它的内部链接；扫描它只会产生「改不了的红」。

### 不做的：`#fragment` 锚点校验

上游会校验「`#命令` 是否真的对应某个标题」。本仓库当前**零处**使用锚点链接
（实测 grep）。为不存在的需求实现「标题转 slug」这套逻辑，是纯粹的复杂度，
而且一旦与渲染器（GitHub）的 slug 规则不一致就会产出误报。

这条记在重访信号里：等真的用上锚点再加，那时应以实际渲染器规则为准。

## Alternatives considered

- **引入 mdast 做 AST 级解析** — 上游就是这么做的，能精确区分「代码块里的链接示例」与「真链接」，还能顺带校验锚点。否掉是因为本仓库的链接形态很简单，用「跳过代码区域」的轻量预处理就能覆盖同样的事，而引入 mdast 要带一棵依赖树与它的 GFM 扩展。**但这不是原则性拒绝** —— 若将来需要锚点校验，mdast 就是正确选择，那时该引入。
- **只做一次人工清扫，不加门禁** — 零代码，当前确实没断链。否掉是因为断链会**持续产生**：每次归档笔记都可能弄断入站链接。人工清扫只解决此刻，不解决下一次。
- **复用笔记门禁的链接检查逻辑** — 不用新写代码。否掉是因为两者职责不同：笔记门禁验的是「笔记之间的关系」，它跑在 vendored 的 `.ts` 脚本里，本仓库无权改（会被哈希门禁拦下）。而顶层文档不在它的扫描范围内。硬塞进去要么改 vendored 文件（被拦），要么绕过它（等于两条不一致的实现）。
- **把校验放进 `verify-plugin.mjs`** — 少一个文件、少一条 npm script。否掉是因为失败含义不同：`verify-plugin` 失败是「包装不上」，断链失败是「文档指向不存在的文件」。分开能让 CI 日志直接指向问题性质，也让 `md:links` 可以被单独跑。
- **报错时只列前 10 条以保持输出简洁** — 输出更干净。否掉是因为断链数量天然很少（弄断一条就该被立刻修）。限制条数会让「有 12 条断链」显示成「有 10 条」，而漏掉的恰是排在后面的。
- **允许指向仓库外的相对路径** — 更宽松，不会误伤 symlink 场景。否掉是因为本仓库没有跨仓 symlink 需求，而放开它会让 `../` 穿越变成合法输入 —— 一个只会被误用的口子。

## Consequences

- **收益**：补齐了「文档互相引用」这条链上唯一没有门禁的环节。`npm run md:links` 已接入 `npm run check`。
- **收益**：12 个测试 + 10/10 故障注入。故障注入分两层：**输入层**（往文档里塞坏链接，验证门禁会红）与**实现层**（把实现改错，验证测试会红）。后者抓到 4 条真缺口 —— 见下条。
- **收益**：实现层故障注入发现我的 4 条测试是**假的**：图片链接、尖括号目标、百分号编码、vendored 目录这四条，删掉对应实现后测试仍然绿。根因是它们用了「不存在的文件」构造用例 —— 那种情况下无论实现对不对都会报错，区分不出差异。改成用**真实存在的文件 + 编码形式**构造后全部变红。
- **收益**：顺带修掉两个真实的测试稳定性缺陷。`project-skill.test.mjs` 的 `cpSync` 没建父目录（`cp ENOENT ...\.agents\skills\agent-notes`）；`self-update.test.mjs` 用永不 resolve 的 fetch 留了悬挂后台任务，`finally` 里删掉目录后它还在跑。前者偶发红过一次，后者偶发红了两次 —— 都属于「本机能过、并发时炸」的类别。
- **代价与已知上限**：正则解析 Markdown 在极端写法下会漏（例如链接文字里含 `]`、目标里含未转义的 `)`）。这些写法在真实文档里罕见，而漏检的方向是**假绿**（漏报而非误报）—— 这个方向必须记住：它不会误伤，但也挡不住刻意构造的坏链接。
- **代价与已知上限**：不做锚点校验（理由见上）。
- **重访信号**：若开始使用 `#fragment` 链接，应改为引入 mdast 做 AST 解析并校验 slug —— 那时正则方案不再是正确选择。另一个信号：若文档里出现含 `]` 的链接文字导致漏检，同样该切到 AST。

## Verification

```sh
npm run md:links                       # 当前 28 文档 / 54 链接
node --test tools/md-links.test.mjs    # 12 个用例
npm run gate:fault-injection           # 含「自证清单必须有真实用例」
```

故障注入（已实测）：
- 输入层 10/10 —— 不存在的文件、尖括号目标、带标题目标、图片、路径穿越各自变红；存在的链接、代码块内链接、行内代码、绝对 URL、页内锚点各自放行。
- 实现层 10/10 —— 不跳过围栏代码块 / 不跳过行内代码 / 不校验越界 / 不检查存在性 / 不解码百分号 / 扫描 vendored 目录 / 只扫顶层 / 绝对 URL 当本地路径 / 尖括号不识别，各自变红。另有 1 条**等价变换**（去掉可选的 `!` 前缀）标注为「应仍绿」—— 它删掉后行为完全相同，不该变红，保留它是为了记住这个判断。
