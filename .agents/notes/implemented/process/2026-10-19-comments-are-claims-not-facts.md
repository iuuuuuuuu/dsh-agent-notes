# Agent Note: 注释里的「可用」是待验证的承诺，不是事实

Status: implemented

> 同属**流程补齐**这条线，是
> [2026-10-19-verify-notes-was-never-actually-standalone.md](../bug-fix/2026-10-19-verify-notes-was-never-actually-standalone.md)
> 的延续 —— 那一篇发现 `verify-notes` 的跨仓库承诺是假的，这一篇把
> 「这类承诺」当成一类资产**系统性核查**。
> 门禁盲区的处理见
> [2026-10-19-markdown-links-need-a-gate.md](./2026-10-19-markdown-links-need-a-gate.md)。

Independent: 本篇处理的是「如何对待声明性承诺」与「md-links 的目录目标崩溃」，
与注册状态机、发布记账、文档同步策略是不同的失效面。

## Problem

上一轮发现 `verify-notes.mjs` 的注释与 README 都写「任意仓库可用」，实测四种
用法全崩。那引出一个更值得问的问题：

> **仓库里还有几处类似的、写在注释里的承诺？它们有多少是真的？**

「脚本只依赖 Node 内建模块」「门禁要能对任意仓库生效」「同一份脚本能装进
任何仓库」—— 这些都是**声明**，而声明不会自己验证。

### 系统性核查：10 个门禁脚本逐个实测

把每个脚本拷到临时 git 仓库里真跑一遍：

| 脚本 | 结果 |
|---|---|
| `verify-notes.mjs` | 明确报错（上一轮修好的） |
| `notes-coverage.mjs` | 可用 |
| `notes-supersession.mjs` | 可用 |
| `doc-budget.mjs` | 明确报错（无清单时 exit 2） |
| `bilingual-docs.mjs` | 可用 |
| `md-links.mjs` | 可用 |
| `text-integrity.mjs` | 可用 |
| **`notices.mjs`** | **崩溃（ERR_MODULE_NOT_FOUND）** |
| `release-check.mjs` | 可用 |
| `install-hooks.mjs` | 明确报错（非仓库根时 exit 2） |

**9/10 站得住。** 唯一的崩溃者是 `notices.mjs`——但它**不该**被拷到别处
（README 与 AGENTS.md 都没承诺这一点），所以那不算违背承诺。

结论：**逐条核查之后，「任意仓库可用」这条纪律基本是兑现的**。上一轮的
`verify-notes` 是个例外，不是通例。这个区别很重要 —— 否则会误以为整个仓库
的承诺都不可信。

## Decision

### 一、核查方法本身值得固化

写一个探针，把 `tools/` 下每个门禁脚本拷进临时 git 仓库真跑一遍，按
「可用 / 明确报错 / 崩溃」三档归类。

关键设计：**区分「明确报错」与「崩溃」**。前者是正确行为（环境不具备时说清
怎么办），后者是缺陷（用户看到未捕获异常栈，不知道该做什么）。两者退出码
都非 0，光看退出码分不出来。

### 二、顺手修掉一个真缺陷：`md-links` 遇到目录目标会崩

核查 README 的「许可」章节时发现两版都写：

> vendored 上游内容版权归其作者，见 `skills/agent-notes/` 内注释与上游仓库。

实测那个目录里**没有任何版权声明**（唯一含 "MIT" 的是看板 UI 的一句文案
「遵循 MIT 协议开源」，那不是归属声明）。真正的归属声明在
`THIRD_PARTY_NOTICES.md` —— 它存在、有校验门禁，**两版 README 都没指过去**。

于是 MIT 要求的「保留原版权与许可声明」在分发物里没有入口，而读者被指向
一个不存在的地方。已修：两版都改为指向真实文件。

修的过程中发现 `md-links` 的一个缺陷：**指向目录**（例如链接目标写成
的链接会让 `readFileSync` 抛 `EISDIR`，**整个门禁崩溃**。

`must`：**门的崩溃与门的失败必须区分。** 崩溃时退出码非 0，看起来像「门禁
红了」，实际是「门禁没能运行」—— 那是本仓库最忌讳的形态：红的含义必须清楚。

现在会明确报「链接指向目录而非文件」，并给出怎么改（写全文件名）。

## Alternatives considered

- **把 `notices.mjs` 也改成跨仓库可用** — 让 10/10 都通过。否掉因为它**没有这个承诺**：它是本仓库专属的合规工具，生成自己的归属声明，不需要也不应该在别的仓库里跑。为一个没人需要的场景加依赖降级，是把「核查通过」的数字做漂亮，不是解决问题。
- **用 `require`/静态检查替代真跑** — 快得多。否掉因为上一轮的教训正是如此：静态检查抓不到「脚本就在眼前却看见不到」。**「跨仓库可用」这件事只有真跑才算数。**
- **把这次核查做成 `npm test` 的一部分** — 防止将来再退化。否掉（暂时）因为它要为 10 个脚本各建临时 git 仓库，耗时明显长于 `npm test` 现有的 30 秒预算。已记在重访信号里：**若某个脚本的跨仓库行为真的退化过两次以上，就该把它固化成测试。**
- **给 README 加一句「归属声明见 `skills/agent-notes/` 注释」就完事** — 零代码。但那句话本来就是错的，指过去的地方什么都没有。改对它比绕开它更便宜。

## Consequences

- **收益**：确认「脱离 DSH 也能用」这条纪律**基本兑现**（9/10 可用，1 个不适用）。这把一个笼统的自我评价变成了一份可核查的清单。
- **收益**：修掉两处 README 的错误归属指向。MIT 要求分发时保留归属声明，现在它在文档里有真实入口了。
- **收益**：修掉 `md-links` 遇到目录链接就崩的缺陷。这是**门禁可用性**问题 —— 它崩溃时没人知道是文档有问题还是门禁坏了。
- **收益**：`md-links` 新增一条测试，覆盖「目录」「目录 + 尾斜杠」「./ 前缀目录」与「图片指向目录」四种形态。
- **代价与已知上限**：核查脚本在 `.probe/` 下不入库，所以下次要复核得重写。但**判定依据的形态**（三档分类）写进了笔记，重写的成本很低。
- **代价与已知上限**：这次只核查了 `tools/` 下的**可执行脚本**。`lib/` 里的模块不单独跑（它们是被这些脚本 import 的），但如果将来某个模块也被直接当入口用，同样要过这一关。
- **代价与已知上限**：`md-links` 仍**不能**判断「指到的那个文件里真的有你要的东西」。本轮的缺陷正是这一类：README 指向 `skills/agent-notes/`，那**是个真实存在的目录**，所以「文件存在」检查通过；错的是「那里没有版权声明」。这类「存在但答非所问」的错误，本门禁结构上抓不到 —— 要抓它需要知道每个链接**期望**指向什么内容，那不是链接校验能做的事。
- **重访信号**：某个脚本的跨仓库行为**再退化一次**，就把这项核查固化进 `npm test`（而不是继续放在 `.probe/` 里）。另一个信号：若 `md-links` 将来需要更强的语义校验（比如「README 里的归属链接必须指向含版权声明的文件」），那已经超出链接存在性校验的范围，应作为独立门禁而非塞进 md-links。

## Verification

```sh
node --test tools/md-links.test.mjs   # 13 个用例（新增「指向目录」一条）
npm run check                        # 283 测试、33 篇笔记、16 道门禁
```

十脚本核查探针（`.probe/tmp/scan-standalone.mjs`，不入库）：每个脚本拷进
临时 git 仓库真跑，按「可用 / 明确报错 / 崩溃」三档归类。**判据是跑出来的，
不是读注释读出来的。**
