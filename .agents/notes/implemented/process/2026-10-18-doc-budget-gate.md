# Agent Note: 文档预算 —— 阻止 AGENTS.md 无限吸收「顺便补一句」

Status: implemented

> 本篇属于「借鉴 deepseek-harness 笔记规范」这组。
> 已落地的其他条目见

> [2026-10-18-notes-supersession-check.md](2026-10-18-notes-supersession-check.md)（新笔记与既有笔记的关系）、
> [2026-10-18-defensive-git-flags-not-optional.md](2026-10-18-defensive-git-flags-not-optional.md)（防御性 flag）。

## Problem

`AGENTS.md` 是给人读的规范文件。它有个结构性弱点：**每次改动都会往里面
吸收一句「顺便补上」**，而没有任何东西阻止它增长。

实测本仓库的曲线：

| 提交 | 词数 |
|---|---|
| `6cbefea` | 148 |
| `11ba8df` | 204 |
| `df71579` | 210 |
| `c6270f1` | 220 |
| `8194bf2` | 275 |

**不到一天翻倍。** 按这个速度，它很快会变成一份没人读完、也没人敢删的长文 ——
而「删它」需要逐条判断「这句还成立吗」，成本高到没人做。

DSH 对此的做法是给 7 个文件各设字数预算（`doc-budgets.manifest.json`：
`AGENTS.md` 2080、`docs/AGENTS.md` 1430…）。这是它多人协作下维持
文档可读性的机制。

## Decision

给「会持续增长」的散文文件设字数上限，做成门禁：

```json
{ "budgets": { "AGENTS.md": 2100, "README.md": 5900 } }
```

```sh
npm run doc:budget            # 检查
npm run doc:budget -- --update  # 有意放宽时写回当前值
```

**must**：预算刻意**贴近当前值**（只留几十的余量）。
留太多等于没设 —— 下次「顺便补一句」不会触发，机制就退化成装饰。

**must**：中文按**字**计、英文按**词**计，两者相加。
`wc -w` 对中文会严重低估（中文没有空格分词，一整段算 1 个词），
按词计数时中文文档的增长**永远触发不了预算**。

**must**：清单里有但文件不存在 → **红**，不是「无需检查」。
文件被删或改名后，那个预算项会静默失效 —— 那等于该文件失去保护。

### 2026-10-21：空清单按无效配置处理

预算清单必须至少包含一个预算项；普通检查与 `--update` 都在空清单时退出 2，且不写回清单。原实现接受 `{ "budgets": {} }`，并输出「0 个文件都在预算内」，使删除全部预算项成为静默绕过。

回归测试先在未修复实现上真实失败：预期退出 2，实际退出 0。加入非空校验后，`node --test tools/doc-budget.test.mjs` 的 9 项测试全部通过，`npm run doc:budget` 退出 0。测试同时检查普通模式、更新模式和清单内容保持不变。

收益是阻止预算保护被整体清空；代价是刻意停用预算时必须显式修改门禁配置，而不是留下空清单。本次不调整既有预算，也不改变中文计字、英文计词规则。

## Alternatives considered

- **允许空清单表示主动停用**：配置简单，也便于逐步接入。否掉：当前检查链将退出 0 解释为有效检查，无法区分主动停用与误删全部预算项；停用应通过明确的流程变更表达。

- **用行数或字节做预算** — 统计更简单。否掉：行数受排版影响（同一段
  可以写成 3 行或 1 行），字节数对中文严重不等价（一个中文字 3 字节，
  一个英文字母 1 字节）。词/字数更接近「读者要处理多少信息」。
- **用 `wc -w`** — 一行命令就行。否掉：中文按词计数会低估一个数量级。
  实测 `AGENTS.md` 的 `wc -w` 是 275，而按字计是 2014 —— 差 7 倍。
  用前者永远触发不了预算。
- **不设硬上限，改成「增长超过 X% 就警告」** — 更宽松，不阻碍正常更新。
  否掉：警告在 CI 日志里会被忽略，而**能被忽略的检查等于没有**。
  硬上限会真的拦住提交，逼出一次取舍。
- **靠人自觉控制篇幅** — 零成本。否掉：这正是当前失效的那一环。
  每次改动时人的注意力都在「把这次的事说清楚」上，不在「总量控制」上。
  这与 notes-coverage 里「多轮对话里必被挤掉」是同一个机理。
- **把 AGENTS.md 拆成多个文件来规避单文件上限** — 能绕过预算。否掉：
  那只是把同一份内容分到两个文件，读者要处理的总量没变。
  若确实需要拆分，拆的理由应该是「内容分属不同主题」，不是「躲预算」。
- **只在 CI 检查，不进本地钩子** — 少一处实现。否掉：本地写文档时
  就该知道还剩多少余量。实测我自己在写 AGENTS.md 时**查了一次余量**
  才决定怎么措辞 —— 那正是这个机制该起的作用。

## Consequences

- **收益**：`AGENTS.md` 与 `README.md` 的增长第一次有了约束。
  实测我自己加一行命令说明前先查了余量（86 → 71），
  **机制在第一次使用时就开始起作用**。
- **收益**：把「该不该加这一句」从模糊的自觉变成一次明确的取舍 ——
  想加就得先删掉同样多的字，或明确说「我要放宽」。
- **代价**：写文档时多一道心智负担。这是**有意**的，也是它的全部价值。
- **代价**：`--update` 提供了一条轻易放宽的路径，可能被滥用。
  缓解手段是它需要人主动敲一条命令并看到那句提示 ——
  比静默增长好，但仍不如「必须删掉等量内容」严格。
- **已知缺口**：只覆盖 `AGENTS.md` 与 `README.md`。`README.en.md`
  与 `.agents/notes/` 下的笔记不在预算内 —— 后者按设计可以长
  （每篇是一个完整决定），但**笔记总篇数**没有上限。
  重访信号：笔记树超过 50 篇且开始有重复主题时。
- **已知缺口**：**计费单位不等于可读性**。一份 2000 字的文档可能比
  另一份 3000 字的更难读（取决于结构、冗余、术语密度）。
  预算只能防「无限膨胀」，防不了「写得差」。

## Verification

```sh
node --test tools/doc-budget.test.mjs   # 6 项
npm run doc:budget
```

| 场景 | 期望 | 实测 |
|---|---|---|
| 超预算 | 红 | ✅ |
| 在预算内 | 绿 | ✅ |
| 中文按字计（30 字 vs 预算 20）| 红 | ✅（按 `wc -w` 会是 1，漏检）|
| 清单有但文件不存在 | 红 | ✅ |
| 清单损坏 | 退出码 2 | ✅ |
| `--update` 写回实际值 | 绿 | ✅ |

**故障注入（真红）**：

| 注入 | 结果 |
|---|---|
| 恒判「在预算内」 | 2 项红 |
| 中文按词计（`wc -w` 的错法） | 3 项红 |
| 清单损坏时 `exit 0` | 1 项红 |

**故障注入过程中修掉一处自己的缺陷**：第一版里「是否超预算」被**判定两次** ——
一次设 `status`，另一次独立算 `over`。故障注入打到其中一处时另一处仍在生效，
于是「注入后测试仍全绿」，掩盖了真实行为。已合并成单一真源
（`over` 从 `rows` 的 `status` 派生）。这与
[2026-10-18-notes-supersession-check.md](2026-10-18-notes-supersession-check.md)
里发现的「死代码 + 假绿测试」是同一类问题：**故障注入要能打到真正的判定点**。
