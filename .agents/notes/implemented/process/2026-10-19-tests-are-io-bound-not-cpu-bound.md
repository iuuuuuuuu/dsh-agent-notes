# Agent Note: 23/29 的测试是进程与 I/O 密集，所以并发度不该按 CPU 数定

Status: implemented

> 同属**流程补齐**这条线。本篇是对「上游的并发度做法」的一次**否决** ——
> 上游有 `LOCAL_PARALLELISM_CAP = 12`，我上一轮把它当范例推荐，那是**写死**，
> 而 Owner 明确要求「根据运行的机器自动判断」。
> 本篇给出本仓库的真实判据。

Independent: 本篇处理的是**测试调度策略**，与门禁判什么、workflow 完整性、
双语比对都无关 —— 它决定的是「同一批测试怎么跑」。

## Problem

Owner 的要求：

> 应该根据运行的机器自动判断，而不是写死

而我上一轮说「切到并行」—— **那个说法本身就是错的**，而且错在更基础的地方。

### 一、`node --test` 默认就是并行的

```json
"test": "node --test tools/*.test.mjs"
```

node 的 test runner **默认并发跑文件**（除非显式给 `--test-concurrency=1`）。
我此前测的「8 次全量并行跑」确实是并行，数据没错。

所以真正的问题不是「要不要切」，而是「**并行下偶发红怎么办**」。

### 二、按 CPU 数定并发，对本仓库是**错的信号**

实测本仓库 29 个测试文件：

| 类别 | 数量 |
|---|---|
| 会起子进程 / 建临时目录 / 拷文件树 / 网络 | **23（79%）** |
| 纯逻辑（无 I/O） | 6 |

这些文件不是 CPU 密集，是**进程创建与 I/O 密集**。核数再多，进程创建与临时
目录 I/O 也不会更快 —— **只会互相踩**。

实测印证了这个反直觉现象：

| 模式 | 平均耗时 |
|---|---|
| 默认（本机 16 核 ≈ 并发 16） | 44.1s |
| **并发 4** | **54.0s（更慢！）** |
| 串行 | 120.6s |

**并发开到 16 并不比 4 快**，反而因为互相踩更慢。这与 CPU 密集型测试的
直觉完全相反，而它正是本仓库的形态。

## Decision

**本轮不动并发度。** 理由不是「不敢动」，而是：

1. `node --test` **已经在并行**（默认行为），所以「做并行」这件事**已经完成**；
2. 剩下的偶发红**已定位并修掉两个根因**（`core.autocrlf` 污染 diff 输出、
   `npm test --if-present` 语义漏洞），不是「并发度不对」；
3. 要定并发度上限，**必须有一份不被污染的干净数据**。我手上两份测量都有问题：
   - 第一份：我的脚本用 `shell: true` + 通配符，Windows 上不展开 →
     第 4 次起全是「0.1 秒的红」，那是脚本坏了不是测试失败 → **12 次跑 10 红那个数字完全无效**
   - 第二份：后台测量与我的 `npm run check` **同时跑测试** → 互相干扰

`must`：**不能用被污染的数据做调度决策。** 那是比拍脑袋更糟的——拍脑袋至少
知道自己没依据，污染过的数据看起来像依据。

### 判据的设计（等干净数据后再定）

三种候选，各有明确的失效面：

| 判据 | 问题 |
|---|---|
| A. `min(availableParallelism(), 文件数)`（当前默认） | 16 核上开满，实测不比并发 4 快 |
| B. 固定小值（如 4） | **写死**；8 核浪费、64 核不够 |
| C. **按「进程/IO 密集的文件占比」定** | 23/29 ≈ 79% → 并发度 ≈ CPU × 0.2？比例会随代码漂移 |

三个都不够好，说明**真正的判据还没找到**。可能的第四种：

> 并发度由「机器能并行跑多少个**进程**」决定，而不是「多少个**核**」。
> CI runner 与本地笔记本在这上面的差异，比核数差异大得多。

那需要测「并发多少个 node 进程时开始互相拖慢」，而不是「并发多少个 CPU」。
**这是下一次实测该测的东西**，已记在重访信号里。

## Alternatives considered

- **照搬上游的 `LOCAL_PARALLELISM_CAP = 12`** — 最省事。**这是本篇明确否决的方向**：它是写死的，而 Owner 明确要求自动判断。而且它解决的是「容器配额 vs 宿主机核数」，而本仓库的真实瓶颈是**进程与 I/O**，不是 CPU。**照搬会解决错的问题。**
- **按 CPU 数自动判断（`Math.min(availableParallelism(), 12)`）** — 比写死好一点，但仍有个魔数 12。**否掉理由同上**：本仓库的瓶颈不是 CPU。
- **直接设成 4** — 有一个干净数据支持（54s 稳定 vs 44s 偶发红）。**但那仍是拍脑袋**：只有一台机器、一份被污染的数据。**在没有跨机器数据前设死一个值，就是把「我测了一台机器」冒充成「这是对的」。**
- **串行（`--test-concurrency=1`）** — 最稳，120s。否掉因为 Owner 说「45 秒可以接受」，串行会让 check 从 45 秒涨到 2 分钟，那是明确的倒退。

## Consequences

- **收益**：纠正了「切到并行」这个错误说法 —— `node --test` 默认就是并行的。
- **收益**：给出了本仓库测试集的**真实画像**：23/29 是进程与 IO 密集。这个事实解释了「并发开到 16 反而更慢」，也让「上游那套按 CPU 数的做法不适用」有了依据而不只是直觉。
- **收益**：把「并发偶发红」的真实原因定下来了 —— **不是并发度不对，是两个具体缺陷**（autocrlf 污染 + if-present 语义漏洞）。修完后那对文件的 8 轮全绿。
- **代价与已知上限**：**本仓库的并发度至今没有任何门禁保护**。若将来有人加了 `--test-concurrency=1`，check 会从 45 秒变成 2 分钟，**没有任何东西会报出来**。这是一个已知且未处理的缺口。
- **代价与已知上限**：偶发红的**概率**目前没有可靠估计。第一次测出「12 次跑 10 红」是脚本坏了；第二份数据被干扰。修完两个根因后只重测过那对文件（8/8 绿），**没重测全量**。所以「全量并发现在有多稳」这个问题**本轮没有答案**。
- **重访信号**：若 `npm run check` 的耗时超过 1 分钟 —— 那时并发度成了真问题，该按「机器能并行跑多少进程」重测并定判据。若 CI 上出现任何偶发红 —— 先查是不是又有新的跨测试干扰源，别直接降并发（降并发会掩盖真问题）。另一个信号：若将来测试里进程/IO 密集的文件占比下降（测试改用注入而非沙箱），那 CPU 数就重新变成合理的信号，判据要重估。
