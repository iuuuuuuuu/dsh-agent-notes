# Agent Note: 中英双语能比的只有语言标记，段落数不能

Status: implemented

> 同属**流程补齐**这条线，与
> [2026-10-19-bilingual-docs-compare-structure-not-length.md](./2026-10-19-bilingual-docs-compare-structure-not-length.md)
> 直接接续 —— 那一篇比「标题层级 + 围栏数量」，本篇回答「还能比什么」。
> 它也**替代**了本篇原计划的 mdast 方案（见 Decision）。

Independent: 本篇处理的是**双语比对的判据选择**，与门禁触发时机、
workflow 完整性都无关 —— 它改的是「比什么」这个判据本身。

## Problem

Owner 说「mdast 双语比对 做」。动手前我核实了两件事，结果**推翻了我自己给的理由**。

### 一、mdast 的增量看起来很明确

造 7 个「结构相同但语义不同」的中英样例，跑现有实现：

| 场景 | 现有正则 |
|---|---|
| 两版段落数不同 | **测不到** |
| 两版列表项数不同 | **测不到** |
| 一版用列表、一版用表格 | **测不到** |
| 两版链接数不同 | **测不到** |
| 两版代码块数不同 | ✔ 测到 |
| 两版标题层级不同 | ✔ 测到 |
| 英文版整段缺失 | ✔ 测到 |

**7 个里漏 5 个** —— 看起来 mdast 增量明确。

### 二、但那 5 个**不能**当门禁

翻 git 历史（16 个 commit × 2 版）：

| 指标 | 结果 |
|---|---|
| 结构不一致（现有门禁能测） | **0 处** |
| 语义计数不同（mdast 能测） | **30 处** |

看起来 mdast 该做有实证。但**逐条看过后，那 30 处是我方法的假象**：

- 列表项第 1–26 条**两版逐条对应**（同一条内容的两种语言）
- 差的 2 条在第 27、28 位：中文版排在**列表**里、英文版排在**正文段落**里
- 中文版还有 7 处是「一格多项」（顿号分项），英文版会拆成独立 item

**「段落数/列表数不同」在中英之间根本不是漂移信号** —— 两种语言的排版惯例
本来就不同。做成门禁会一直红，**且红了也没错**。

那是我第二次用「未经验证的方法」去论证一个结论。

## Decision

### 一、只比**语言标记**，因为它不承载语言

实测三个候选，只有一个无歧义：

| 候选 | 为什么（不）适合 |
|---|---|
| 段落数 / 列表项数 | ❌ 中英排版惯例不同，会常红且红得没道理 |
| 代码块内的命令行 | ❌ 命令**相同**，但**注释不同**（注释本就该翻译） |
| **围栏代码块的语言标记** | ✅ **完全相同** |

` ```sh ` / ` ```bash ` / ` ```yaml ` 翻译它没有任何意义，所以两版不一致
**一定是真漂移**。

### 二、**不需要 mdast**

判据就是「围栏行里那三个反引号后面跟的词」，它在**代码块内容之外**，
正则不会误吃块内文本（块内的 ` ``` ` 若未转义会提前闭合围栏 —— 那本身
就是坏的 Markdown）。

所以：**省掉了那个依赖**，只用十几行正则。

> 这是本篇最好的结果：**原计划引依赖，最后发现不需要**。
> 若当初直接按「mdast 增量 5/7」动手，会引入一个不必要的依赖去测
> 一件测错的事。

### 三、只取**开启**围栏，且**顺序也要比**

```js
const marks = [...text.matchAll(/(?:^|\n)(?:```|~~~)([^\n]*)/g)].map((m) => m[1].trim());
const fenceLangs = marks.filter((_, i) => i % 2 === 0);   // 开闭成对，奇偶位置是开
```

不取开启的会把一堆空字符串（闭合围栏的标记）混进序列，噪声大且易误判。

顺序也要比：同样的标记但前后不同，说明两版的示例顺序不一致。

## Alternatives considered

- **按原计划引 mdast 做完整 AST 比对** — Owner 说了「做」，且看起来增量明确。**这是本篇最强的一条被否方案**，而否掉它的过程本身就是本篇的价值：动手核实后发现那 5 个「增量」全是方法假象。**引一个依赖去测一件测错的事，是最坏的结果。**
- **比段落数/列表项数（mdast 的增量主体）** — 差值看起来很有说服力（30 处）。否掉因为逐条看过全是排版惯例差异。这类「数字很有说服力但经不起逐条看」的证据，是最容易被当成实证的 —— **数字必须能追到具体位置才算证据**。
- **比两版的链接目标** — 看起来也该比（路径不翻译）。**否掉因为唯一的差异是两版互链**（`README.en.md` 在中文版里、`README.md` 在英文版里）—— 那是**正确**的，不是漂移。直接判会假红。要比得先排除互链，那是另一个话题。
- **比代码块内容逐字一致** — 更严格。否掉因为代码块里**混着命令输出示例**（`查看开关与笔记树状态` / `Show switch and note-tree status`）—— 那是给人看的，自然要翻译。只比「命令本身」可行，但那要区分「命令」与「输出」的形态，比语言标记复杂得多，而语言标记已经覆盖了主要漂移面。

## Consequences

- **收益**：`docs:bilingual` 多了一道**无歧义**的检查 —— 语言标记漂移会红，且报错精确到具体标记。
- **收益**：**没有引入新依赖**。原计划的 mdast 方案被更好的方案替代了。
- **代价与已知上限**：语言标记只是**又一个**信号，不是全部。中英 README 里的「段落讲的是不是同一件事」**仍然只有人能判断** —— 本仓库的笔记里有 `docs:bilingual` 注释写明的重访信号（要判断语义需要翻译配对检查，可能是语言模型，也可能是人工维护的锚点映射表）。
- **代价与已知上限**：只取开启围栏的奇偶位置，隐含假设「围栏成对且不交叉」。**块内出现未转义的 ` ``` ` 会破坏这个假设** —— 而那本身是坏的 Markdown，会让两侧都算错。这类输入下门禁可能给出一个看似合理的错误结论。实测过：块内的 ` ``` ` 会提前闭合围栏，后续内容被当正文。
- **重访信号**：若将来某个语言版本的 README 出现「结构一致但内容讲的不是同一件事」的具体事故 → 那是语义级漂移，需要真正的翻译配对检查（可能是语言模型，也可能是人工维护的锚点映射表），本门禁结构上做不到。另一个信号：若开始出现「围栏嵌套」（外层 `~~~` 内层 ` ``` `），奇偶假设会失效，需要改成真正的状态机。

## Verification

```sh
npm run docs:bilingual              # 当前两版：语言标记本来就相同
node --test tools/bilingual-docs.test.mjs   # 14 个用例（新增 4 条）
```

**故障注入 6/6 全部符合预期**（用真实的 `verifyBilingual`，不是探针）：

| 注入 | 期望 | 实际 |
|---|---|---|
| 基线（两版一致） | 绿 | ✔ 绿 |
| 英文版 ` ```sh ` → ` ```bash ` | 红 | ✔ 红，点名「语言标记不一致」 |
| 只给一版加围栏 | 红 | ✔ 红 |
| **两版同时加同样围栏** | **绿（不误报）** | ✔ 绿 |
| 顺序不同但集合相同 | 红 | ✔ 红 |
| 闭合围栏被当成开启 | 绿（抽取正确） | ✔ `["sh","yaml"]` |

第四条最关键 —— 它证明这不是「只要有围栏就红」的假红门禁。
