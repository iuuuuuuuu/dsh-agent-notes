# Agent Note: 一条命令把别的仓库的门禁配套升到当前版本

Status: implemented

> 直接动因：Owner 让把这套装到 6 个在用仓库上。实测发现其中 **4 个仓库自带的格式门禁
> 仍是未修复版**（`l.indexOf("<!--")`），会把行内代码里的 HTML 注释标记当成真注释、
> 把合法笔记判红 —— 正是
> [2026-10-24-format-gate-masks-inline-code-as-comment.md](../bug-fix/2026-10-24-format-gate-masks-inline-code-as-comment.md)
> 修掉的那个缺陷，在那些仓库里**原样活着**。
> 手工再拷一遍解决不了：下次还是得手工。所以要一条命令。

## Problem

每个仓库各拷一份 vendored 脚本（`.agents/skills/<技能名>/scripts/` 或 `.agents/notes-scripts/`），
拷完就再没人同步。这类副本的漂移不会自己暴露：

- 会不会漂：会。6 个仓库里 4 份格式门禁是旧的，1 份归档脚本是**刻意的本地分叉**
  （wt-port 修了「全零 sha 静默通过」），1 个仓库根本没有脚本。
- 漂了会怎样：旧副本继续把合法笔记判红，而人只会去改笔记。
- 能不能手工发现：不能。同一份文件在不同仓库里有四种形态（原文、旧版、本地分叉、缺失），
  靠 diff 猜不出哪份是「旧」、哪份是「人家改的」。

## Decision

新增 `tools/configure-notes-gate.mjs --root <仓库>`，做三件**克制**的事：

1. **沿用目标仓库已有布局**，不另建第二份：
   - 有**完整**的 `.agents/skills/<任意名字>/scripts/` → 用它（实测有仓库用旧技能名
     `write-notes-like-deepseek`；另建 `agent-notes/` 会让「哪份生效」变成隐式约定）；
   - 否则有 `.agents/notes-scripts/` → 用它，assets 放 `.agents/assets/`
     （`build-board.ts` 按 `../assets/` 找模板）；
   - 都没有 → 建官方 `.agents/skills/agent-notes/`。
2. **只覆盖能证明是旧副本的文件**：与「未打补丁的原文」逐字相同 ⇒ 纯升级，写；
   其它不同 ⇒ 视为**本地改过**，跳过并打印原因（`--force` 才覆盖）。
3. **不碰**目标仓库的 `.agents/notes/`（那是内容）、它自己的门禁壳（`notes-gate.mjs`）
   与项目专用脚本（`notes-coverage.mjs` 之类）。

`--check` 供 CI 用（配套落后即退 1）；`--dry-run` 只打印计划。

`must`：**判断「能不能覆盖」时要认「旧副本」，不要认「不一样」。**
「不一样」里混着两种完全相反的东西：没跟上版本的旧文件，和别人刻意改好的修正。
把后者一起覆盖，等于拿「版本旧」换掉「人家的修正」—— 比不升级更糟。

## Alternatives considered

- **继续手工拷（本次就是这样发现问题的）** — 零新代码，也不用设计覆盖策略。**否掉因为它不可持续**：这次能拷，下次发版还得拷；而「谁拷了谁没拷」没有任何记录，漂移只是被推迟到下一次。
- **覆盖一切（不做本地修改检测）** — 语义最简单：目标仓库就是插件的镜像。**否掉因为它会抹掉真实存在的修正**：wt-port 那份归档脚本修的是「基线的三种查不到一律静默通过」，比当前上游更严；覆盖之后那个洞会重新打开。**「以插件为准」在这里不成立，因为插件自己还没修那条。**
- **把脚本作为 npm 依赖装进目标仓库**（`@iuuuuuuuu/agent-notes` 装成 devDependency）— 版本管理最正规，`npm update` 就能升级。**否掉因为多数目标仓库不是 Node 项目**（Flutter/Rust/混杂），为几个 `.ts` 门禁引入 `node_modules` 不划算；而且插件已按「零 `@deepseek-ai` 依赖」设计，不该反过来要求宿主有包管理器。
- **只校验、不改写**（`--check` 单独使用）— 最安全。**否掉因为它把「怎么改」留给用户**：报告「你需要更新 7 个文件」，然后人去 diff 四份形态？本轮实测已经证明人工判断会错（4 份旧副本一直没人发现）。
- **强制一个统一布局（全部迁到 `.agents/skills/agent-notes/`）** — 一个仓库只有一份，最好维护。**否掉因为迁布局会连带改调用方**：`notes-coverage.mjs` / `notes-selftest.mjs` / CI 都硬编码了 `.agents/notes-scripts/`，迁移是一次跨文件重构，与「升级门禁」这件事本身无关。

## Consequences

- **收益**：一条命令让 6 个仓库的门禁配套跟上当前版本；实测 4 份旧副本被升级、1 份本地分叉被跳过（并打印原因）。
- **收益**：`--check` 让「配套落后」变成可被 CI 抓住的事实，而不是靠人记得。
- **收益**：升级后行为可验证 —— CloudeMusicX 里放一篇「行内代码写 `<!--`」的笔记，
  它自己的脚本现在 `ok: 15 note(s) verified`（修复前会报「缺 ## Consequences」）。
- **代价与已知上限**：「旧副本」的判定靠**与未打补丁原文逐字相同**。上游一旦改动这些脚本，
  旧副本就不再逐字相同 ⇒ 会被当成「本地改过」而跳过。这是保守方向（宁可不改），
  代价是升级会变迟钝，需要人看一眼 `--check` 的报告。
- **代价与已知上限**：工具只同步 `scripts/`、`assets/` 与（新建时）`SKILL.md`/`references`/`templates`。
  目标仓库若自己扩了 `notes-gate.mjs` 之类的壳，那层不会被更新 —— 有意为之。
- **代价与已知上限**：它**不写笔记、不提交**。每个仓库要不要为这次同步留记录，由那个仓库自己决定；
  本轮用的是 `Note-Skip:`（机械同步，决策在插件仓库记过一次）—— 同一个决定写 6 遍是噪声。
- **重访信号**：
  - 若「旧副本」判定开始频繁误判为「本地改过」→ 说明该把补丁/版本号写进文件头，
    用显式标记判断来源，而不是逐字比对。
  - 若目标仓库开始出现第三种布局 → 先在 `resolveLayout` 里加，再考虑统一迁移。
  - 若某个仓库的分叉修好之后被上游采纳 → 那份分叉应当删掉，改回标准副本。

## Verification

```sh
node --test tools/configure-notes-gate.test.mjs   # 8 tests / 8 pass
npm run gate:fault-injection                      # 51 个测试文件全部登记
```

8 条用例覆盖：三种布局选择、旧副本安全升级、本地修改跳过（含 `--force`）、
`--check` 的 1/0、`--dry-run` 不落盘，以及**端到端**那条（配置后用目标仓库**自己的**
格式门禁跑一篇「行内代码写 `<!--`」的笔记，必须 `exit 0`）。

真实仓库验证（6 个在用仓库）：

### 顺带修掉的真缺陷：上游校验会永久挂住

配置过程中那条「不存在的 ref」用例开始稳定超时（120s）。手工复核发现不是抖动：
不带超时的 `fetch` 遇到「服务端接受连接却永不响应」会**一直等** —— CLI 45 秒零输出。
CI 上 `upstream-sync.yml` 定时跑 `--auto`，这会把 job 挂到平台超时；
而**门禁挂住比门禁红更糟**：没有任何结论，也没人看得见。

修法：每次请求带 20 秒超时；超时判「环境问题」（exit 2）且**不重试** ——
不响应的端点不会在 250ms 后恢复，重试只会把等待乘以三；错误里带上 URL，
否则「哪个请求卡住」无从判断。同一场景现在 21 秒以 exit 2 结束。

回归：`tools/sync-upstream.test.mjs` 新增一条**真服务器**用例（接住请求、永不回包），
断言超时在 5 秒内触发、消息里有地址、判为环境问题且不可重试；
真变异（丢掉错误的 `name`）⇒ 该用例红。

### 2026-10-25：force 拆成两类，且「跳过」必须可见

真实事故：我用一个 `--force` 同步仓库级工具，顺手把 route-deck 里**本地 fork 过**的
`verify-archived-agent-notes.ts` 覆盖了（那 fork 修的是短名/长名路径问题）。
`git checkout` 还原后更有意思：再跑 `--dry-run` 只看到「一致 9，需更新 0」，
**完全看不出那份 fork 被跳过、更看不出它存在** —— 因为 `main()` 从来没打印过 `skipped`。

两处都修了：

1. **`--force` 拆成 `--force-vendored` / `--force-tools`**（`--force` 保留为两者都强制，
   但会打一行告警）。依据是实测出来的不对称：6 个在用仓库里 **2 个** fork 过 vendored 脚本
   （route-deck、wt-port 的归档脚本），而那两个仓库级工具**没有任何仓库动过**。
   用一个开关把两种风险捆在一起，只想更新工具时就会误伤别人的修正。
2. **`skipped` 逐条打印**（文件路径 + 原因 + 该用哪个 flag），`--check` 另外补一句
   「N 个文件与当前版本不同，但按规则未被检查/更新」。否则 `--check` 的「已是最新」是假绿：
   它只比对了它自己打算写的那些文件。

回归 8 → 11 条；真变异：不打印 skipped ⇒「被跳过的文件必须出现」红；
vendored 一律覆盖 ⇒「--force-tools 不会碰本地 fork」红。
