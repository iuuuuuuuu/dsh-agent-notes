# Agent Note: 门禁的语料不得被悄悄收窄 —— 语料下限与区域对账

Status: implemented

> 承接[三层检查必须对齐](../process/2026-10-18-three-layer-checks-must-align.md)
> 与[自证清单必须与磁盘对账](./2026-10-21-fault-injection-list-must-reconcile-with-disk.md)：
> 那两篇管「门禁被绕过」与「门禁自己的测试没登记」，
> 本篇管第三种失效：**门禁还在跑，但它的语料被改小了**。

Independent: 本篇只增加一道「语料覆盖面」的横向判据；
各道门禁各自判什么、以及它们各自的空集合行为，都不变。

## Problem

门禁判定的是**语料**。语料被收窄时，门禁不会红 —— 它只是变得没那么有效了，
而报告上写着「通过」。

本轮实测过的三种收窄，每一种**都让整条 `check` 链 exit 0**：

1. `tools/md-links.mjs` 里删掉 `walk('docs')` → `docs/` 整个不在语料里，
   而那 2 篇文档正是全仓唯一承载 46 道判定表的产物（`docs/upstream-46-gates.md`）。
2. `tools/text-integrity.mjs` 的递归改成只看顶层 → 97 篇笔记全部脱离扫描。
3. `tools/doc-refs.mjs` 的源码侧扫描目录从 4 个缩成 1 个 → 源码侧引用大半消失。

这三种都不是「门禁被删了」，而是「门禁变钝了」。它们的共同点是**没有声音**：
门禁照常打印「通过」，退出码 0，CI 全绿。

上游 A 对这件事有明确判据。`scripts/verify-concrete-terms.ts:56-61`：

```ts
if (!files.includes('AGENTS.md')
    || !files.some((f) => f.startsWith('packages/'))
    || !files.some((f) => f.startsWith('docs/'))
    || !files.some((f) => f.startsWith('vendor/'))
    || !files.some((f) => f.startsWith('.agents/notes/archived/'))) {
  throw new Error('verify-concrete-terms: tracked-file discovery omitted a required repository area');
}
```

它的关键点不是「数字要够大」，而是**按仓库区域对账**：语料必须仍然覆盖每一个
该覆盖的区域。数字会随仓库长大而失效，区域不会。

## Decision

新增 `tools/corpus-floor.mjs` 与 `tools/corpus-floor.manifest.json`，
做成两层判据。

**第一层：区域覆盖（主判据）。** 每道门禁登记它**必须仍然覆盖**的仓库区域。
语料收集用的是**那道门禁真正在用的收集函数**（`collectDocuments` /
`collectDocRefDocuments` / `collectSourceScanFiles` / `collectFiles` /
`listTrackedFiles`），不是重新实现一遍 —— 重新实现等于测了一份副本，
真实的收窄照样发生而门禁不红。

本门禁覆盖 5 道门禁：`md-links`、`doc-refs`（文档侧 / 源码侧分开登记）、
`text-integrity`、`eol`。

**第二层：数量下限（辅判据）。** 每道门禁在 manifest 里记一个下限
（`{min, reason}`），语料条数不得低于它。下限**下调必须写理由**，
没有理由的下限会被悄悄调小 —— 门禁自己也因此红。

区域划分用**目录前缀**而不是后缀白名单：后缀白名单会随新增目录而悄悄失效
（实测 `text-integrity` 的后缀白名单就漏掉了 4 个无扩展名文本文件：
`.gitignore`、`.gitattributes`、`LICENSE`、`.githooks/commit-msg`）。

`vendored`（`skills/agent-notes/`）**不在** `text-integrity` 的区域清单里 ——
它刻意跳过 vendored（本仓库无权改它），要求它覆盖 vendored 会与设计矛盾。

接进 `package.json` 的 `check` 链（`npm run corpus:floor`）与
`.github/workflows/verify.yml` 的独立步骤；登记进 `tools/fault-injection.mjs`
的声明表（该表与磁盘双向对账）。

## Alternatives considered

- **只比数字（语料条数不得低于某个阈值）**：实现最简单，十几行就能写完。
  仍然否决：数字有个致命的失效形态 —— 把 `docs/` 的 2 篇删掉、再从别的目录
  补 2 篇，数量不变但覆盖面变了。**区域对账抓得住这个**，因为 `docs` 是一个
  区域，它的条目数会掉到 0。两条判据合起来才够：区域保证「该看的地方还在看」，
  数量保证「看得够多」。
- **在各道门禁内部各自加一条「语料不能为空」**：这是最省事的形式，而且
  `doc-refs.mjs` 已经这么做了（`:364-365`、`:422-423` 的空集合守卫）。
  仍然否决：空集合只是**最极端**的收窄形态。真实的收窄是「从 97 篇变成 3 篇」，
  语料非空，守卫不会响。要抓它就必须横向对账，而横向对账需要一个知道
  **所有**门禁语料的地方 —— 那就是本门禁。
- **把区域对账做成 `ci-alignment.mjs` 的一种新判据**（那个门禁已经在对账
  「CI 有没有跑这道门禁」）：少一个文件、少一条 npm 脚本。仍然否决：
  `ci-alignment` 判的是**workflow 文本与 package.json 的一致性**，
  语料覆盖是**代码运行时**的属性。两件事塞进一个脚本会让它的失败信息变成
  两类互不相干的结论，而它本来的定位是「门禁自身的基础设施有没有被改坏」。
- **自动发现所有门禁的语料**（像 `fault-injection` 那样从磁盘反查）：
  自动、不会漏。仍然否决：每道门禁的语料收集函数形状不同（有的返回文件、
  有的返回相对路径、有的含豁免规则），自动发现只能猜；而**猜错的后果是
  假红**（把某道门禁合法豁免的目录算进它的必需区域）。显式登记表虽然要人写，
  但它同时是一份**意图声明** —— 写下来才知道这道门禁到底该看什么。
- **下限只写数字、不写理由**：省事。仍然否决：没有理由的下限会被人随手调小
  来「让门禁先绿」，而这正是这道门禁要防的事。把理由变成必填项，调小就要
  解释。

## Consequences

- **收益**：上面三种实测收窄现在都会红。region 判据抓「某块区域整个脱离语料」，
  数量判据抓「整体缩水但区域还在」。
- **收益**：语料**变大**不红 —— 仓库长大（新增笔记、新增工具）不该被当成缺陷。
  这一点有专门的用例守着。
- **代价**：每道门禁的「该看哪些区域」要人写一次，且仓库结构变了要跟着改。
  这类漂移**会被本门禁自己抓到**（区域消失会红），但前提是有人记得改登记表 ——
  改登记表时它会报「这个区域现在没有文件」，那正是提示。
- **代价与已知上限**：本门禁只认**目录前缀**。某个门禁如果把语料从多个区域
  合并到别处（例如把 `docs/` 的文档搬进 `notes/`），区域判据会误报「docs 区域缺失」——
  这是**假红**，但假红的方向是安全的（会引人去看）。
- **已知上限**：下限是**当前值附近的锚点**，不是精确值。仓库大幅缩小（比如
  大量笔记被归档）时下限需要调整，而调整需要写理由 —— 这是有意的摩擦。
- **已知上限**：本门禁只覆盖已登记的 5 道门禁。将来新增门禁若不登记，
  本门禁对它无感 —— 这一点靠 `fault-injection` 的双向对账**不能**覆盖
  （那张表对的是测试文件，不是门禁语料）。**这是一个尚未关闭的缺口**，
  重访信号：新增门禁时检查是否需要登记区域。

## Verification

```sh
node --test tools/corpus-floor.test.mjs
# tests 10 / pass 10 / fail 0                                     (exit 0)
```

10 条用例：当前仓库语料齐全（绿基线）1 条；`areaOf` 区域划分（归档必须先于
笔记命中、vendored 单列）1 条；**删掉 `docs/` 语料必须红** 1 条；
**笔记树整体脱离语料必须红** 1 条；数量低于下限必须红 1 条；
**语料变大不得红** 1 条；清单缺条目 / 下限无理由必须红 1 条；
下限必须为正整数 1 条；真实清单每条都写了理由 1 条；
**CLI 在语料被收窄时非零退出**（真跑子进程）1 条。

用例的夹具是**临时目录里的迷你仓库**，`collect` 会真的去那里找文件 ——
门禁的价值恰恰在于「它查的是门禁真正在用的那个收集函数」。

**真故障注入**：把 `tools/corpus-floor.mjs` 的区域判据
`if (!present.has(area))` 改成 `if (false)`（区域对账整体失效）→
**8 pass / 2 fail**，红的正是「删掉 `docs/` 语料必须红」与
「笔记树整体脱离语料必须红」两条区域用例；还原后（`diff` 逐字比对一致）
10/10 绿。

注意这两次红**没有波及**数量下限那几条 —— 数量判据与区域判据是两条独立
的线，这正是把它们分开的理由：一条失效时另一条仍然有效。

`node tools/corpus-floor.mjs` → 退出码 0，输出「语料下限通过：5 道门禁的语料
都仍覆盖各自应有的区域，且不低于记录的下限。」

这些是离线回归结果，不是实机验证，也不是「上游对齐已完成」的结论。
