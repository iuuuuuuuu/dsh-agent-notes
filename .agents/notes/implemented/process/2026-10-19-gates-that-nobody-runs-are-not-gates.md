# Agent Note: 门禁存在但没人跑它，等于没有门禁

Status: implemented

> 同属**流程补齐**这条线，且直接接续
> [2026-10-19-ufffd-passes-every-gate.md](./2026-10-19-ufffd-passes-every-gate.md)
> （那道字符门禁是本篇要修的那个「不可靠」的部分）。
> 钩子的原有设计见
> [2026-10-18-notes-coverage-gate.md](./2026-10-18-notes-coverage-gate.md)。

Independent: 本篇处理的是「门禁**何时被触发**」，与门禁**判什么**
（字符损坏、链接可达、归属一致、CI 对齐）是不同的问题 —— 那些门禁本身是对的。

## Problem

字符完整性门禁（`text-integrity`）在 PR #3 上线。它**每次都正确工作**。

但 Owner 在我写笔记时指出：

> 你在写的过程中遇到了乱码，把这个也加入门禁吧，防止以后发生这种情况
> 而不自知，一直留在项目里面

核查后发现：**门禁早就在，CI 也早就在跑**（PR #3 那轮就把 `text:integrity`
接进了 CI）。真正的问题不是「门禁不够」，而是——

### 数据：门禁一次都没被绕过，是人一次都没跑它

```
门禁上线于 45948a4，此后有 2 个提交
结论：门禁上线后，2 个提交里没有一个把乱码带进历史。
```

**历史是干净的。** 但我自己在这几轮里反复写出乱码（至少 5 次），每一次
`text-integrity` 都报红——我只是**没在提交前跑它**。

所以真实缺陷不是「门禁漏了」，是：

> **门禁靠「记得跑」触发。** 而记得跑这件事，在「紧急修个 CI 问题」的
> 场景里必然被挤掉——注意力全在「让它绿」。

这比假绿更隐蔽：门禁明明在工作，日志里甚至能看到它报红，只是**没有人
执行它**。

### 同一个毛病还有第二处

比对本仓库 `check` 链与 CI 的 `verify` job：

```
本地 check 链有、但 CI 没跑的步骤：
  ✖ notices:check  ✖ md:links  ✖ docs:bilingual
  ✖ text:integrity  ✖ release:check
```

**连续三轮加了五道门禁，全都只接进了本地 `npm run check`，CI 一道都没跑。**
后果：那五道门禁红过时 CI 毫无反应。这与字符门禁是同一种病：门禁存在，
但没人执行它。

## Decision

### 一、提交那一刻自动跑，不靠记性

`commit-msg` 钩子从 **2 道**扩到 **8 道**：

| 门禁 | 为什么必须在提交那一刻 |
|---|---|
| 字符完整性 | **已经漏过 5 次**，每次都是「门禁红了但我没跑」 |
| 门禁对齐 | 接不进 CI 的门禁等于没有；它是那个缺陷的发现者 |
| Markdown 链接 | 归档笔记后入站链接无人修，钩子是即时反馈 |
| 双语结构 / 归属声明 / 发版记账 | 毫秒级，改文档时最常踩 |
| 覆盖 + supersession | 原有两道，保留 |

钩子正文拆到 `tools/hook-body.mjs` 导出 —— 因为它**是门禁的门禁**，
藏在 `install-hooks.mjs` 的模板字符串里就没法单独测。

`must`：**只放快门禁，不放 `npm test`。** 283 个用例约 34 秒；每次提交
都等这么久，人就会转去 `--no-verify`——那时门禁彻底失效，比没有更糟
（因为它还给人「有门禁」的错觉）。完整套件仍由 CI 兜底，那才是权威。

### 二、新增门禁对齐检查，让这类漏接不可能再发生

`tools/ci-alignment.mjs`：本地 `check` 链里的每一步都必须在 CI 里出现。

判据分两类：**判据只依赖当前文件内容**的必须进 CI；**依赖变更范围**的
（coverage / supersession）由 CI 用 `event.before..HEAD` 单独跑，豁免必须
在 `CI_ALTERNATIVES` 里登记理由。

`must`：**豁免必须显式登记。** 否则将来有人删掉 CI 那步时，本门禁不会
知道少了东西 —— 那正是它要防的那类缺陷。

## Alternatives considered

- **只提醒「提交前记得跑 npm run check」**（写进 CONTRIBUTING） — 零代码。**这是已经失败的方案**：字面上「加门禁」的那一轮我就跑过 check，文档里也早就写着「提交后跑」。人的记性在紧急场景里靠不住，靠的是机制。
- **把 `npm run check` 整个塞进钩子** — 一行就能接全。否掉因为它含 `npm test`（34 秒）+ `gate:fault-injection`（多个子进程）。代价是每次提交等半分钟以上 → `--no-verify` → 门禁作废。**慢门禁放进即时钩子等于把门禁拆掉。**
- **用 husky 管理钩子** — 生态成熟、多钩子支持。否掉因为那引入 devDependency 与一层封装，而本仓库只需要一个 `commit-msg`；且 husky 自己也要被 `npm run hooks:install` 装上，并没有减少安装步骤。
- **把字符检查改成 pre-commit 而非 commit-msg** — 时机更早。否掉因为 `Note-Skip:` 写在提交信息里，pre-commit 阶段还读不到，会把合法出口堵死（这在已有笔记里记录过）。
- **让 CI 成为唯一防线，钩子只留原来两道** — 少改。否掉因为 CI 反馈要等 push + 跑完一轮，而「本地全绿、CI 变红」正是最难排查的一类。作者能在 5 次里全靠 CI 兜住，说明这道兜底虽然有效但**太晚也太贵**。

## Consequences

- **收益**：乱码从「靠记性」变成「跑不掉」。实测验证：真仓库里提交含 U+FFFD
  的文件被**第一道门禁拦下**（exit 0），正常提交**被放行**（八道全跑过）。
  验证过程本身还抓到了 `hook-body.mjs` 里我自己写的一处乱码。
- **收益**：五道门禁从「只有本地跑」变成「CI 也跑」，并新增对齐门禁让这种
  漏接不可能再无声发生。
- **收益**：新增 16 个测试（`hook-body.test.mjs` 10 + `ci-alignment.test.mjs` 6）。
- **代价与已知上限**：钩子可被 `--no-verify` 绕过。这**是有意的** ——
  `Note-Skip:` 是合法出口，堵死它只会让人更坚定地绕过。所以 CI 仍是权威，
  钩子是即时反馈。这个定位必须一直记着：钩子红是提醒，CI 红才是权威。
- **代价与已知上限**：钩子只跑**快子集**，`npm test` 仍只在 CI。所以
  「提交前全部验证过」这句话**不成立** —— 只有 8 道跑过。
- **代价与已知上限**：钩子每条命令都起一个 node 进程（约 3–5 秒）。为省时间
  而不加并发，理由是可读性比 2 秒更重要——钩子失败时要能一眼看出是哪一道。
- **重访信号**：若某道门禁**再退化一次**（钩子漏了），说明该把它从「记得跑」
  升级成别的机制（例如写进 `npm run prepare-commit`）。另一个信号：若仓库
  将来引入 husky 或 lefthook，应把这份钩子正文整体迁过去而不是并存两份 ——
  两份钩子定义必然漂移。

## Verification

```sh
node --test tools/hook-body.test.mjs        # 10 个用例
node --test tools/ci-alignment.test.mjs    # 6 个用例
npm run ci:align                            # 10 道内容型门禁都在 CI 里
npm run check                               # 299 测试、16 道门禁
```

**真仓库实测的两组证据**（探针在 `.probe/` 不入库，因为它们要真提交）：

| 场景 | 结果 |
|---|---|
| 提交含 U+FFFD 的文件 | **被拦 ✔**（字符完整性拦下，`exit 0`） |
| 提交正常文件 | **通过 ✔**（八道门禁全跑过，无误拦） |
| 跑完后工作区 | **与跑之前完全一致 ✔** |

### 验证过程里踩到的三个坑

1. **沙箱不真实 ≠ 钩子不对。** 在临时沙箱里验证，对照组连续失败三次，
   每次原因都是沙箱不完整（缺 `node_modules` → notices 模块解析失败；
   造的 `package.json` → 归属声明不一致；只有 1 篇笔记 → AGENTS.md 链接全断）。
   **现象与「钩子逻辑错」完全一样，修复方向相反。** 最后回到真仓库验证 ——
   那里的一切本来就完整。

2. **`git reset --hard` 会毁掉当时所有未提交工作。** 我的探针原本设计成
   撤销后 `reset --hard` 复原，而那一刻工作区里正躺着本轮刚写的 5 个文件。
   改为 `reset --soft` + 精确清索引，并加「跑前跑后对比工作区」断言。
   这个仓库历史上已被它毁过 5 次 —— 验证脚本自己更不能是事故源。

3. **作用域错误让清理代码静默失效。** `usedRealCommit` 声明在 `try` 块内，
   `finally` 读不到 → ReferenceError → **清理没执行** → 探针提交
   `116b2a4` 与文件留在了仓库里。失败发生在清理阶段，而清理失败往往
   不显眼。已手工撤销并确认工作区与预期一致。

### 一个反复出现的模式

本轮第三次撞上「扫全文没区分注释与命令」：`ci-align` 的第一版把某一步换成
**注释行**后仍判定「已覆盖」而全绿；`hook-body` 测试的第一版断言扫全文，
把自己那句「为什么不跑 `npm run check`」当成了违规。

两者都是：**验证 A 时若连 A 的说明文字一起匹配，就分不清「A 存在」与「提到 A」**。
