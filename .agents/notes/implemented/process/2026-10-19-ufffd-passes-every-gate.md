Independent: 本篇处理的是**字符级内容损坏**，与链接可达性、结构一致性、
同步流程是不同的失效面 —— 那些坏的是「指向错了」，本篇坏的是「内容本身」。

## Problem

写一篇 rejected 笔记时，正文里出现了 5 处 **`<U+FFFD>`（U+FFFD 替换字符）**——
中文被截断后留下的痕迹。它安静地待在段落中间：

```
它会在半年␦␦被人重新提起
见上␦␦被否的第三条
版本段必须严格递减（␦␦␦件里最新版本在前）
```

**所有现有门禁都看不见它。** 实测一份含 U+FFFD 的 Markdown 过 `md-links`：

```
md-links 对损坏字符的反应: errors = 0 → 放行（没拦）
```

笔记门禁也不拦：格式完全合法 —— 标题层级对、段落结构对、链接可达。**只是内容坏了。**

### 为什么它能穿过所有检查

U+FFFD 本身是**合法的 UTF-8 字符**。它是无损检测的结果：某个字节序列无法
解码，就用 U+FFFD 代替。文件因此在编码层面完全正常。

也就是说：

| 检查 | 为什么抓不到 |
|---|---|
| 编码合法性 | U+FFFD 本身就是合法字符 |
| `md-links` | 链接结构没变 |
| 笔记格式门禁 | 标题/段落/链接都合规 |
| `docs:bilingual` | 结构对齐，只是内容坏了 |

### 危害

它比「错别字」严重得多：读者看到「见上␦␦被否的第三条」只会以为作者写了个
怪字，**不会想到是编码损坏**。而且一旦提交就进历史，永久留在文档里 ——
`git grep` 都找不全（实测它扫出 0 处，而门禁扫出 12 处）。

## Decision

新增 `tools/text-integrity.mjs`（`npm run text:integrity`，已接入 `check` 与 CI）：

1. **拒绝 U+FFFD** —— 字节损坏的确凿证据，一律拦。
2. **拒绝裸控制字符**（除 `\t` `\n` 外，含 DEL）—— 通常是脚本拼接漏转义。
3. 报错带**文件名 + 全部行号**，便于直接定位。

`must`：**只抓「确定是错的」，不抓「不够好」**。措辞、换行、列表风格是风格，
不是损坏。这道门禁若开始报风格问题，会被立刻绕过 —— 那时它保护不了任何东西。

`must`：**不扫 vendored 上游内容**（`skills/agent-notes/`）。本仓库无权改它，
它可能有自己的编码习惯。上游内容由哈希门禁负责。

`must`：**测试数据不得用 U+FFFD 字面量**。本门禁会扫到测试文件本身，而那里
的 U+FFFD 是**故意构造的** —— 写成字面量会让门禁永远红，且无法区分
「测试数据」与「真损坏」。

所以测试里用 `String.fromCharCode(0xfffd)` 构造：测试语义完全不变（生成的
就是 U+FFFD），但源码里没有那个字节。

`must`：**不能用 `grep` 找 U+FFFD**。实测 `grep -rl $'\ufffd'` 扫出 0 处，
而门禁扫出 12 处 —— shell 与编辑器对损坏字节的解码路径不同，grep 不可信。
判断依据必须是真实的 code point。

## Alternatives considered

- **让 `md-links` 顺手检查字符完整性** — 少一个文件。否掉因为两件事的失效面完全不同：断链是「指向错了」，字符损坏是「内容本身坏了」。合并后报错的文件名会让人分不清是哪类问题。
- **只靠 pre-commit 钩子拦，不进 CI** — 零配置。否掉因为钩子可被 `--no-verify` 绕过（本仓库已有三道 CI 权威门禁的设计前提），而且字符损坏恰恰是「本地看着好好的」的那类问题 —— 它最需要远端那道。
- **用 `grep -P` 或 `iconv` 在 CI 里查** — 零新代码。否掉因为见上面那条：**grep 在这个问题上不可靠**，实测漏报全部 12 处。门禁必须是确定性的代码，不是 shell 组合。
- **顺手把措辞/换行也一起检查（做成一个「文档质量」门禁）** — 看起来一次做完更省事。否掉因为风格检查的误报率必然高，而误报多的门禁会被绕过，之后连字符检查也一起失信。**宁可只抓一种确定的错。**

## Consequences

- **收益**：补上了「所有门禁都漏」的那一类损坏。首跑就抓出 **12 处**，散落在 7 个文件里 —— 其中**包括已合并进历史的笔记**（PR #1 那批 8.3 短路径笔记）。它们已经污染了仓库一段时间，只是没人看得见。
- **收益**：8 个测试 + **7/7 故障注入全部符合预期**（含「只报第一处损坏」「行号基准写错」「把制表符当控制字符（误伤）」「扫描范围收窄」）。
- **代价与已知上限**：这个门禁**抓不出「字节没丢但内容错了」的情况**。例如把「必须」手写成「必需」—— 那是拼写错误，不是损坏，本门禁看不见。
- **代价与已知上限**：已污染的那 12 处里，有一部分在**已推送的历史**中。修的是当前 HEAD，**历史里的旧版本仍然带损坏**。彻底清除需要改写历史，而本仓库明令禁止裸 `--force`（且 `main` 已有分支保护）。这是有意接受的：改写历史的代价高于它要解决的问题。
- **代价与已知上限**：测试必须用 `String.fromCharCode` 构造 U+FFFD，这让测试数据**不如字面量直观**。已在测试文件里写明理由，避免下一个维护者「顺手改回字面量」然后门禁变红。
- **重访信号**：若仓库开始引入非 JS/MD 的文本文件（`.txt` / `.rst` / `.adoc`），要把它们加进 `EXTENSIONS` —— 否则新格式的内容不受保护。若将来支持非 UTF-8 文件，需先确认 U+FFFD 的判定是否仍然适用。

## Verification

```sh
npm run text:integrity              # 当前 103 个文件
node --test tools/text-integrity.test.mjs   # 8 个用例
```

故障注入（已实测，7/7 全部符合预期）：不检测 U+FFFD、只报第一处损坏、
行号基准写错成 0 起算、把制表符当控制字符（误伤）、扫描范围收窄、
连 vendored 也扫、错误信息缺文件名。

其中「连 vendored 也扫」标注为**应仍绿** —— 上游副本当前没有损坏字符，
扫了也不该红。它验的是「纳入 vendored 不会引入假红」。
