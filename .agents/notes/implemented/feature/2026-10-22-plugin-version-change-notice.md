# Agent Note: 插件版本变了要主动说一句（一次性提示）

Status: implemented

- 日期：2026-10-22
- 适用：`lib/version-notice.js`、`lib/state.js`、`lib/policy.js`、`lib/index.js`

与 [../bug-fix/2026-10-19-sync-auto-check-silently-writes.md](../bug-fix/2026-10-19-sync-auto-check-silently-writes.md)
是同一族的两个方向：那篇讲「自动同步不许偷偷写盘」，本篇讲「版本变了不许一声不响」。
与 [../bug-fix/2026-10-22-format-gate-missing-section-was-masked-comment.md](../bug-fix/2026-10-22-format-gate-missing-section-was-masked-comment.md)
的关系：那篇修的是「说错了」，本篇补的是「该说没说」。

## Problem

Owner 2026-10-22 原话：「版本更新时 agent 对话根本不会触发提示，还不如笔记规范如果启用，
加一个版本号更新变更，然后引导去更新比较好。」

实测现状：插件升到新版本后，**对话里没有任何信号**。已有的两条相关机制都盖不到这件事：

```text
① 项目副本落后提示（project-skill.js 的 buildDriftHint）
   → 只在 `.agents/skills/agent-notes/` 与插件内置副本**内容不一致**时才说话。
     而插件升级时插件内置副本变、项目副本没变 —— 确实会触发；
     但「插件自己换了版本」这件事（新判据、新门禁、行为变化）它一个字都不提。
② 自更新（self-update.js）只管插件自己那份技能目录的远端同步，
   → 不涉及「版本号变了」这个事实，也不产生任何面向对话的文本。
```

后果：用户装了新版，却以为行为没变；项目副本可能已经落后一版而没人知道；
新版本引入的门禁在项目里第一次红灯时，人来不理解为什么 —— 只能当成「门禁又抽风」。

## Decision

在**规范段落挂载时**比一次版本号，变了就往段落尾部追加一段**一次性**提示：

```text
读 package.json#version（不写死常量）→ 与状态文件里记录的 pluginVersion 比
  ① 没有记录（首次运行）        ⇒ 不提示，只记录
  ② 记录与当前相同              ⇒ 不提示，也不写盘
  ③ 不同                        ⇒ 追加提示，然后记录当前版本
  ④ 任一版本号形态不认识        ⇒ 不提示（宁可不说话，也不编一个版本号）
提示内容：从哪个版本到哪个版本、更新还是回退、变更看 CHANGELOG、
          项目副本要更新就 `/agent-notes sync-skill`、「这段提示每个版本只出现一次」。
```

记录存在**插件状态文件**里（`pluginVersion` 字段），不写进用户仓库 ——
插件不该为了提示一句话就在别人的仓库里制造未提交改动。

## Alternatives considered

**① 联网查 npm/GitHub 上的最新版本，用「有新版本可用」触发提示。**
最强的理由：这才是真正的「更新提醒」——本地记录法只能告诉你「变了」，
不能告诉你「该不该变」。
否掉的原因：三条都硬。其一，离线/墙内环境下这条提示会静默消失，
而「提示没出现」与「本来就是最新」在日志里长得一模一样 —— 又是一种假绿。
其二，每次挂载都发网络请求会把会话冷启动变成不可预测的等待。
其三，本仓库已有自更新链路负责「远端有没有更新」，
提示层再做一遍等于两处判据、两处漂移。

**② 干脆不做提示，把版本写进规范正文的固定行。**
最强的理由：零状态、零写入、永远不会漏。
否掉的原因：固定行会变成噪音 —— 每个会话都出现，人会当它不存在；
而「一次性提示」承载的正是「这次和上次不一样」这个信息量。
另外固定行写死版本号，一定会与 `package.json` 漂移（本仓库栽过写死版本的跟头）。

**③ 首次运行也提示一次「欢迎，这是 0.9.0」。**
否掉的原因：那不是提示，是横幅。首次运行没发生任何变化，
说成「更新」就是伪造事实（本仓库的判据：没记录 ≠ 更新过）。

## Consequences

收益：

- 版本变化从「无声」变成「一次性、可核对、带下一步」的信号。
- 首次运行/版本未变/版本号脏三种情况都不打扰 —— 用例逐条钉死。
- 状态只在值真正变化时落盘，不会让状态文件 mtime 失去意义。

代价：

- 提示只在**规范段落挂载**时产生（会话创建或开关切换），
  插件在同一会话内被热更新时不会立刻出现。接受：那种情形本来就少见，
  且下次挂载一定会补上。
- 状态文件多一个字段与一次迁移成本；`pluginVersion` 与状态 schema 的
  `version` 只差一个词，容易误读 —— 已在代码注释里点名区分。
- 只看数字三段比大小，预发布后缀不参与排序：`0.9.0-rc.1 → 0.9.0` 会被
  说成「回退」。这是刻意的，提示只回答「变了没有」。

## 补充（同日）：Owner 澄清要的是**标签**，不是正文里的一段话

Owner 原话：「我说的版本更新，是指这个注入的**笔记规范**这个标签，加一个 xxx 更新的提示，
这样子提示。」⇒ 光在正文里加一段提示不够，要挂在**看得见的那一行**上。

实现（`buildVersionLabel`，改动落在 `lib/policy.js` 的标题行拼接）：

```text
# 决策笔记（Agent Notes）· v0.9.0            ← 版本没变：只报坐标
# 决策笔记（Agent Notes）· v0.9.0 · 已更新   ← 刚变过：多一个标记
```

三条判据（都有用例）：

- 标签**始终**带版本号 —— 于是「我现在跑的是哪个版本」不用去翻 `package.json`。
- 「已更新」只在 `lastSeen !== current` 那一次出现；下一次挂载 `lastSeen` 已被记录成
  `current`，标记自动消失。它标记的是**这一次**的变化，不是永久徽章。
- 正文顺序固定为「版本变化 → 项目副本落后」：前者是「你该知道发生了什么」，
  后者是「你可能要做一件事」，先说事实再说动作。

为什么不做成 `systemPrompt.section` 的 `name`：宿主 `PromptSection` 声明的字段只有
`name` / `order` / `text` / `interpolate` / `complete` 五个（`@deepseek-ai/dsh-system-prompt`
的类型声明，2026-10-22 实测读的是本机 DSH 安装里的那一份），**没有独立的显示标题**；
`name` 是唯一标识（重复注册会抛），把它改成随版本变化的字符串会让「同一会话里
重装 section」的键也跟着漂。所以标签走正文第一行。

（这里刻意不写宿主文件的绝对路径与行号：那是别人机器上的安装位置，
写进笔记既校验不了、也会在 CI 上被行内引用门禁判红 —— 这个门禁抓的正是
「引用了不存在的东西」，包括我自己刚犯的这一次。）
