## Problem

三件事，都因为同一个根：**参考式链接**（`[文字][ref]` + `[ref]: 目标`）
的路径不在 `()` 里，所以用 `](路径)` 正则的代码全都看不见它。

实测本仓库现状：**行内式 137 条、参考式 0 条**。
所以这是**防御性完备**，不是修现存缺陷 —— 写清楚，免得日后误以为
「以前会报错、现在修好了」。

### 上游为什么支持（读了源码才明白，不是「顺手支持一下」）

`up-translation-links.ts:62` 的类型里显式含 `definition`，
`:236-246` 追踪 `linkReference` 并**只处理被引用过的** definition。

而它做的是**自动改写**（`rewriteTranslationLinkLocales`）——
只改行内式、漏了定义行 → **一篇文档改了一半**，比不改更糟。

★ **这才是「自动改写型工具必须支持参考式」的真正理由**，与「省 token」无关。
 Owner 猜的省 token 确实是真的收益，但上游自己 0 处使用参考式
（查过 `AGENTS.md` / `README.md` / `.agents/notes/AGENTS.md`，全是 0），
所以那不是上游支持它的原因。

## Decision

抽出共用件 `tools/markdown-links.mjs`，三处都接它。

**★ 为什么不各写一份正则**：三处（`md-links` / `archive-note` / 双语互链改写）
都要扫链接。各写一份的话口径迟早分叉 → 「一个放行一个拦下」。
本仓库已经吃过这个亏（`archive-note` 与 `md-links` 的围栏口径分叉过一次）。

### 三处各自的处理

| 位置 | 处理 | 为什么这样 |
|---|---|---|
| `md-links` | 检查行内式 + 参考式；**新增**「未定义引用」检查 | 未定义引用渲染出来是字面的 `[文字][ref]`，原实现完全看不见 |
| `archive-note` | 改写行内式 + **仅被引用过的**定义 | 孤立定义不是链接，可能是历史残留或给别人复制的示例，改它就是擅自修改未使用的内容 |
| `bilingual-links`（新） | 双语互链自动改写，语言切换器那行跳过 | 与上游 `skipTargets` 同口径 |

### 第三件：双语互链自动改写

对标上游 `rewriteTranslationLinkLocales`。

**★ 必须诚实说明它的适用面**：本仓库只有一对文档，且互链**当前是对的**：

```
README.md:3     `English` 链接 + `**中文**`
README.en.md:3  `**English**` + `中文` 链接
```

而上游 `translation-pairing.ts:305-307` 的 `languageSwitcherTargets`
把这两行**列为 skipTargets** —— 它的自动改写**不管语言切换器**。

★ 所以严格说：**上游那套机制对我们当前没有可改的东西。**
它针对的是多语言仓库（`README.md` / `.zh.md` / `.ja.md` …）正文中的互链，
本仓库还没有那种场景。本篇做的是**同一机制的最小可用形态**。

## Alternatives considered

- **只加一条「禁止使用参考式」的门禁** —— 便宜，且把「不支持」变成明确的。**否掉因为 Owner 指出的是更根本的一点：参考式有真实收益**（同链接引用多次时路径只写一次，正文更干净）。**为一篇我们自己维护、内容里 0 使用的写法去禁止它，是把「我不支持」当成了「不该用」。**
- **等有第二对双语文档再做** —— 更保守。**否掉因为 `archive-note` 那一半是现在就需要**：混用两种写法的一篇笔记，归档时只改行内式、漏了定义行 → 笔记内部自相矛盾，**比完全不改更坏**。那是**制造缺陷**，不是漏报。
- **引 mdast 来解析**（上游的做法）—— 能彻底避开手写正则。**否掉因为本仓库判据就是「哪些行是链接」，正则够用**，而引依赖有真实成本（Owner 已批准过一次 `spdx-expression-parse`，但那是解一个明确的解析需求，不是省事）。
- **把三处合成一个更大的工具** —— 那样连「口径一致」都不用维护。**否掉因为职责不同**：`md-links` 要收**全部**路径（孤立定义指向的文件若不存在就该报），`archive-note` 只要改**被引用过的**。合成会逼出一个两边都不对的折中。

## Consequences

- **收益**：参考式链接在两处都能被正确处理 —— 检查得到、改写得到。
- **收益**：新增「未定义参考式引用」检查 —— 一类原本完全不可见的坏引用。
- **收益**：双语互链有了自动改写，将来加第二对文档时不必临时补。
- **代价与已知上限**：**当前零使用**（参考式 0 条、互链 0 处要改）。所以这三件事都是**未被真实场景验证过的** —— 只被故障注入验证过。
- **代价与已知上限**：`blankOutFences` 用**等长空白**挖掉围栏（不是空串）。这是必须的：换成空串会丢掉多字节字符的字节，偏移随之全错。**但代价是「围栏内变成空格行而非空行」** —— 若将来某个消费方用「遇空行终止」的逻辑（如 `bilingual-docs` 的表格提取），它看到的是空格行不是空行。目前 `bilingual-docs` 用的是自己的 `withoutFences`（替换成 `\n`），不受影响；但**两条路径将来若合并，这里会咬人**。
- **代价与已知上限**：共用件的正则不支持**快捷式引用**（`[ref]` 无第二个方括号）。那种引用只在**全文没有任何定义行**时才有意义，而那正是坏引用（渲染成字面量），由 `undefinedReferences` 报出。上游用 mdast 的 `linkReference` 节点天然覆盖，本仓库不引依赖所以不实现。
- **重访信号**：
  - **真的出现第二对双语文档** → `PAIRS` 要扩，而互链改写的判据要重新验证（多对之间互指时，「正确语言」的定义会变复杂）。
  - **有人引 mdast** → `markdown-links.mjs` 应整体改用它，别再修手写正则。
  - **`bilingual-docs` 的 `withoutFences` 要与 `blankOutFences` 合并** → 注意上面那条「空格行 vs 空行」的坑。

### ★ 三条方法教训（本轮各栽一次）

**① 注释承诺 ≠ 实现做到**

`collectRelativeLinks` 的 JSDoc 写着「★ 只扫围栏代码块之外」，
**而实现里根本没有围栏过滤**。实测：围栏内的示例链接被收进去了。

★ 之所以漏：注释比实现先写，验的时候只跑了注释里的例子，**没跑反例**。

**② ★ 只用 ASCII fixture 验含中文的实现必然漏**

`blankOutFences` 把围栏内的行换成 `''` —— ASCII 下长度不变（偏移正确），
但中文文档下**每个汉字 3 字节，换成 0 字节就丢了**：

```
原文 71 字节 → 处理后 42 字节
```

于是所有 `start` / `end` 都指向错误位置，替换落在别处 →
**围栏里的示例反而被改了**。

★ 这与「测试工具自己坏了」那两次同类：**症状出现在被测对象上，
  原因在实现里，而测试数据恰好绕开了它**。
**判据**：实现涉及偏移或字节位置时，fixture 必须含多字节字符。

**③ 断言本身可能写错**

故障注入里我断言「中文 README 的所有链接都不指向 README 自身」——
失败了。查证后发现**断言错了**：第 3 行确实指向 `README.en.md`，
那正是**语言切换器**，是正确行为。

★ 断言失败时先问「是实现错还是断言错」。我这次默认了实现错。
