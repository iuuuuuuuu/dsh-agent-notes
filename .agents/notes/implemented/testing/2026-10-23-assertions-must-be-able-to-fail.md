# Agent Note: 用例必须「弄坏就会红」，否则它测的是恒真

Status: implemented

- 日期：2026-10-23
- 适用：`tools/*.test.mjs`；尤其新门禁的第一批用例

## Problem

同一个坑在一天里踩了两次，两次都不是判据写错，而是**用例根本没在测**：

第一次，`tools/ci-alignment.test.mjs` 里那条「字符串里的键不算键」写的构造是
`run: echo "continue-on-error: 文本"`。键前面紧贴引号，而判据的键起边界要求前面是
空行/空白/`{`/`,`/`-` —— 这条输入**压根不会被判据看见**。于是把判据里的字符串豁免
整段短路掉，这条用例照样绿。它有 `assert`、有名字、跑得飞快，判别力是零。

第二次，是给 `lib/notes-layout.js` 打变异时我自己的变异写错了：把 `errors.push(…)`
改成 `void 0; errors.push(…)`。`void 0;` 是空语句，`errors.push` 照旧执行 ——
变异是惰性的，于是「变异后仍然绿」被误读成「用例没有判别力」。真实情况是变异没生效。

两个方向的错都指向同一件事：**绿本身不提供信息**。要么用例能红，要么变异能生效，
否则「跑过了」只是把恒真算式算了一遍。

## Decision

新增门禁或新增判据时，用例的验收不是「跑起来绿」，而是**改坏判据就有一条用例红**，
并且这条红要落在「本该红」的那条上。具体做法固定为三步：

1. 先写用例；
2. 把判据打坏（条件短路、返回值改常量、豁免删掉），跑一遍，确认目标用例变红；
3. 按字节还原，核 SHA-256 与变异前一致，再跑绿。

配套两条判据：

- **变异的落点必须是判据的判定本身**，不是它的前置（`errors.push` 前面加空语句、
  在注释里改字、改一个没被读的变量名都算没变异）。变异后仍绿时，第一件事是确认
  变异真的改变了行为，而不是先怀疑用例。
- **用例的构造必须落在判据的识别面上**。像「键紧贴引号」那种输入，判据从一开始
  就不看它，用例再怎么写都测不到豁免逻辑。

## Alternatives considered

**① 只要求「新门禁必须有一条能红的用例」，不要求每次改动都重跑变异。**
最强的理由：变异要手工改生产代码再还原，麻烦且容易忘；把「至少红过一次」当门槛
已经是巨大改进（历史上空的 `verify-agent-note-tree.ts` 在空树上 exit 0 也算绿的年代，
连这一条都没有）。
否掉的原因：判据会演化。今天能让用例红的输入，明天判据收紧后可能落在识别面之外，
用例静默失效而没人知道 —— 第二次踩坑（惰性变异）正是「红过一次」的记录还在、
当次却没验的表现。要求「改动判据就重跑一次」成本很低（一次 `node --test` 加一次还原），
收益是这条用例此刻真的有判别力。

**② 引入变异测试工具（Stryker 之类）自动跑。**
最强的理由：把「判别力」变成可自动化、可度量的指标，不用靠人记得做。
否掉的原因：本插件的硬约束是零 `@deepseek-ai/*` 依赖、门禁要能在别人的项目里跑，
为一个手工动作引入一整套工具链与依赖不划算；而且自动化变异对「变异点写得对不对」
同样无能为力 —— 它只会报「存活变异体」，而存活的原因可能是变异本身是惰性的。
先把「人做的变异必须落在判定上」这条写清楚，比换工具更便宜。

**③ 不写用例，直接靠 `tools/fault-injection.mjs` 的端到端故障注入。**
最强的理由：那套注入跑的是真实脚本与真实退出码，比单元级断言更接近真相。
否掉的原因：端到端注入证明「这道门禁会红」，不证明「这条用例能红」。判据被删掉一半
时，端到端仍红（另一半还在红），单元用例若恒真则永远不会提示少了一半。

## Consequences

收益：

- 用例的通过重新变成信息：它意味着「这条输入会被这条判据处理」。
- 惰性变异（改了但没改到判定）被明确划成「没变异」，不再冒充「用例没判别力」。

代价与残留：

- 每加一条判据都多一次手工变异与还原，且必须核哈希确认还原干净；忘了核哈希就会
  把变异留在工作区（本仓库历史上因此红过一次全量 check）。
- 判别力仍是抽样：一次变异只证明「至少有一条用例真的在看这个判据」，
  不证明每条用例都有判别力。要更强只能逐条变异，成本上升一个量级。
- 端到端注入与单元判别力是两件事，两道都要有，不能互相替代。

## Verification

- `tools/ci-alignment.test.mjs`：把 `insideQuotedScalar()` 的豁免短路掉，
  第一版构造**仍然 40/40 绿**；把构造改成 `echo "log continue-on-error: 文本"`
  （键前先是空白）之后，同一变异使该用例变红。这条前后对比就是本文 Problem 的第一段。
- 判别力扫描（2026-10-23 一次性探针，已删）：对六道门禁各打一个落在判定上的变异，
  要求对应用例文件出现失败、随后按字节还原并核 SHA-256：

  | 门禁 | 变异点 | 结果 |
  | --- | --- | --- |
  | `tools/eol.mjs` | 结尾多空行判据返回通过 | fail=5 |
  | `tools/eol.mjs` | Git 语料被清空（列表置空） | fail=5 |
  | `tools/corpus-floor.mjs` | 低于下限的判据短路 | fail=1 |
  | `tools/syntax-check.mjs` | 空语料守卫短路 | fail=3 |
  | `tools/release-check.mjs` | lock 版本比较取反 | fail=6 |
  | `lib/notes-layout.js` | 未知目录判据短路 | fail=5 |
  | `lib/notes.js` | `explainMaskedCommentSections` 直接返回空串 | fail=2 |

  七次全部 `还原=ok`（SHA-256 与变异前一致），随后 `git status --short` 为空。
- 扩大到十八处判据后（2026-10-23 另三轮一次性探针，已删），**十七红一存活**：
  存活的是 `tools/release-check.mjs` 里「`package-lock.json` 缺少顶层 `version` 字段」这条，
  把它换成 `void 0` 后 `tools/release-check.test.mjs` 仍 12/12 全绿 —— 那条分支此前是
  纯装饰，用例只覆盖了「版本不相等」与「读不出来」，没覆盖「字段缺失」。
  补上用例（断言话术必须是「缺少顶层 version 字段」而不是「版本是 undefined」，因为两者
  的修法不同：前者要重新生成 lock）之后，同一变异 `fail=1`。
  这一条是本节的实践例证：**普查的价值就在存活的那一个**，红的那十七个只是背景。
- 反向例子（惰性变异）留档：`errors.push(…)` → `void 0; errors.push(…)` 使
  `tools/notes-layout.test.mjs` 得 `fail=0`。它不是「用例没判别力」，是变异没生效 ——
  换成把 `if (!NOTE_ROOT_LIFECYCLES.includes(name))` 短路后立刻 `fail=5`。
