# Agent Note: 子进程崩溃不算「门禁变红」

Status: implemented

## Problem

`tools/fault-injection.mjs` 的职责是证明**每道门禁在该拦的故障上真的会红**。它原来把
子进程的 `status ?? -1` 当成退出码：`spawnSync` 在子进程被信号杀掉或 spawn 失败时
`status` 是 `null`，折算成 `-1` 之后当然「非零」，于是进入「该红」分支；那个分支只要
诊断文案匹配就记 `✔`。

这条路径会把**崩溃记成证据**：门禁在半路炸掉（例如 import 阶段抛栈前已经打印过期望的
错误前缀），输出里恰好含有该匹配的文串，故障注入就宣布「这道门禁能拦住该故障」。
而实际上它什么都没拦住 —— 它自己先死了。

独立复审把这条列为「P2：崩溃与按契约变红不可区分」，触发点是我自己在
`tools/fault-injection.mjs` 的 `run()` / `runCli()` 里用 `status ?? -1` 抹掉了这个区别。

## Decision

故障注入里，「该红」有两道门槛，缺一不可：

1. **进程必须正常结束** —— `status !== null`。`status === null`（signal 或 spawn 失败）
   直接记失败，文案是「子进程未正常结束（signal=…），不能算作门禁变红」；
2. **诊断必须指向该故障** —— 输出要匹配该用例的正则（这条原来就有，保留）。

`run()`/`runCli()` 同时回传 `status` 与 `signal`，让失败信息能说清是「崩溃」还是
「按契约变红但文案不对」；「该绿」分支的失败信息也带上 `signal`。

顺带把「输出末尾三行」抽成 `lastLines()`：这段拼接原先在四个地方各写一遍模板串，
其中一次跨行编辑把真实的换行写进了字符串字面量，`tools/fault-injection.mjs` 自己语法错
—— 报错位置在门禁脚本身上，看起来像被测门禁坏了，实际是诊断代码写坏。集中一处之后
这种自伤只剩一个地方可能发生。

## Alternatives considered

**给「该红」分支加重试，崩溃就再跑一次。** 最强的理由是：本机确实出现过子 node 崩溃
（`3221226505` = `0xC0000409`，见
[2026-10-21-one-green-run-did-not-prove-stability.md](2026-10-21-one-green-run-did-not-prove-stability.md)），
重试能让偶发崩溃不阻塞。否掉的原因：重试会把偶发崩溃从视野里抹掉，而故障注入的**唯一**
产出就是「这道门禁靠得住」这个断言 —— 一次崩溃意味着这一次证据不成立，把它重试成绿，
等于用「第二次没崩」替换「这一次证明了什么」。

**只把 `signal` 写进消息，判定逻辑不动。** 改动最小、零风险，且文案匹配本身已经拦掉了
大多数崩溃（崩溃的栈很少恰好匹配期望前缀）。否掉的原因：这依赖「崩溃的输出恰好不含匹配
串」这个巧合，而 `expectRed` 的匹配是 `RegExp.test`，只要输出里任何位置出现该子串就算过；
把正确性建立在输出内容巧合上，正是这道门禁要防的那类假绿。

**要求退出码等于某个具体非零值。** 更严格，但门禁的失败码本身没有统一约定
（本仓库既有 `1` 也有 `2`，例如 `tools/doc-budget.mjs` 用 `2` 表示用法错误），
按具体值断言会把合法语义写死。否掉。

## Consequences

- 收益：这场「崩溃 vs 变红」的混淆被消除 —— 一次崩溃现在必然是故障注入的失败，不再是
  一条 `✔`。失败信息带 `signal` / 码值，能直接看出是炸了还是判错了。
- 代价：偶发崩溃现在会**真的**让 `gate:fault-injection` 变红，包括本机那类
  `0xC0000409`。这是刻意接受的：宁可红一次去看清崩溃，也不要一条来路不明的绿。
- 已知边界：`status === null` 只覆盖「没正常结束」，不覆盖「正常结束但退出码离谱」
  （例如 `3`）；后者仍按「非零 + 文案匹配」算红。要更严就得给每道门禁约定失败码，
  那是另一个决定，没做。
- 顺带：`lastLines()` 把四处重复的「末尾三行」收敛成一处，减少同类自伤面。
