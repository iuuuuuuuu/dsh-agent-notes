# Agent Note: 双语门禁补表格 —— 前三次都是假绿

Status: implemented

> 接续 [2026-10-19-i-was-wrong-about-not-needing-mdast.md](../bug-fix/2026-10-19-i-was-wrong-about-not-needing-mdast.md)
> —— 那篇纠正了「不需要 mdast」的说法，并在末尾留下「tables / lists 两项未评估」。
> **本篇补上 tables，并给出 lists 不做的实测依据。**
> 机制沿用同一篇确立的分工：`npm test` 管逻辑，`.probe/` 管真渲染。

Independent: 本篇改的是同一份门禁的另一项判据，与那篇不冲突但也不重复 ——
那篇确立「比语言标记不需要 mdast」，本篇是「比表格也不需要 mdast」。

## Problem

`tools/bilingual-docs.mjs` 只比三种结构：标题层级、代码块数量、**代码块语言标记**。
上游 `translation-pairing.ts` 比五项（另加 tables / lists）。

Owner 认为值得补。**先量，再决定补哪一项。**

### 实测：表格零误报，列表有一处真漂移

分节实测 25 节里 24 节结构一致。唯一不一致的第 19 节：

| | 表达形式 |
|---|---|
| 中文（行 345） | 两个 `- ` 列表项 |
| 英文（行 400） | 两段散文，零列表项 |

**内容不缺，表达形式不同** —— 属排版选择，不是漏同步。

表格则完全不同：4 张真表（6×2 / 6×2 / 4×3 / 11×2），
中英**每行单元格数逐行相同**。因为表格是**跨语言刚体** —— 同一份对照表，
列数不一致读者就对不上，而那与翻译无关。

**所以 tables 进、lists 不进。**

### 上游的 `excluded` 帮不上

读 `up-translation-pairing.ts:202` 确认：`excluded` 是**文档路径级**排除
（`entry.endsWith('/') ? file.startsWith(entry) : file === entry`），
**没有段落级降噪机制**。所以「照抄上游就能降噪」这条路不通。

而 `GENERATED_REGION`（`<!-- BEGIN GENERATED x -->`）是给**机器生成内容**用的
（配 `spliceGeneratedRegion` 做替换），不是降噪清单。

## Decision

**只加表格比对，不加列表比对**，并在代码注释里写明列表为什么不做。

### 表格提取的三次失败 —— 两次是假绿

★ 这是本篇最该记住的部分：**前三次提取逻辑都留下碎片，而中英碎片恰好一致，
所以门禁每次都绿。**

**① 没有分隔行判据** → 正文里带 `|` 的普通行被切成 6 张单行碎片。

**② 分隔行判据放在「是不是内容」之后** → 分隔行 `|---|---|` 的字符**全在
`[\s|:-]` 里**，所以那个判据对它必然为假 → `isDelimiter` 永远不成立 → 分隔行被
当普通非表格行冲掉。

★ 而当时中英两边**同样地错** ⇒ 门禁照样绿 ⇒ 我看到「张数没变」一度以为修复生效。

**③ 顺序对了但状态机错了** → 分隔行 push 后把 `pending` 置空，
**后续数据行就成了新片段**，真表格被拆成 `[表头,分隔]` + `[数据...]` 两半。
实测真表格应是 `[2,2,2,2,2,2]`，出来的是 `[2,2]` 和 `[2,2]`。

### 最终规则

1. **只有被分隔行确认的候选才算表**。孤立含竖行一律丢弃 ——
   那正是碎片来源：行 3 的语言切换链接（`README.en.md` 旁边一个 `|` 再加「中文」）、
   行 273 的列表项里的代码（含 `patch|minor|major`）。
2. **分隔行必须先判**，因为它的字符全在 `[\s|:-]` 里。
3. **表格体由空行终止**（GFM 规则），后续数据行并进当前那张表。

结果：11 张（含碎片）→ **4 张全真**，中英结构逐行相同。

## Alternatives considered

- **表格和列表一起加** —— Owner 最初的意思大概是「都补」。**否掉因为列表已实测有一处漂移**，加进去立刻红，且红了也没错（那是排版选择）。**半边比全边比更有价值**：加进能加的那一项。
- **先引入上游那种 `GENERATED_REGION` 标记机制，再比 tables/lists** —— 那是本篇最强的一条被否方案。**因为标记机制解决的是「机器生成内容不该人工校对」，与「中英排版惯例不同」是两回事** —— 后者不是「生成」造成的，标出来也不该被跳过。上游用它是为了 `spliceGeneratedRegion` 做替换，本仓库没有那个需求。
- **引入段落级 `excluded` 清单**（上游没有）—— 能解决列表问题。**否掉因为当前只有 1 处漂移，而引入清单意味着「作者要手工维护哪些段落不比」**。等漂移多到 3、5 处再说，那时才知道清单的形状对不对。
- **只加数量不比结构**（表几张、几行）—— 比 `[2,2,2,2,2,2]` 简单。**否掉因为它漏得更多**：删一列不改行数，结构比能抓到、用例 1 就验了这条。

## Consequences

- **收益**：双语门禁多一维真信号。**表格列数被改而忘了同步英文版，现在会被拦下。**
- **收益**：碎片不再进结构 —— 那是**假绿的源头**。此前碎片会稀释真漂移（真表格改了，碎片数恰好也变了就能蒙过去）。
- **代价与已知上限**：列表**仍不比**。将来若中英在同一节选了不同排版，只有列表那种漂移会漏。**这是有意识的取舍**，注释里写明了原因。
- **代价与已知上限**：`DELIMITER_ROW` 只认 `---`（至少 3 个）与 `:---` `---:` `:---:` 对齐标记。**不支持** GFM 允许的其它写法 —— 但那些极罕见。
- **代价与已知上限**：提取逻辑是手写状态机而非 mdast。**手写状态机的风险已实测三次**（本篇的三次失败）。上游用 mdast 是为了避开这类问题，而本篇选择手写 —— 因为判据就是「哪些行是表格」，正则够用，且不引依赖。
- **重访信号**：
  - **中英列表漂移超过 3 处** → 引入段落级排除清单，那时才知道清单的形状。
  - **有人开始用 mdast** → 表格提取应改用它，别再修手写状态机。
  - **README 之外出现多对双语文档** → `PAIRS` 要扩，而提取逻辑按位置对齐标题的假设要重新验证。

### ★ 第二条方法教训（同一类错误，栽了两次）

故障注入第一版报「表格门禁根本没生效」—— 四个该红的用例全返回 `[]`。
真因是**我的注入脚本自己坏了**：`read` 的键写成 `/` 分隔，而
`verifyBilingual` 传进来的是 `join(PACKAGE_ROOT, ...)` 产生的 `\` 分隔路径，
**键不匹配 → 落回 `readFileSync` 读真文件 → 注入被静默忽略**。

★ 与归档那次（围栏转义把三个反引号写成单个）**是同一类**：
**测试工具的缺陷症状离原因很远**，而且症状看起来像「被测对象坏了」。

**判据**：验之前先确认**注入真的生效了** —— 加一条「基线无报错」并同时打印
表数，两边对不上就说明注入没进去。
