> [process-tree-cleanup](../../rejected/architecture/2026-10-19-process-tree-cleanup-not-needed-on-windows.md)、
> [code-block-parity](../../rejected/architecture/2026-10-19-code-block-parity-two-approaches-failed.md)、

Independent: 本篇**不改任何门禁行为**，只记录两个已定位的空白与它们的现状判断。

## Problem

本仓库的 `tools/md-links.mjs` 用**手写正则**提取链接：

```js
const pattern = /!?\[[^\]]*\]\(\s*(?:<([^>]*)>|([^\s)]+))(?:\s+"[^"]*")?\s*\)/g;
```

它支持行内链接的尖括号与标题形态（说明作者在意 CommonMark 目标形态），
但**不支持两种**：

| 形态 | 正则表现 | 后果 |
|---|---|---|
| **引用式链接** `[文字][ref]` + `[ref]: path` | 完全不匹配 | **坏链接静默通过** |
| **嵌套括号**（链接目标里带圆括号，如 `path(1).md`） | `[^\s)]+` 遇 `)` 即停 | 目标被截断在第一个 `)` 前 → **误报「目标不存在」** |

而上游的 `markdown.ts` 用 mdast 解析（`mdast-util-from-markdown` +
`gfm`），这两种形态**天然覆盖**。

## Decision

**记录两个空白，不改门禁。** 因为**本仓库一个都没踩到**。

### 实测：门禁确实有这两个空白

用**真实门禁**验（探针文件写在仓库顶层，`collectDocuments` 第一段就扫
`readdirSync(PACKAGE_ROOT)` 的 `.md`）：

| 用例 | 结果 | 判定 |
|---|---|---|
| ① 行内链接指向坏路径（**已知支持**） | 红 | ✔ **测试有效的证据** |
| ② 引用式链接指向坏路径 | **绿** | 空白确认：静默放过 |
| ③ 嵌套括号链接（目标含圆括号） | 红（报「目标不存在」，路径被截断） | 误报确认 |
| ④ 坏链接藏在代码块里（**已知会剥代码块**） | 绿 | ✔ 不误报 |

① 与 ④ 两头都对 → **测试有效**，② ③ 的观察可采信。

### 但扫遍 62 个文档：两个形态一个都没有

扫描范围与 `md-links` **完全一致**（顶层 `.md` + 笔记树，跳过 `archived/`）：

```
引用式链接：1 处命中 → 查证是 self-review-found-three-silent-gaps.md:115
           「（`[文字][引用]` 加一行引用定义）。本仓库的笔记不用这种写法」
           —— 那是我笔记里的**示例代码**，不是真链接

嵌套括号：  0 处
```

**所以两个空白当前完全无害。**

## Alternatives considered

- **改 `extractLinks` 正则，额外支持引用式与嵌套括号** — 成本最低。**这是本篇最强的一条被否方案**，理由不是「做不了」而是**做了也验不到任何东西**：正则改复杂了，但我无法构造「它抓到了」的证据——因为本仓库没有那种写法。**而无法证明有效的门禁改动，等于往正则里堆没人验证的分支。**
- **照搬上游 `markdown.ts`（引 mdast）** — 一次性消掉两个空白，未来也不会再有。**否掉因为成本与收益不成比例**：本仓库 62 个文档、118 条链接，两个空白都从未被触发；而引入 mdast 是**永久的依赖**（运行时 + 本仓库的 devDeps）。**且这正是我上一轮否决 mdast 那条路的延续** —— Owner 说「值不值得它的成本」，这里的答案是：62 个文档、0 次触发，不值得。
- **什么都不做，只记录** — **这是本篇的决定**。

## Consequences

- **收益**：两个空白被**精确定位并实测确认**，不是猜测。将来真碰到时，改动点与验法都已写清（改正则 + 用这四个用例验，且**必须确认 ① ④ 仍符合预期**才算测试有效）。
- **代价与已知上限**：**若有人写出引用式链接，它会静默失效**（门禁绿，实际坏了）。那属于「靠人记得别用」，不是靠机制。
- **代价与已知上限**：嵌套括号会误报，但报的是「目标被截断后不存在」——**错误信息会让人困惑**（去查一个不存在的路径，而真问题是解析错了）。
- **重访信号**：
  - **笔记里第一次出现引用式链接** → 立刻改 `extractLinks`，或改用上游的 `markdownDestination`。触发条件明确、可验证。
  - **`md-links` 报出「目标不存在」但那个路径看起来被截断**（如含 `(`）→ 同一件事的另一个信号。
  - **若本仓库文档数超过 ~200** → 正则的维护成本开始显著，此时引 mdast 才划算。

## Verification

```sh
node .probe/tmp/test-md-links-v2.mjs   # 四个用例，验真实门禁
node .probe/tmp/scan-link-forms.mjs    # 扫 62 个文档的实际用法
```

实测（`test-md-links-v2`）：

```
基线（无探针文件）: 绿 ✔
① 行内链接 → 坏路径           红   ✔ 符合预期（测试有效的证据）
② 引用式链接 → 坏路径         绿   ← 空白确认：静默放过
③ 嵌套括号链接（目标含圆括号）   红   ← 误报：目标被截断，报「目标不存在」
④ 坏链接藏在代码块里          绿   ✔ 符合预期（不误报）
```

实测（`scan-link-forms`）：

```
扫描范围: 62 个文档（与 md-links 一致）
引用式链接: 1 处 → 查证是笔记里的示例代码，非真链接
嵌套括号:   0 处
```

**一个探针错误值得记**：第一版把探针写进 `.probe/tmp/`，那**不在 md-links 的
扫描范围**，三个用例全是「绿」——**连已知支持的行内链接都没抓到**。
若不检查 ① 而只看 ②③，会得出「两个空白都不存在」的错误结论。

判据：**若一个测试连「已知能工作的路径」都验不到，那是测试坏了，
不是被测对象坏了。**
