# Agent Note: 看板补丁的选择器对齐 —— 把「自己写下的失效面」变成门禁

Status: implemented

## Problem

看板窄屏补丁的做法是「不改上游 HTML，额外注入一段覆盖 CSS」。它的代价在
[2026-10-17-board-narrow-viewport-adaptation.md](../feature/2026-10-17-board-narrow-viewport-adaptation.md)
里已经自己写过：

> 多了一层「上游 HTML + 宿主覆盖 CSS」的耦合。覆盖样式依赖上游的类名
> （`.hud-topbar`、`.deck-tabs`、`.hud-grow` 等），**上游改类名时这些选择器会静默失效**
> —— 样式不报错，只是不再生效，退回竖排。这是这套方案最脆弱的地方。

这段话说得对，但**它只是一句话**。当时没有门禁，于是它一直是可以随便失效的：

1. 类名写错/上游改名后，样式表里那条规则**照旧合法**，浏览器只是匹配不到元素；
2. 任何用例都不会红 —— 除非有人正好在那个视口下肉眼比对；
3. 而本仓库的 `npm run sync` 会把 vendored 看板**整页换新**。也就是说，「上游改名」
   不是假想的风险，是这个仓库每个月都会发生的动作。

同一篇笔记里还留着另一条类似的残留：`md-table` 之类注进页面的类名也没有人核对过。
这一批「我最清楚会坏、但只是记了一笔」的东西，属于用户反复要求处理的那一类
（不得把测试全绿表述为绝对无优化空间）。

## Decision

新增一道纯文本可判定的门禁：**我们的选择器里出现的每一个类名，必须在 vendored 看板
页面里真的存在**。

- 判据实现在 `lib/board-selector-audit.js`（纯函数，不读盘、无依赖）；
- CLI 外壳是 `tools/board-selector-alignment.mjs`，接入 `npm run check` 的
  `board:selectors` 一步，并在 `.github/workflows/verify.yml` 里同样占一步
  （`ci:align` 会核对两边一致）。

**「必需集合」取两处证据**：CSS 文本里的选择器类名，以及 `querySelector('…')` /
`querySelectorAll('…')` 的字符串实参。只认这两处，是为了不把 JS 属性访问
（`.join`、`.length`）和 CSS 里的时长（`0.18s`）当成类名。

**「存在集合」取三处证据**：vendored 页面里静态的 `class="…"`，以及 vendored 脚本里
`className = '…'` / `classList.add('…')` 动态加上去的类名（`radar-dot`、`status-badge`
这类只在运行时出现）。

**「自建集合」单独算**：补丁自己创建并使用的类名不算缺，包括 `className` 赋值语句里
出现的字符串（`kpi-row-5` 是「已经带了就不重复加」的三元式加上的，正则在整条
`className …=` 语句里取字面量）、`classList.add`，以及注入片段里写死的 `class="…"`
（表格补丁的 `md-table`）。判据是 `必需 − 存在 − 自建`。

两道防收窄的守卫，因为「什么都没扫到」必须判红（同
[2026-10-22-vendored-gates-are-vacuous-on-empty-tree.md](./2026-10-22-vendored-gates-are-vacuous-on-empty-tree.md)，
空集合上的 `ok` 不算通过）：

- 某个模块抽不到任何选择器时，**必须显式声明 `noCssReason`** 才放过
  （`lib/board-markdown.js` 的样式全是内联，属于合法事实，不是遗漏）；
- 全部模块的选择器总数低于 `MIN_SELECTORS = 20`（当前 22）判红 —— 抽取口径或模块
  清单被悄悄收窄时，只靠「每条都对齐」是发现不了的。

## Alternatives considered

**只写测试、不做 CLI 门禁。** 最强的理由是：门禁的真实效力本来就来自测试（`npm test`
才是会红的那一步），多一个 CLI 文件和一步 CI 只是重复；`npm run board:selectors`
能抓到的东西，测试里那条「当前仓库全部对齐」的用例同样能抓到。否掉的原因：
两者的读者不同。测试是给改代码的人看的，`npm run check` 那一步是给**做上游同步的人**
看的 —— 同步完改的是 vendored 文件，报错得出现在「看板选择器对齐」这个标题下，
而不是淹在两百条测试输出里。此外这一步会进 `ci:align` 的对账，等于同时钉住
「这道门禁不许被从 CI 里删掉」，单独一份测试文件没有这层保护。

**起浏览器渲染、量真实布局（沿用之前那套 headless Chrome 探针）。** 最强的理由是：
它验的是**结果**而不是**文本**——真正想知道的是「窄屏下 KPI 卡还在同一行」，
而不是「类名还能对上」。类名对上了但规则被上游更高的特异性压掉，前者能发现，
后者不能。否掉的原因：那套探针要起浏览器、几十秒起跳，且它验的是**某一个固定视口**；
更关键的是它依赖本机 Chrome，在 CI 上要么装浏览器、要么这条门禁降级成跳过 ——
而「降级成跳过」正是本仓库明令禁止的假绿形态。文本判定 30 毫秒、每次提交都跑、
不依赖任何外部程序，覆盖的正是那个**静默**失效面。

**把选择器从「类名」改成「属性选择器或结构选择器」，绕开类名耦合。** 最强的理由是：
那就根本不需要这道门禁了 —— 不依赖类名就不会因为改名而失效，从根上消掉这个失效面。
否掉的原因：vendored 页面的结构同样会变（`div` 嵌套、兄弟顺序），改成结构选择器只是
把「会在改名时失效」换成「会在改结构时失效」，而且更难读。类名是上游**有意**暴露的
稳定面，跟它耦合是对的选择，缺的是核对而不是绕开。

**在 `sync-upstream` 之后自动跑一次并自动改选择器。** 最强的理由是：这样连人工介入都
省了。否掉的原因：改选择器是**设计决定**（改名意味着上游结构变了，覆盖 CSS 里那条
规则可能该整条重写），自动化只能改字面量、会把「这里需要人看一眼」变成「悄悄改通」。
门禁的职责是判断，不是修。

## Consequences

- 收益：那条自己写下的「最脆弱的地方」从**一句话**变成**每次提交都跑一次的判据**。
  上游改名不再静默：`npm run check` 会点名「选择器 `.deck-tabs`（CSS 选择器）在
  vendored 看板页面里不存在 —— 上游改名了，这条样式已静默失效」，并给出处
  （CSS 还是哪个 `querySelector`）。
- 收益：报错**带出处**。同一个类名既被 CSS 选中又被 `querySelector` 取用时，两处都记，
  修的时候不用自己再 grep 一遍。
- 代价：22 个类名从此是一份**必须一起改的清单**。上游真改名时，门禁会红，而红的理由
  是「我们的补丁过期了」—— 这次改动**必须**连同类名与覆盖规则一起更新，不能只改门禁。
- 代价：`PATCH_MODULES` 是一份人工维护的表，新增补丁模块要记得加。它防不住「新模块压根
  没登记」，只防「登记过的模块选择器失效」。这一点与本仓库其他清单型门禁同一局限，
  已在此写明而不是留给人猜。
- 已知上限（不掩饰）：这道门禁判的是**名字还在不在**，判不了**规则是否仍然生效**。
  上游若把 `.deck-tabs` 保留但改了嵌套（例如把 `nav` 换成 `div`），类名仍存在，
  覆盖规则可能因为 `nav.deck-tabs` 这类复合选择器而失效 —— 这种情况它抓不到，
  只能靠窄屏探针或肉眼。写下这条是为了不让下一个人误以为它证明了「样式一定生效」。
- 已知上限：`setAttribute('class', …)`、`dataset`、CSS-in-JS 之类**其他创建类名的写法**
  不在「自建集合」的识别范围里，出现时会被误报成缺失。误报比漏报好，但会多一次人工判断。

## Verification

`node --test tools/board-selector-alignment.test.mjs` → **15 tests / 15 pass / 0 fail**。
`node tools/board-selector-alignment.mjs` → `看板选择器对齐通过：2 个补丁模块、22 个
选择器类名都在 vendored 页面里存在。` exit 0。
`node tools/ci-alignment.mjs` → `本地 check 链的 17 道内容型门禁都在 verify.yml 里`。

真故障注入五次（每次 `cp` 备份 → 变异 → 只跑本文件 → 还原 → `cmp` 确认逐字节相同）：

| 变异 | 结果 |
|---|---|
| 去掉 vendored 页面的静态 `class="…"` 扫描 | 9 pass / **5 fail** |
| 关掉 `querySelector` 那一半 | 12 pass / **2 fail** |
| 空集合一律放行（无视 `noCssReason`） | 14 pass / **1 fail** |
| `MIN_SELECTORS` 改成 `0` | 15 pass / **1 fail** |
| 去掉注入片段里 `class="…"` 的自建识别 | 14 pass / **1 fail** |

其中**两次一开始没被抓住**，这是这段工作里最该记下来的部分（同一类教训的完整版在
[2026-10-23-assertions-must-be-able-to-fail.md](./2026-10-23-assertions-must-be-able-to-fail.md)）：

1. 「关掉 `querySelector` 那一半」最初 12/12 全绿 —— 因为当时没有任何用例依赖那一半。
   补了两条（一条单测「指向不存在的类名会被点名」、一条夹具里给副本模块追加
   `querySelector('.deck-tabs')` 再让上游改名）后才变红。顺带纠正了一个错误前提：
   我原本想用 `kpi-num` 当例子，实测发现那段卡片是**本模块自己注入**的
   （`'<div class="kpi-num">'`），它对上游改名本来就不敏感 —— 豁免它是对的。
2. 「`MIN_SELECTORS` 改成 `0`」最初也全绿 —— 因为那条断言把导出的常量当真理
   （`assert.ok(result.total >= MIN_SELECTORS)`），常量改成 0 它自己就自证成立。
   改成用夹具构造「只对账到 1 个类名」的真实收窄，并额外断言常量本身 `>= 20` 之后才红。

这两处都是「用例看起来在验，其实验的是自己」，是在故障注入里暴露出来的，
不是靠读代码看出来的。
