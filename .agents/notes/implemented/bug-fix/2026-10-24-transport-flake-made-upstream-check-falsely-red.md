## Problem

2026-10-24 复跑 `npm run check`，`sync-upstream` 的用例又红了。这次错误不是
`fetch failed`，而是：

```
合并失败: terminated
```

`1 !== 0` —— 断言在说「契约被破坏」（exit 1 = 上游真有差异），实际是请求没做完。

### 三处叠加，结果是最坏的那个

**第一处：分类判据漏了一整族错误。** `isEnvironmentUnavailable()` 只认
`fetch failed`、`ENOTFOUND`、`ETIMEDOUT` 等词表。而 CDN 读到一半关连接时，
undici 抛的是：

```
TypeError: terminated
  cause: SocketError: other side closed   code=UND_ERR_SOCKET
```

名字、message、code 三样都不在词表里 → 判定失败 → 退回 exit 1。
**这正是那篇分类笔记自己写下的重访信号应验**（它说「换了 HTTP 客户端措辞会变」，
实际客户端没换，是**同一客户端的另一种失败形态**）。

**第二处：没有重试。** 一次传输层抖动 = 整条门禁失败。

**第三处：抖动是真实存在的。** 配对对照实测取到（方法见本篇 Verification）：
同一窗口内 40 轮里，不重试的一臂失败 1 轮，重试的一臂 40/40 成功，
且重试**实际救回 5 个已经失败的请求**（两轮 70 场合计）。

## Decision

### 一、`isEnvironmentUnavailable` 认 undici 传输层错误码族

除原有词表外，新增三类判为「环境不可用」（exit 2）：

| 类别 | 例子 | 为什么是环境问题 |
|---|---|---|
| 连接被掐断 | `terminated`、`socket hang up`、`other side closed`、`ECONNRESET`、`EPIPE` | 请求没做完，不是上游内容变了 |
| 传输层错误码 | `code === 'ECONNRESET'` / `'EPIPE'` | 同上 |
| undici 错误码族 | `^UND_ERR_`（SOCKET / CONNECT_TIMEOUT / HEADERS_TIMEOUT / BODY_TIMEOUT / CLOSED …） | 前缀即语义：全是「本次请求没能完成」 |

`must`：**用前缀而不是穷举措辞。** 一条条抄具体 message 就是今天这个缺陷的成因
（换一种断法就漏）。`UND_ERR_` 这一族没有一个是「上游有差异」，
不可能把真差异误判成环境问题。HTTP 状态码类失败走的是自造错误
（`拉取失败 404: <url>`），不带 `UND_ERR_`，分类不会被带偏 —— 有对照用例钉住。

### 二、传输层失败做有限重试（3 次，250ms / 500ms 退避）

新增 `retryTransport()`，只包住**传输层**失败；404 等 HTTP 状态码失败不重试。

`must`：**重试范围必须比「环境不可用」判据更窄。**
`isEnvironmentUnavailable` 把 401/403/429 也算环境问题（该退 2，人不该去查差异），
但立刻重试这三类只会加深限流。所以两张判据分开：一个回答「这次算不算检查成」，
一个回答「要不要再试一次」。

### 三、假红与假绿同罪

门禁红着但原因是抖动、且重试一下就能过 —— 这是**假红**。
它的危害不是「多红几次」，而是**人会学会忽略它**：一个随机红的门禁，
三次里红一次，很快就被当成噪声，那时它拦真问题的能力也一起没了。
所以修假绿的红线同样适用于修假红，而**不是**靠「反正重跑就好」。

## Alternatives considered

- **维持原判：不加重试**（即维持那篇 rejected 笔记的结论）— **这是本篇最强的一条被否方案**，它不是懒，是当年**实测**出来的：7/7 立刻重试全部 `ECONNRESET` 失败，失败还是成簇的（前 6 次连败、随后 14 次全通），据此判断「那不是抖动，是连接被重置，重试解决不了」。**它错在把一种失败形态的结论外推成了全部**：簇状 `ECONNRESET` 期间重试确实无效（这一半今天仍然成立，见代价），但今天的失败是**零散的** `UND_ERR_SOCKET`，重试能救回来 —— 70 轮配对实测里救回 5 个请求。判据没变的是「成簇断网时别指望重试」，变了的是「零散断流时重试有用」。
- **换源（jsDelivr → GitHub raw 直连）** — 避开出问题的那一端点。**否掉因为方向反了**：源码注释记着直连 `raw.githubusercontent` 在本机**会被重置**（`ECONNRESET`），jsDelivr 已是实测更稳的选择；而且今天失败的是 body 读取被掐，换源等于把已排掉的问题换回来。
- **网络不可用时用「上次成功的清单快照」兜底** — 让断网时仍能验点东西。**否掉**：它需要定义「快照多久算过期」，且过期快照会**制造假绿**（拿旧基线比对，结论必然是「一致」）。那是设计而非补丁，且与「环境不可用不是通过」相冲突。原笔记也把它列为未做的方向，本轮仍不做。
- **把 `sync:check` 从 check 链移除** — 不受影响就不会红。**否掉因为那是把问题藏起来**：会让人以为「副本与上游一致」有人在验，实际没有。门禁消失比门禁红更糟。
- **提高尝试次数（3 → 5 或 10）** — 更耐受。**否掉因为收益递减而代价确定**：实测失败是零散的、单次重试就能救回，从 3 提到 10 只会在**真断网**时把失败延迟得更久（每轮 21 个文件 × 10 次 × 退避）。真断网时正确的行为是**尽快说「这次没验成」（exit 2）**，不是硬撑。
- **只改分类判据、不加重试** — 更小的改动面。**否掉因为它只治一半**：`terminated` 会说对话了（exit 2 而非 exit 1），但门禁照样红，只是红得更有道理。抖动仍然能让人无视它。

## Consequences

- **收益**：抖动不再直接判成「上游有差异」。此前 `terminated` 走 exit 1，把人引去查「为什么上游不一致」；现在明确说「这是环境问题，本次没验成」。
- **收益**：零散断流被真实救回。70 轮配对实测中重试救回 5 个已失败请求；不重试那臂出现过整轮失败，重试那臂 0 轮失败。
- **收益**：判据从「穷举措辞」改成「认错误码族」，下次 CDN 换一种断法不会立刻失效。
- **代价与已知上限**：**成簇断网时重试仍然无效** —— 这是原笔记的正确部分，没有被推翻。真断网/被限流时，3 次重试只会让失败晚 3 倍时间到来，最终仍以 exit 2 如实报告「没验成」。**环境不可用依然不是通过。**
- **代价与已知上限**：`attempts=3` 与退避基数是**判断而非实测最优值**。实测只支持「单次重试足够救回零散失败」，没有测出「3 是最优」。若将来出现需要更多次才救回的形态，要重新测量而不是直接调大。
- **代价与已知上限**：重试**只覆盖传输层**。若 CDN 改成返回 5xx（而非断连），那走的是 `拉取失败 5xx` 的 HTTP 分支，**不会重试**，且被判为「检查失败」(exit 1) —— 那可能又是一次假红。本轮没有证据说明它发生过，故不预先放宽（放宽 5xx 会掩盖真实的端点问题）。
- **代价与已知上限**：本轮的强证据是**配对对照**（同一窗口内两臂对比）。相对较弱的证据是最早那次「修前 CLI 三次里红两次、修后 5/5 全绿」—— 那两段不在同一时间窗口，**不能当成因果证据**，只作为「确实存在坏窗口」的旁证。
- **重访信号**：
  - 若出现「重试 3 次仍失败的**零散**断流」（而非成簇断网）→ 说明单次重试不够，要重测尝试次数与退避曲线。
  - 若 CDN 开始返回 5xx/429 而非断连 → 5xx 是否该重试需要重新权衡（现在明确不重试）。
  - 若 `sync-upstream` 换 HTTP 客户端 → `UND_ERR_` 前缀不再适用，要更新分类判据并跑那两条真实断流用例。

## Verification

新增 5 条用例（`tools/sync-upstream.test.mjs`，总计 10 条，全部通过）：

```sh
node --test tools/sync-upstream.test.mjs   # 10 tests / 10 pass / 0 fail
```

- **真实断流**：起真服务器、真把 socket 打掉，拿到的就是生产那个错误 ——
  断言 `message === 'terminated'`、且判为环境不可用。手搓错误对象只能证明
  「我以为的形状」，所以这条必须真断。
- **对照 404**：真服务器返回 404，必须留在 exit 1，不许被断流判据一起吞掉。
- **重试有效**：真服务器前两次掐断、第三次正常，断言正好尝试 3 次并拿到完整响应。
- **重试用尽**：始终断流时重试 3 次后仍抛原错误，且仍判为环境不可用（不许变成 exit 1）。
- **HTTP 不重试**：404 类错误只尝试 1 次。

**故障注入（真变异，改完还原）**：

| 变异 | 结果 |
|---|---|
| 删掉重试（传输层错误直接抛） | 5 条新用例里恰好 2 条变红（8 pass / 2 fail） |
| 挂载接线丢掉版本标签 | 见 `version-notice.test.mjs` 的三条真实挂载用例 |

**真实 CDN 配对实测**（探针写在 `.probe/`，不入库 —— 下面把方法写全，
便于日后重建；探针本身是一次性的）：

方法：完全复刻 `sync-upstream` 的取文件序列（1 次目录清单 + 21 个文件），
每轮在同一次网络条件下跑两臂 —— **A 臂首次传输层失败即判该轮失败（不重试）**，
**B 臂按本实现重试 3 次**。同一轮内相邻跑，避免把时间差异当成臂差异。

```
40 轮：A 无重试 39 成功 / 1 失败（fetch failed/UND_ERR_SOCKET）｜B 重试3次 40 成功 / 0 失败（触发重试 4 次）
30 轮：A 30 / 0                                        ｜B 30 / 0（触发重试 1 次）
```

即两轮 70 场合计：重试**实际救回 5 个已失败的请求**（B 臂各轮的 retries 之和），
不重试那臂出现过整轮失败，而同一窗口内重试那臂 0 轮失败。

**注意第一批数据差点被误读**：最早的 8 轮实测两臂 **8/8 全成功、重试 0 次触发** ——
若就此收工，会写成「网格稳定，重试无用」，而那是**只描述了一个时间点**
（rejected 那篇的「第一步」正是这么栽的）。所以样本量从 8 轮提到 40 轮，
才等到失败出现。**测抖动必须跨窗口多次采样，单次安静窗口说明不了任何事。**

CLI 层面同一实现：修前三次里红两次（exit=2）、修后 5/5 exit=0。
**但这两段不在同一时间窗口，不能当因果证据**，只作为「确实存在坏窗口」的旁证 ——
真正的证据是上面的**配对对照**。
