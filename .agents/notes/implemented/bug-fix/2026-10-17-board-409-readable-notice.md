# Agent Note: 看板 409 不再吐原始 JSON，也不许猜仓库

Status: implemented

## Problem

同一项目下开多个会话时，侧边栏的「笔记」tab 偶尔整块空白，显示一坨原始 JSON：

```json
{ "error": "no notes root resolvable for this session", "reason": "NO_NOTES_ROOT", ... }
```

重新打开 tab 又好了 —— 用户的原话是「莫名其妙的自己好了」。

两个独立问题叠在一起：

1. **成因**：`/agent-notes/ui` 是 iframe 的 `src`，而会话 id 来自持久化的 tab。切会话/重连后，tab 可能仍用**旧会话 id** 请求数据；而 `sessions.get(id)` 只查**活跃会话**，那个会话可能尚未加载 —— `header.cwd` 取不到，于是 `resolveTargetCwd` 返回 `NO_CWD`，路由回 409。实测可稳定复现：拿任意未加载的会话 id 请求 `/agent-notes/ui`，必得 409。
2. **呈现**：409 对 `/ui` 也回 JSON，而浏览器会**原样渲染** iframe 的响应体 —— 用户看到的是一坨机器错误，看着像插件坏了。

## Decision

两件事分开处理。

**① 呈现层：`/ui` 回可读说明页。** 新增 `renderNoticePage()`（`lib/board-route.js`），在解析不出笔记根时给 `/ui` 返回一张 409 的 HTML 页面：说清成因、给出恢复方法（切会话或重开 tab）、回显会话 id 与 `reason`。`/board`、`/note` 这些给程序用的端点保持 JSON 不变。

`must`：说明页里的会话 id 必须 HTML 转义。它直接来自 URL 查询参数并回显到页面里，不转义就是一个反射型 XSS（虽然 iframe 带 sandbox，但没有理由把未转义的用户输入拼进 HTML）。

**② 解析层：不猜仓库，只把诊断写清楚。** `resolveTargetCwd` 保持「拿不到 cwd 就明确失败」的契约，只是把 detail 从「检查 sessions 服务与 header.cwd」改成面向使用者的说明：这通常发生在持久化的 tab 仍用旧会话 id 时，切会话或重开 tab 即可恢复。

`never`：不得为了「让 409 消失」而退回 `process.cwd()`，也不得从 `sessions.list()` 里随便取一个活跃会话的 cwd。理由见下方 Alternatives。

## Alternatives considered

- **从同项目的其它活跃会话推断 cwd**（Owner 最初选定的方向，我实现后又撤回） — 这是最有吸引力的方案：不改契约、不改前端，一个回退就能让 409 消失。我实际写了两版实现，最后否掉，因为**它无法安全判定「同项目」**：
  - 第一版按「活跃会话里是否恰好只有一个项目目录」判断 —— 致命缺陷是：当只有**别的项目**活跃时，它会把看板指向别人的仓库，显示别人的决策笔记。那种「绿」比报错更坏，正是当年假绿门禁的成因。
  - 第二版改用「会话 id 同前缀」作判据。实测证伪：同一项目下的会话 id 是彼此无关的 UUID（实测 209 个会话同在一个项目目录下，id 形如 `059ba98b-…`、`06a9f391-…`，无任何共享前缀）。判据永远匹配不到，等于没写。
  - 根因是**信息不足**：会话 id 是 UUID，不含项目信息；`get()` 只查活跃会话；磁盘上的会话文件是 zstd 压缩的 jsonl，不适合作为同步路径的输入。没有可证信号能把目标会话绑定到某个项目，任何「推断」都是猜。
- **退回 `process.cwd()`** — 一行就能让 409 变成 200。否掉是硬性的：`process.cwd()` 是 DSH 自己的安装目录（实测通常是 `C:\...\dependencies\dsh`），那里也有 `.agents/notes`（DSH 自己的开发笔记），于是门禁会**真的跑通并返回绿**，测的却是另一个仓库。这条已经踩过一次并写进 `lib/target.js` 顶部注释。
- **前端把 409 的 JSON 解析出来、画成友好提示** — 能做到和说明页一样的效果，且不动服务端。否掉是因为 iframe 拿不到自己的响应体（跨文档读不到），前端只能靠 `fetch` 预检再加 iframe，多一次请求、多一个失败点。服务端直接回 HTML 更简单。
- **让 tab 不持久化会话 id，每次渲染都取当前会话** — 能根治成因。否掉是因为会话 id 由宿主 props 传入（`conversation.view` 的顶层 `sessionId` / better-sidebar 的 `scope.sessionId`），插件无权决定宿主何时传什么；而且 tab 的持久化是宿主行为，改它超出本插件边界。
- **把 409 改成 200 + 空看板** — 用户不会看到错误。否掉是因为它把「读不到」伪装成「没有笔记」—— 空看板会让用户以为项目没有决策笔记。空集不是证据，这是本仓库反复强调的一条。

## Consequences

- **收益**：409 时用户看到的是可读说明与恢复方法，而不是一坨机器 JSON。实测截图确认。
- **收益**：`resolveTargetCwd` 的契约没有被放宽。多项目并行时不会把看板指到别人的仓库 —— 这条比「少一个 409」重要得多。
- **收益**：说明页零外部依赖、内联样式、跟随系统深浅色，且它在错误路径上，不依赖任何可能同样失败的东西。
- **代价与已知上限**：**成因本身没有修**。持久化 tab 用旧会话 id 请求数据时，仍然会 409，只是现在看得懂了。真正的修复点在宿主的 tab 持久化行为，超出本插件边界。
- **代价与已知上限**：说明页是一段内联 HTML 字符串（约 2KB），多了需要维护的 UI 代码 —— 与本插件「不自绘 UI」的既定取舍有轻微冲突。但它是错误页而非看板，不涉及与上游的视觉同步，可以接受。
- **代价与已知上限**：`/board` 等端点仍是 JSON，若将来有第三方直接嵌 `/board`，需要自己处理 409。
- **重访信号**：若宿主某天改成「tab 总是使用当前活跃会话」，这个 409 会自然消失，说明页变成死代码 —— 那时可以删掉 `renderNoticePage()` 与对应测试，但保留「不猜仓库」的契约。

## Verification

```sh
node --test tools/board.test.mjs
```

两条新测试：
- `解析不出根时 /ui 回可读说明页，不是原始 JSON` —— 断言 409 + `text/html` + 含标题/成因/会话 id，且响应体不以 `{` 开头；同时断言 `/board` 仍是 JSON。
- `说明页必须转义会话 id（防注入）` —— 用 `<script>alert(1)</script>` 作会话 id，断言响应里出现 `&lt;script&gt;` 而非原始标签。

故障注入（已实测，两条都真红）：把 `/ui` 的说明页分支改成 `if (false)` → 第一条变红；把四个转义 replace 去掉 → 第二条变红。还原后全绿。

实机复现：`curl '/agent-notes/ui?session=<任意未加载 id>'` → 409 + HTML 说明页（截图确认可读）。
