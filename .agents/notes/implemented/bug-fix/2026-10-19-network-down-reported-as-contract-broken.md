# Agent Note: 断网时门禁报「契约被破坏」，实际是网络不行

Status: implemented

> 同属**流程补齐**这条线，与
> [2026-10-19-publish-gate-had-no-guardian.md](../process/2026-10-19-publish-gate-had-no-guardian.md)
> 同批（那一篇修的是「发布门禁没人保护」，本篇修的是「门禁在环境不可用时
 * 说的话是错的」）。
> 退出码约定的既有用法见 `tools/verify-notes.mjs` / `install-hooks.mjs` /
> `doc-budget.mjs`（三者都用 exit 2 表示「无法进行」）。

Independent: 本篇处理的是**失败信息的语义正确性**，与门禁判什么、
何时触发、跑多快都无关 —— 它不改任何判据，只改「不可用时怎么说」。

## Problem

本机网络断了一次（SSL 握手失败，curl exit 35），`npm run check` 红了：

```
✖ 同步清单确实存在且覆盖全部上游文件
  AssertionError: --check 在上游一致时应 exit 0，实际 1
  合并失败: fetch failed
```

**这条断言在说「契约被破坏」，而实际是「网络连不上，压根没检查成」。**

而且它误导排查：人会去查「为什么上游不一致」，而真因是网络。

### 根因

`sync-upstream.mjs` 的 catch 块：

```js
main().catch((error) => {
  console.error(`合并失败: ${error?.message ?? error}`);
  process.exit(1);        // ← 1 = 「检查失败」
});
```

网络不可用与「上游真有差异」**共用 exit 1**，上层无法区分。

## Decision

### 一、工具侧：区分 exit 1 与 exit 2

新增 `isEnvironmentUnavailable(error)`，把网络类错误映射到 **exit 2**：

| 类别 | 例子 | 退出码 |
|---|---|---|
| 环境不可用 | `fetch failed`、`ENOTFOUND`、`ETIMEDOUT`、`ECONNREFUSED`、`EAI_AGAIN`、证书错误、401/403/429 | **2** |
| 有效检查结果 | 404（ref 不存在）、合并冲突 | 1 |

404 留在 1 是有意的：**上游确实没那个 ref，那是真问题**，不是「查不到」。

`must`：**措辞向既有约定靠拢，不要求既有约定改。** 我最初写「无法检查上游」，
而 `self-update.test.mjs:299` 早就断言 exit 2 时消息匹配
`/查不到上游 HEAD|无法校验/`，注释还写着「网络不可用时明确跳过，不算假绿」
—— **它比我先处理了这个问题**。改成「无法校验上游」。

### 二、测试侧：环境不可用要说清楚，但**仍然失败**

```js
if (code === 2) {
  assert.fail(
    '**环境不可用**，不是契约被破坏 —— 上面的 exit 2 表示网络不可用或被限流，'
    + '这次检查压根没做成。\n'
    + '（这是真实结论：本次运行没有验证「' + what + '」这条契约。）\n' + out
  );
}
```

`must`：**不用 `test.skip()`。** 跳过是假绿的温床 —— 它会让「这条契约现在
没人验」静悄悄过去。选择「仍然失败，但把失败信息说清楚」：CI 上有人看得见
「这条没验成」，排查的人不会被引向错误方向。

这与本仓库「门禁以退出码为准，脚本缺失算失败但不得降级为通过」一致 ——
**环境不可用不是通过。**

### 三、纯本地的用例不受影响

`sync-upstream.test.mjs` 4 个用例里，第 4 个（`上游清单与元数据可解析`）
只读本地文件，**断网时仍绿**。实测确认。

新增的第 5 个用例验的是纯函数 `isEnvironmentUnavailable()`，
**在任何网络状态下都能跑** —— 不真去断网。

## Alternatives considered

- **断网就 skip 那几个用例** — 最省事。**这是本篇最强的一条被否方案**，因为它把「本次没验证」变成「看起来通过了」。本仓库的红线明确写着「门禁不得显示通过但实际没验证到东西」，skip 就是那种形态的温和版。
- **让 sync-upstream 完全不联网（只比本地缓存）** — 根治网络依赖。否掉因为它的职责就是「核对内置副本与上游是否一致」，不联网它什么也验不了 —— 那道门禁会变成恒绿。
- **在 `npm test` 层面统一处理（网络不可用就整体退出 2）** — 一处解决。否掉因为粒度太粗：29 个测试文件里只有 3 个需要网络，其余 26 个本可以正常跑。整体退出会让一次断网浪费全部验证。
- **把措辞改成「无法检查」并顺手改 `self-update.test.mjs` 的断言** — 也可行。否掉因为那条测试的注释表明它**早就在处理这个问题**，且约定是它定的。新代码向既有约定靠拢比让既有约定迁就新代码更稳 —— 否则下一个人又会引入第三种措辞。

## Consequences

- **收益**：断网时门禁说的是真话。「本次运行没有验证 X 这条契约」比「X 被破坏」有用得多。
- **收益**：`sync-upstream.mjs` 的退出码与本仓库其它工具一致（2 = 无法进行），调用方可以用退出码判断「该不该重试」。
- **收益**：新增的纯函数用例在任何网络状态下都能跑，**不把门禁的可用性绑在网络上**。
- **代价与已知上限**：断网时 `npm test` 仍然红。这是有意的 —— 环境不可用不是通过。代价是断网时 CI 会红，需要人判断「是环境问题还是真问题」（现在错误信息会明说）。
- **代价与已知上限**：`isEnvironmentUnavailable` 用**消息与错误码的字符串匹配**判定。若上游把 `fetch failed` 改成别的措辞，这个判定会失效 —— 而失效的表现是「exit 2 变回 exit 1」，即回到今天这个状态。有测试钉住当前措辞，但措辞变了要改测试。
- **代价与已知上限**：401/403 被判为「环境不可用」而非「检查失败」。若上游真的返回 403 表示「该 ref 不可见」，那会掩盖问题。**判据是「403 更可能是限流或权限问题，而不是内容差异」** —— 这是一个判断，不是事实。
- **重访信号**：若 `sync-upstream` 改用别的 HTTP 客户端（消息措辞会变）→ 要更新 `isEnvironmentUnavailable` 并跑那条纯函数用例。若本仓库开始支持私有上游（403 变成正常路径）→ 要把 403 从「环境不可用」里移出。

## Verification

```sh
node --test tools/sync-upstream.test.mjs   # 5 个用例
npm run check                              # exit 0（313 测试）
```

**实测断网时的行为**（真的断了网络）：

```
$ node tools/sync-upstream.mjs --check
上游: https://github.com/czm15053/write-notes-like-deepseek.git @ 72573a5b...
无法校验上游: fetch failed
这是**环境问题**（网络不可用或被限流），不是「上游有差异」。
退出码 2 = 无法进行（本次没有完成校验）；上游真有差异时退出码是 1。
$ echo $?
2
```

```
✖ 同步清单确实存在且覆盖全部上游文件
  AssertionError: **环境不可用**，不是契约被破坏 —— 上面的 exit 2 表示
  网络不可用或被限流，这次检查压根没做成。
  （这是真实结论：本次运行没有验证「--check 在上游一致时」这条契约。）
```

网络恢复后同样 5/5 全绿 —— 说明它验的是真契约，不只是没报错。
