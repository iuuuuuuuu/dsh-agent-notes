# Agent Note: 5xx 被判成「上游有差异」，全 404 被判成「一致」

Status: implemented

> 接续 [2026-10-24-transport-flake-made-upstream-check-falsely-red.md](2026-10-24-transport-flake-made-upstream-check-falsely-red.md)
> ——那一篇修的是**传输层**族（`UND_ERR_` / `terminated`）漏判，
> 本篇修的是同一张表里剩下的两类：**HTTP 状态码**与**一个文件都没读到**。
> 空集合当绿的判据来源见
> [../process/2026-10-22-empty-corpus-must-not-pass.md](../process/2026-10-22-empty-corpus-must-not-pass.md)。

## Problem

只读审计（`.probe/audit-tool-gates.md`）在同一个文件里又挖出两条，方向相反：

**一、5xx 假红。** `isEnvironmentUnavailable()` 用 `/\b(401|403|429)\b/`
匹配**消息里的数字**，5xx 整族（500/502/503/504）与 400/408/451 全落进
「检查失败」→ **exit 1**，即「上游真有差异」。实测：503 时只请求 5 次
（4 次清单 + 1 次文件）⇒ **既不判环境、也不重试**；同一探针换成 undici
传输层错误则请求 7 次（4 + 3 次重试）并正确退 2。**同一种「这次没做完」
在两种失败形态下得到相反的结论。**

**二、全 404 假绿，并会把基线写没。** `upstream-missing`（取到 404）不计入
任何计数，于是「21 个文件全部取不到内容」与「21 个文件全部相同」走**同一条
绿分支**：打印「内置副本与上游一致，无需合并」并 `exit 0`。更重的是同一分支在
非 `--check` 时调 `writeManifest`，**不需要 `--yes`**：实测隔离副本里
`files` 从 **21 条写成 0 条**、`upstream.json.fileCount=0`、exit 0。
空清单再喂回 `--auto` ⇒ `✔ 已是最新，且内置副本与清单一致`。

两条的根因是同一个：**没有把「这次到底验了多少东西」当成判据。**

## Decision

### 一、失败分类收敛成一处，且认类别不认措辞

原来的两份独立词表（`isEnvironmentUnavailable` 判退出码、`isTransportError`
判要不要重试）合成 `classifyFailure(error)`，返回
`{ area: 'environment' | 'contract' | 'incomplete', retryable }` ——
**一张表回答两个问题**，两份词表必然漂移。

判据顺序：先读本脚本自己抛的结构化字段（`kind: 'http-status'` 配
`status` / `endpoint`，`kind: 'upstream-layout'`，`kind: 'incomplete-check'`），
再读传输层错误码族（`^UND_ERR_` 前缀与 errno 码），最后才是消息兜底
（服务「别的来源抛来的错误对象」）。

### 二、口径表

| 情形 | 分类 | 重试 | 退出码 |
|---|---|---|---|
| 文件端点 404（`fetchUpstream` 返回 `undefined`） | 有效结果 `upstream-missing` | — | 由比对下限决定 |
| **清单端点 404**（ref 不存在） | `contract` | 否 | **1**（真差异） |
| 408 与 5xx | `environment` | 是（3 次，250/500ms） | 2 |
| 401/403/429 | `environment` | **否** | 2 |
| 其余 4xx（400/405/451） | `environment` | 否 | 2 |
| 传输层（`UND_ERR_*` / `ECONNRESET` / `terminated`…） | `environment` | 是 | 2 |
| 上游目录结构变了 | `contract` | 否 | 1 |
| 比对不完全部枚举文件 | `incomplete` | 否 | 2，**且零写入** |
| 认不出来的 | `contract` | 否 | 1 |

`must`：**只有清单端点的 404 让 HTTP 失败留在 exit 1。**
把所有非 404 的 HTTP 失败一律改成 exit 2 更简单，但那会把「ref 不存在」
这种真差异一起掩盖 —— 那是本仓库最不该放过的一类。

### 三、比对下限：一个文件都没读到 / 只读到一部分都不许绿

`paths` 是从**上游自己的目录清单**枚举出来的，所以「同一份清单里既列出又取不到」
只可能是这次校验没做完（CDN 不一致、负缓存，或 `--ref` 指的是会移动的分支）。
只要有 `upstream-missing` 就抛 `incomplete-check`（exit 2），**在写盘之前**，
所以基线一条都不动。

`must`：**部分读不到也判红，不只判「一个都没读到」。** `manifest` 是
「这次真读到了什么」的记录，少读一个就抹掉一条基线，而结论照样印成「一致」。
**零写入比写坏好。**

## Alternatives considered

- **把所有非 404 的 HTTP 失败一律判 exit 2** — **这是本篇最强的一条被否方案**。它的理由很硬：口径简单一致，不用为「哪个端点」分情况，而且绝大多数 HTTP 失败确实都是「没做成校验」。**否掉因为有一条例外伤不起**：清单端点的 404 意思是「这个 ref / 这条路径不在上游那棵树上」，那是**真差异**，正是这道门禁存在的意义。一律退 2 会让「内置副本指向了一个不存在的上游」被说成「网络问题」，排查方向直接反了。所以例外只有一条，且写进了口径表与用例。
- **只把 5xx 加进那张数字表**（`/\b(401|403|429|5\d\d)\b/`）— 改动最小。**否掉因为它治的是症状**：问题从来不是「少写了几个数字」，而是「拿消息里的数字当判据」。补数字能过今天这个用例，下一次 CDN 换一种失败（或改措辞）照样漏 —— 而今天下午刚因为同一原因栽过一次（`terminated`）。改成结构化字段后，判据不再依赖任何措辞。
- **保留两份词表，各自打补丁** — 改动面更小，不用动两个调用方。**否掉因为两份表一定会漂移**：今天 5xx 就是**同时**从两张表漏出去的（既不判环境也不重试），这正是「两份真相」的必然结果。收敛成一个返回值，就没有「只更新了一张表」的余地。
- **把 `upstream-missing` 继续当正常状态，只把「下限为 0」判红** — 更贴近原来那句「上游已无此文件（保留本地）」的语义。**否掉因为部分读不到同样会写坏基线**：只要有一个文件读不到，写下去的 manifest 就少了那一条，而结论仍然印「一致」。界线应该画在「这次读全了吗」，不是「读到几个」。
- **顺带把写盘路径的 `--yes` 前置条件一起收紧** — 那条路径现在不需要 `--yes` 就改两份数据文件，与「确认后合并」的语义不一致。**本轮不做**：比对下限已经挡住了这次实际发生的自毁（所有走到写盘的路径都要求比对完整），再把 `--yes` 语义一起改会扩大改动面且要动 CI 的 `--auto`。见重访信号。

## Consequences

- **收益**：5xx 不再被说成「上游有差异」。实测 503 ⇒ exit 2 且重试 3 次（请求计数 7 而非 5）。
- **收益**：「一个文件都没读到」不再可能报「一致」，也不可能写盘 —— 21 条基线在隔离副本里逐条保留，有断言钉住。
- **收益**：判据从「穷举措辞」变成「结构化字段 + 错误码族」，下次 CDN 换一种失败形态不必再补一次数字表。
- **代价与已知上限**：**5xx 重试 3 次仍失败 ⇒ 仍是 exit 2**，环境不可用依然不是通过。真断网时只是让失败晚 3 倍时间到来。
- **代价与已知上限**：401/403/429 判为环境问题（exit 2）仍是**判断而非事实**。若将来上游真的用 403 表示「该 ref 不可见」，那会被说成环境问题而掩盖真差异。判据是「403 更可能是限流或权限问题」。
- **代价与已知上限**：`incomplete-check` 覆盖了「有任意一个 `upstream-missing`」，因此**上游合法删文件**这种情形也会被判红（即使内容比对全都成功）。若上游真的删文件，正确做法是先把新 ref 同步进来，而不是让门禁放行一份缩水清单 —— 但这是取舍，不是显然的。
- **代价与已知上限**：本轮的后半段（比对下限与写盘守卫）由 teammate 实现但**未带测试交付**，测试与笔记由 Lead 补齐；实现与测试不是同一时刻落盘的。
- **代价与已知上限**：**变异测试第一次真把仓库基线写坏了**（`files` 21 → 0，只能从 HEAD 恢复）。原因是那条用例刻意走写盘路径却在真仓库里跑。现已改成**隔离副本**（`sandbox: true`），并在用例里断言真仓库的 manifest 逐字未动 —— 这类「测闸门的用例自己会破坏地盘」的坑，仓库里早有笔记记过（`2026-10-18-ci-vendored-tampered-by-tests.md`）。
- **重访信号**：
  - 若开始允许「上游删文件」作为正常同步结果 → `incomplete-check` 的覆盖范围要重新画（现在是一刀切）。
  - 若有人给写盘路径补上 `--yes` 前置 → 要重跑本节的下限用例，确认两者的语义不冲突。
  - 若 CI 的 `upstream-sync.yml` 因本改动出现假红（例如上游确实删过文件）→ 先看它是不是真的比对不全，不要直接把阈值放宽。
