# Agent Note: 发版记账门禁的测试与 CHANGELOG 形状耦合

Status: implemented

> 触发场景：发 0.6.0 时 `npm run check` 红 5 条，全部来自
> `tools/release-check.test.mjs`。
> 门禁本身（`tools/release-check.mjs`）没问题 —— 是**测试的前提过时了**。

Independent: 与本仓库其它笔记不重叠 —— 那些讲判据设计（该比什么），
本篇讲**测试如何依赖会变的外部状态**。

## Problem

发版时的动作是：把 CHANGELOG 的 `[Unreleased]` 段转成 `[0.6.0] - 日期`，
再改 `package.json` 版本，再打 tag。

而 `tools/release-check.test.mjs` 里有 5 条用例**以真实 CHANGELOG 为输入**，
且其中 4 条假设「CHANGELOG 一定有 `[Unreleased]` 段」。

转段之后那个段就没了 → 那 4 条全红。

### ★ 但真正的问题不是「要改测试」

先查了门禁本身怎么说：

```
把空 [Unreleased] 加回去 → release-check 失败：
  ✖ CHANGELOG.md 的 [Unreleased] 段是空的 —— 要么把内容归入下一个
    版本段，要么删掉这个空段
```

**两者直接矛盾**：

| | 要求 |
|---|---|
| `release-check.mjs`（门禁） | `[Unreleased]` **不能是空的** —— 要删掉 |
| `release-check.test.mjs`（测试） | 假设真实 CHANGELOG **一定有**该段 |

不可能同时满足。所以必须判断**谁过时了**。

### 「上次我这么做没报错」不能当依据

我最初看到的是：`git show v0.5.0:CHANGELOG.md` 里 **0.5.0 发版时留了空段**。
于是推断「流程是转段 + 补空段」——**推错了**。

`git log -S "段是空的" -- tools/release-check.mjs` 显示：

```
caec86c  feat(release): 发版记账门禁 + 修掉并行测试的偶发失败
```

★ 那条「空段必须报错」的规则是 `caec86c` 引入的，**晚于 v0.5.0**。
0.5.0 时能留空段，是因为**那时还没有这条规则**。

## Decision

**把那些用例改成用自造 fixture**，不再依赖真实 CHANGELOG 的形状。

### 三个必须做对的细节

**① fixture 的版本段要跟随 `CURRENT_VERSION`**

我第一版写死 `0.5.0`，于是 `verifyRelease` 先报
「当前版本 0.6.0 在 CHANGELOG.md 里没有对应段」—— 那几条用例看到的是
**这条噪声**，而不是它要验的东西。

**② 「版本号没有对应段」那条不能写死具体版本号**

它原本写死 `0.6.0`，而 fixture 改用当前版本后**恰好含 0.6.0** → 那条错不再
发生，用例变成在验「有对应段」。

改用一个**不可能存在于 fixture 里**的版本号 `99.99.99`，且不随时间失效。

**③ ★ 顺带拆掉一颗定时炸弹**

`往 [Unreleased] 加内容必须放行` 那条靠
`changelogBackup.replace('## [Unreleased]\n', ...)` 找锚点。

★ 真实文件发版后没有该段时，`replace` 找不到就是**空替换**，而断言
「攒内容必须放行」会在**什么都没加**的情况下通过 = **假绿**。

它与「删掉 `[Unreleased]` 段必须放行」互为对照组。只改一条会留下这个雷。

已一并改用 fixture，并**加了一条「替换必须真的发生」的断言** ——
否则那条新断言自己也是空转。

## Alternatives considered

- **改门禁，放行空段** —— 让测试和门禁都满意。**否掉因为那条规则有它自己的理由**（注释原话：「空段会让『攒着不发』这件事看不见」）。为了迁就一条过时测试而废掉一条有效门禁，是本末倒置。
- **每次发版后手动改测试** —— 最小改动。**否掉因为它是「靠人记得」**：本仓库的 `notes:coverage` 那条纪律就是为了消灭这类靠人记得的事（注释里写着「修紧急故障时注意力全在『让它绿』，而『要不要留笔记』需要主动回想，多轮里必被挤掉」）。**同一个坑不该踩两次。**
- **让测试跳过**（`test.skip`）—— 更省事。**否掉因为那等于删掉覆盖**：那几条用例验的「解析器分得清版本段与小节」「缺段/空段/重复段会报错」是真实判据，丢掉可惜。

## Consequences

- **收益**：发版不再让 `npm run check` 变红。**发版本来应该是「版本号 + tag」两步，不该顺手改测试。**
- **收益**：那几条用例不再与版本号耦合 —— 以后每次发版都不用动它们。
- **代价与已知上限**：fixture 是**手写的一小份 CHANGELOG**，只含 2 个版本段与 2 个小节。真实文件有 30+ 个版本段。所以「解析器在超长文件上表现如何」这条覆盖**没有变强** —— 原先靠真实文件间接覆盖的那部分，现在真的没了。
  ★ 但那本来是**偶然覆盖**（测试能不能跑取决于发没发版），不是有意设计。
- **代价与已知上限**：`CURRENT_VERSION` 从 `package.json` 读，所以若 fixture 的版本段与真实版本同名，两者在「缺段」这类用例上会互相干扰。当前 fixture 只有 2 个段，而真实 CHANGELOG 有 30+ 个，**将来真实 CHANGELOG 里出现 `[99.99.99]` 时那几条用例会失效** —— 极不可能，但记下来。
- **重访信号**：
  - **将来 `PAIRS` 扩到多对文档** → 这条笔记的机制（fixture 而非真实文件）同样适用。
  - **若有人想让那几条用例也覆盖真实 CHANGELOG** → 应该加一条独立的「真实文件能解析且无重复段」用例，而不是把 fixture 换回去。

## Verification

```sh
node --test tools/release-check.test.mjs   # 10/10
node tools/release-check.mjs               # 发版记账一致
npm run check                              # exit 0
```

**矛盾已实测**，不是推断：

```
把空 [Unreleased] 加回 CHANGELOG → release-check 立刻失败：
  ✖ CHANGELOG.md 的 [Unreleased] 段是空的
```

### 一条方法教训

「0.5.0 发版时留了空段」这个观察**看起来是规范的直接证据**，实际上那份规范
后来变了。**用历史实例当依据之前，要先查规则是什么时候加的** ——
`git log -S "<规则的关键词>" -- <规则所在文件>` 一条命令的事。

★ 这与本仓库反复栽的「测试工具自己坏了」「注释承诺 ≠ 实现做到」同源：
  **证据是真的，但它证明的是过去，不是现在。**
