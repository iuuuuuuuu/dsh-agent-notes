# Agent Note: iframe 的 load 不是成功，看板空文档由父页恢复

Status: implemented

## Problem

用户在「所有智能体并行推进任务」会话打开笔记 tab，整个区域纯白，重启也一样。
上次用同项目较小会话验证通过，证明不了用户这一个桌面窗口的实际显示。

本次先精确找到原会话：正常浏览器请求 `/ui` 返回 200，434 项数据和脚本正常；
随后仅对桌面当前视图做临时只读诊断，用户保持白屏现场后量到：

- 选中的确是笔记，iframe 存在、可见且约 1126 × 1280，不是高度为零。
- iframe 文档 `readyState=complete`，但标题为空、正文长度为 0。
- 相同目录的数据可正常渲染；独立 Electron 也不能稳定复现这一桌面原生导航故障。

已经证实的是「原窗口停在完成加载的空文档」，不是数据为空、布局压缩或正文脚本报错。
空导航来自桌面哪一层尚未完整定位，修复不把猜测写成根因。
旧实现收到 `load` 就设为 ready，浏览器空文档同样能触发它，于是永远没有恢复机会与错误提示。

## Decision

### 正常导航不变，仅恢复空帧

`watchBoardFrame` 挂到真实 iframe ref，检查文档是否已解析且具有正文。
2.5 秒启动检查；尚未解析时短间隔再查，最多等待 15 秒，不把解析中的页面误判为成功。
`interactive` 且正文已生成即可 ready，不能让字体/图片等非关键外部资源拖住 complete，
反而在已画好的看板上留下加载或错误遮罩。

只有空文档或帧加载失败时，由父页对**同一个已解析会话/cwd 的只读 URL** 发起 fetch，
要求成功的 HTML 响应与非空 body。使用浏览器原生 `DOMParser`，设置完整 `/ui` URL 为
`base.href`，以 `srcdoc` 放回仍带 sandbox 的 iframe。每次挂载只允许一次恢复，
父页请求设 10 秒期限；失败显示错误和显式重试，不循环刷新。

正常文档保持原 URL，不多拉一份 HTML，不替换用户已打开的看板。
切换会话或卸载时取消计时器、事件监听和请求；迟到响应不能写回旧帧。

### srcdoc 的刷新路径按真实基址解析

srcdoc 的 `location` 是 `about:srcdoc`，不能继续从 `location.pathname` 推 `/data`。
热更新补丁改用 `document.baseURI` 加原始 query，通过原生 URL 解析器生成数据端点，
保留挂载前缀、session、cwd。不重写上游看板、抽屉或数据注入器，不手改 vendored。

HTTP base 会让上游 `history.replaceState(..., '#timeline')` 被解析成 HTTP 文档地址，
与 `about:srcdoc` 的实际文档地址冲突。恢复页在上游脚本前注入局部桥接：仅把 `#` 开头的
replaceState URL 改为该 srcdoc 自己的完整片段地址；其他 URL 保留原浏览器检查。
真实浏览器必须验证视图切换、笔记抽屉和关闭，不能只确认首屏卡片。

### 不让浏览器回归只测桩

增加仅开发使用的 `playwright-core`，复用真实 Chromium；测试直接暴露原闭包里的
监视函数运行，不另实现恢复逻辑，不替换 DOMParser、iframe 或 fetch。
两个会执行测试的 workflow 均安装 Chromium；本地缺浏览器明确失败，不按通过处理。

正常路径、原生空 about:blank、HTTP 错误、空 HTML、显式重试、停止后的迟到响应，
以及 srcdoc 的脚本资源和 `/data` query 都在真实页面与本地 HTTP 服务里执行。

## Alternatives considered

- **直接重载 iframe**：改动小，能救短暂断网。但用户重启仍白屏，同一种原生导航
  可能再次完成为空文档；选父页读取再装入的独立恢复路径。
- **所有页面一律 fetch + srcdoc**：统一路径，省去判定。但正常加载凭空多一次请求和
  HTML 解析，还改变所有看板文档地址；仅空帧触发，保留正常路径。
- **修改桌面运行时或注入全局 CSS**：能介入更底层，但尚无证据指向具体桌面故障点，
  iframe 尺寸与可见性正常。局部恢复足够，不扩散到桌面安装或别的插件。

## Consequences

- 空文档不再被 `load` 冒充 ready；能恢复或给出显式错误与重试。
- 不用用户重复重启，不把全局技能、项目笔记或会话数据改写为绕过手段。
- 只有失败路径会额外取一次 HTML；恢复瞬间保留一份 HTML 与 DOM 解析结果，
  多笔记项目存在额外内存开销，但正常路径无此开销。
- srcdoc 需要维护正确 base，且不能承诺修复任意脚本崩溃：已有非空错误页、上游脚本故障
  不等同于空帧。若桌面提供明确导航失败原因，应优先使用真实错误，减少推测。
- 浏览器回归增加开发依赖及约二十秒执行时间；不增加运行时依赖，不吞掉安装失败。

## Verification

- 用户在原桌面白屏会话重新打开后确认「看板和卡片已显示」。这是用户本人观察，
  不冒充执行者截取了原桌面窗口。
- 独立浏览器精确打开同一会话，强制该 iframe 原生文档导航返回空 HTML，
  父页仍访问真实 `/ui`，验证恢复后的 434 项数据、尺寸和无脚本错误。
- `tools/board-frame.test.mjs` 使用真 HTTP + Chromium，分别覆盖正常、空帧、错误、重试、
  中止与正确刷新地址；不使用替代 DOM。
- 最终 `npm run check` 退出码 0：727 条测试全部通过，完整故障注入门禁通过。
  真实浏览器回归缺少 Chromium 会明确失败，本次使用已安装的独立 headless shell，未跳过。
- 隔离副本基线通过；分别注入空文档冒充成功、丢失 base、移除片段历史桥接、
  从 location 解析刷新 URL、仅 complete 才放行等 5 种故障，全部命中预期浏览器回归并
  exit 1；恢复后重新为绿，未在生产目录注入故障。
- 最终构建在原会话验证正常导航和强制空导航两条路径，434 项数据正常显示；
  时间线切换、笔记正文抽屉及关闭均工作；恢复页无脚本异常。无笔记会话仍不出现看板。
  独立截图亲眼判读通过，加载提示不再覆盖已渲染的卡片。原桌面窗口的恢复由用户确认。
