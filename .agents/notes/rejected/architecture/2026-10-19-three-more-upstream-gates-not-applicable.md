分工不同。三项分属不同机制，互不冲突。

## Problem

goal 要求逐项核查上游 65 道 `verify-*`，不适用也要写清理由与重访信号 ——
否则半年后有人重新提起，而没人记得为什么。

本轮核查的是三个「看起来通用、实际不适用」的：

1. `verify-no-top-level-await` —— 禁止模块级 `await`；
2. `verify-export-jsdoc` —— 每个导出都要有完整 JSDoc；
3. `verify-public-repository-links` / `verify-concrete-terms` —— 见下。

## Proposal

曾考虑把这三项吸收为本仓库门禁，理由分别是：

1. **顶层 await** 会让 importer 的求值变异步、失败变成模块求值错误 ——
   听起来对任何 Node 项目都成立。
2. **导出 JSDoc** 是「公共面必须有文档」的通用纪律，本仓库 `lib/` 有 76 个导出。
3. **失效仓库引用 / 模糊来源标签** 看起来是文档卫生的通用检查。

## Decision

### 一、`verify-no-top-level-await` —— 不适用

上游三条理由都具体（importer 求值变异步、拒绝变成模块求值失败、无法降级成
同步 CommonJS 包装），且**明确豁免可执行文件**（`#!` 开头，因为不被 import）。

本仓库实测：

| 文件 | 模块级 await | shebang | 判定 |
|---|---|---|---|
| `lib/` 各模块 | 无 | 无 | 合格 |
| `lib/self-update.js` 的 await | 在 `async function mapLimit` 内 | 无 | 合格 |
| `tools/verify-notes.mjs` | **有** | **有** | 豁免（可执行） |
| `tools/*.mjs` 其余 | 均在函数内 | 多数有 | 合格 / 豁免 |

**唯一在模块作用域 await 的是可执行脚本**，上游同样豁免它。

**决定性理由是「手写实现会漏报」**：正确判定要区分「模块作用域 vs 函数体内
（含嵌套块、条件、循环）」「`for await` 与 `await using`」，还要排除字符串、
模板字面量、注释里的 `await`。上游为此用 TypeScript 解析器。

实测我的粗判脚本（按花括号深度计数）**漏掉了 `const x = await ...` 这一形式**
—— 而那正是本仓库唯一的那处。漏报是假绿的经典形态：门禁显示通过，
而它根本没看见该看的东西。

### 二、`verify-export-jsdoc` —— 不适用（但顺带修了一处）

实测覆盖率：

| 指标 | 值 |
|---|---|
| `lib/` 导出 | 76，**100%** 有 JSDoc |
| `tools/` 导出 | 16，**100%** 有 JSDoc |
| 有参数且有 `@param` | 60 |
| 有参数但缺 `@param` | **1**（`lib/skill.js` 的 `createSkillProvider`） |
| 有返回值但缺 `@returns` | 0（初测报 3，全是 `register*` 的 void 函数，粗判误报） |

**那唯一一处已修** —— 补上 `@param {object} control`。但它是**人工发现的，
不是门禁发现的**。

不加的三条理由：

1. **需要 TypeScript 解析器**。为一条「92 项里 0 项违规」的规则引入 TS，
   是拿重依赖换零收益。
2. **手写近似在两个方向都错**。实测粗判把三个 void 函数误报成缺 `@returns`
   （误报 → 门禁被关掉）；而更糟的是漏报 —— 只看「有没有 `/**`」，
   一个空壳注释也能通过。
3. **本仓库的 JSDoc 是自发的**，不是被门禁逼出来的。这说明团队本来就会写，
   加门禁不改变行为，只增加维护面。

**更根本的一条**：这条规则对**发布为库**的项目是硬需求（使用者只看得到签名）。
本仓库的对外契约是**笔记方法 + CLI 门禁**，`lib/` 是给 DSH 宿主按鸭子类型调的，
不是给人类读的 API 文档。所以「完整流程」在本仓库不包含「生成 API 文档」
这一步 —— 那才是决定性的。

### 三、`verify-public-repository-links` / `verify-concrete-terms` —— 不适用

这两条是**特定仓库专属**，不是通用纪律：

- `verify-public-repository-links`：拒绝引用**某个已失效的旧仓库**。
  本仓库只有一个仓库地址（`iuuuuuuuu/dsh-agent-notes`），从未迁移过。
- `verify-concrete-terms`：拒绝**一个特定的模糊来源标签**（针对某个具体
  字符串的替换）。本仓库没有那种历史包袱。

把「某个仓库的迁移残留」写成通用门禁，会让本仓库带上一份与它无关的
字符串黑名单 —— 那是把别人的技术债搬进自己仓库。

## Alternatives considered

- **给顶层 await 与 JSDoc 各写一个「宽松版」门禁**（只查最常见的形态） — 覆盖 80% 场景。**这是本篇最强的一条被否方案**：宽松版能拦住多数新引入的问题。否掉是因为**漏报的那部分恰好是最危险的**——本仓库唯一那处顶层 await 就是 `const x = await` 形式，宽松版看不见；而空壳 JSDoc 同样能通过「有没有 `/**`」的检查。一个会漏报的门禁比没有更糟：它让人以为已经检查过了。
- **只在 `lib/` 上加 JSDoc 门禁**（tools/ 是脚本，不必严格） — 缩小范围、降低成本。否掉因为 `lib/` 已经是 100%，而唯一的缺口在 `lib/skill.js` 里 —— 加门禁不会让它更早被发现，因为它本来就在 `lib/` 内且被漏了。
- **把这两项写进 `AGENTS.md` 作为约定而非门禁** — 零代码。否掉因为 AGENTS.md 已有字数预算（2100，当前 2073），且「约定」正是本篇反复证明靠不住的那类机制（门禁没人跑、生成物没跟上源，都是「写了但没执行」）。
- **三项都直接跳过不写笔记** — 省时间。否掉因为 goal 明确要求「不适用也要写理由与重访信号」，而且这已经是第二批 —— 第一批的三项若没记，这次就要重新查一遍。

## Consequences

- **收益**：三项有了可复现的判据与数据，附实测脚本。后续任何人重新提起，跑一遍就知道结论还成不成立。
- **收益**：顺带修掉 `lib/skill.js` 唯一一处缺失的 `@param`。这是本轮唯一的代码改动，很小，但它是真实缺口。
- **收益**：确认 `lib/` 与 `tools/` 的 JSDoc 覆盖率是 100% —— 这把「我们文档写得怎样」从主观印象变成数字。
- **代价与已知上限**：核查脚本在 `.probe/tmp/` 下**不入库**（本仓库约定探针不入库）。所以数据是 2026-10-19 的快照，且复核时要重写脚本。**这是本篇的已知敞口** —— 与第一批那三项同一个问题。若这类判定持续累积，应考虑把脚本收进仓库。
- **代价与已知上限**：JSDoc 覆盖率是用「紧邻上方是否有 `*/`」粗判的，**不看内容质量**。所以「100%」只证明有注释块，不证明注释有用。要判质量得读 92 段文字，那是人的工作。
- **重访信号**：
  - **顶层 await**：`lib/` 下出现模块级 await（真实缺陷）→ 那时值得引解析器。
  - **JSDoc**：本仓库开始发布可被第三方 import 的库（`exports` 暴露 `lib/`）→ API 文档成真需求；或覆盖率降到 80% 以下（团队习惯变了）。
  - **失效仓库引用**：本仓库真的迁移过仓库地址时，才需要这条。
