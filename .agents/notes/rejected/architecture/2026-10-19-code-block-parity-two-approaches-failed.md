# Agent Note: 「比代码块内容」的两种折中都被证伪了

Status: rejected — 两种形态规则各留下一处「合理的正确差异」，机械识别做不到

> 接续 [2026-10-19-i-was-wrong-about-not-needing-mdast.md](../../implemented/bug-fix/2026-10-19-i-was-wrong-about-not-needing-mdast.md)
> ——那一篇发现上游签名含 `code`（完整内容）而我只比了 `lang`，并留下
> 「代码块内容这一项值得单独评估 … 可以比『去掉注释后的命令部分』」这个
> 待评估项。**本篇是那个待评估项的结论：两种折中都证伪。**

Independent: 本篇否决两个具体的判据设计，不改变任何门禁行为。

## Problem

待评估的问题是：代码块内容能不能比？若能，怎么处理**混在代码块里的、要翻译的
说明文字**？

实测起点：README 有 12 对代码块，**原样就有 4 对不同**。

## Proposal

曾考虑过以下做法，逐条列在这里以便日后重新评估：

1. **折中一：去掉注释后比对代码块内容** —— 代码里夹着要翻译的说明文字，
   去掉 `#` / `//` / `--` 注释再比。
2. **折中二：只取命令与路径** —— 按制表或多空格分栏，取首个分栏前的部分。
3. **只比「命令 token」，并把 `主题.md` / `topic.md` 这类加入豁免清单。**
4. **为「命令 vs 说明」写更细的形态规则**（按标点密度、按语言特征等）。
5. **引入 mdast 并比完整内容**（上游做法），同时引入 `excluded` 豁免清单。

**但五条都不采纳** —— 前两条本篇已实测证伪；第三、四条会放过真漂移或无限
倒退；第五条的前提（那份豁免清单）本轮没有依据。理由见 Decision。

## Decision

**两种折中都证伪，不做。**

### 折中一：去掉注释后比对 —— 12 块里 3 块仍不同

```
第 2 块  /agent-notes   查看开关与笔记树状态
         /agent-notes   Show switch and note-tree status
第 5 块  .agents/notes/{lifecycle}/{class}/yyyy-mm-dd-主题.md
         .agents/notes/{lifecycle}/{class}/yyyy-mm-dd-topic.md
第 11 块 原始上游 --(GitHub Action，每日)--> 本仓库 …
         original upstream --(GitHub Action, daily)--> this repo …
```

**三类都是「人写的说明文字」，不是命令。**

### 折中二：只取首个分栏前的部分（命令与路径）—— 12 块里 2 块仍不同

```
第 5 块   zh: [".agents/notes/{lifecycle}/{class}/yyyy-mm-dd-主题.md"]
          en: [".agents/notes/{lifecycle}/{class}/yyyy-mm-dd-topic.md"]
第 11 块  zh: []
          en: ["original upstream --(GitHub Action, daily)--> this repo --…--> user machines"]
```

### 关键观察：剩下的差异是**正确的**，不是漂移

第 5 块那处最能说明问题：

```
zh: ...-yyyy-mm-dd-主题.md      ← 中文文件名示例
en: ...-yyyy-mm-dd-topic.md     ← 英文文件名示例
```

**两版各用自己的语言举文件名，这恰恰是正确的翻译。** 任何门禁都会把它当漂移。

第 11 块是 ASCII 图，整行都是说明文字，形态规则根本无从下手。

## Alternatives considered

- **只比「命令 token」并把 `主题.md`/`topic.md` 这类加入豁免** — 能绿。**这是本篇最强的一条被否方案**，因为**豁免清单要人来判断「哪些该豁免」，而判断错就会放过真漂移**。上游确实有 `excluded` 字段，但它服务的是「生成型/指令型文档」，不是「每处措辞差异」—— 用途不同，搬过来就是滥用。
- **为「命令 vs 说明」写形态规则**（如按制表对齐、按标点密度、按语言特征）— 更精细。**否掉因为那是无限倒退**：我刚做的「取首个分栏前」已经是一条形态规则，剩下 2 处差异立刻证明它不够。再加规则能覆盖这 2 处，但**下一对文档又会有新形态**。**靠形态识别「说明文字」没有终止条件。**
- **引入 mdast 并比完整内容**（上游做法）—— 那会让门禁在**当前 README 上就红**（4 块原样不同），除非同时引入豁免机制。**而豁免的前提是先有「该豁免的清单」，那份清单本轮没有依据。**
- **什么都不做，只比语言标记**（现状）—— **这是本篇的决定。**

## Consequences

- **收益**：避免了一个「看起来能绿、实际会放过真漂移」的门禁。第 5 块那处差异是最好的证据：**任何形态规则都会把它误判成漂移，而它是正确的。**
- **收益**：把「代码块内容」这一项从「待评估」变成了**已评估并否决**，附两份实测数据。
- **代价与已知上限**：**门禁能力仍低于上游** —— 代码块内容、表格行列、列表项数、链接目标四项都没比。这是已知的差距，写在这里是为了不被忘记。
- **代价与已知上限**：若将来 README 的代码块**只剩纯命令**（不再夹带说明文字），那「比完整内容」会变成可行且无歧义的。**那时应该重新评估。**
- **重访信号**：
  - **若某次改动造成「两版的命令本身不一致」而门禁没抓到**（比如中文写了 `npm run check`、英文写了 `npm test`）→ **立刻比代码块内容**，因为那时它已是纯命令，无歧义。
  - **若 README 拆成「命令清单」与「说明文档」两份** → 那时分栏规则就自然成立了（命令在清单里，说明在文档里），可以比清单那份的全文。
  - 若真要引入豁免机制，**判据必须是「按文档种类」而不是「按具体差异」** —— 前者可长期维护，后者会无限增长。

## Verification

```sh
node .probe/tmp/eval-code-block-parity.mjs   # 折中一：去注释后比对
node .probe/tmp/eval-command-tokens.mjs      # 折中二：取首个分栏前
```

实测数据：

```
代码块数量:              中文 12 个，英文 12 个
原样就不同的块:          4 / 12
折中一 去注释后仍不同:   3 / 12
折中二 命令序列不一致:   2 / 12
```

**折中二剩下的 2 处差异形态**：

| 块 | 差异 | 是否漂移 |
|---|---|---|
| 5 | `主题.md` vs `topic.md` | **否** —— 两版各用自己的语言举文件名，是正确翻译 |
| 11 | ASCII 图整行说明文字 | **否** —— 形态规则无从下手 |
