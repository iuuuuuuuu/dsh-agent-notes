# Agent Note: 「取代了旧篇就必须归档」做不成门禁 —— 措辞扫出来全是误报

Status: rejected — 机械判据抓不到「旧篇被取代」，且扫出的 3 处全是误报

> 上游 `.agents/notes/AGENTS.md` 明确要求「完全取代的，在同一个 PR 里归档」。
> 本仓库的 `tools/notes-supersession.mjs` **没有这条检查**。
> 本篇是核实该缺口后**否决补这道门禁**的记录。
> 同属「与上游比对」这条线。

Independent: 本篇否决一个具体的门禁设计，不改变任何门禁行为。

## Problem

上游 AGENTS.md 只有 8 行，但有一条本仓库没有的硬规则：

> classify any full or **partial supersession** … and **archive every
> qualifying implemented triplet in the same PR**. Keep **partial** supersessions
> active and cross-linked.

即：**完全取代 → 归档；部分取代 → 保持活跃并交叉链接。**

本仓库的 `tools/notes-supersession.mjs`（333 行）只检查「有没有声明关系」
（相对链接 或 `Independent:`），**不检查「声明了完全取代，旧的是否已归档」**。

现状：**implemented 45 篇 / archived 1 篇**，而 5 篇声明了取代关系。

看起来是个明确的缺口。**但做之前必须先验判据能不能用。**

## Proposal

曾考虑过以下做法，逐条列在这里以便日后重新评估：

1. **做门禁，靠「已被取代」措辞扫描**
2. **只在 commit-msg 钩子里提示，不判红**
3. **什么都不做**
4. **收益**：记下了**上游那条规则的机制**
5. **代价与已知上限**：现有 45 篇里**是否真发生过「完全取代」我不知道**

**但均不采纳** —— 理由见 Decision。

## Decision

**不做这道门禁。** 机械判据抓不到目标，且扫出的全是误报。

### 试过的判据：扫「已被取代」措辞

扫活跃区全部笔记，找这些写法：

```
/已被[^。\n]{0,20}取代/
/被[^。\n]{0,15}替代/
/superseded by/i
/本文取代/  /本篇取代/
/不再适用（因/  /已过时/
```

**命中 3 处，逐条核对后全部是误报**：

| 命中 | 实际是什么 | 为什么误报 |
|---|---|---|
| `ci-vendored-tampered-by-tests.md:109` | 「**这条理由**本身不成立……见那篇」 | 引用**另一篇**里的话，不是本篇被取代 |
| `bilingual-only-fence-langs-are-unambiguous.md:101` | 「原计划的 **mdast 方案**被更好的方案替代了」 | 被替代的是**技术方案**，不是这篇笔记 |
| `zero-dep-was-my-own-self-imposed-shackle.md:72` | 表格里「真实路径跑测试 \| 已被取代」 | **一个技术选项**被取代，不是笔记 |

**3/3 误报。**

而真正「旧篇被新篇完全取代」的情况，一条都没扫到。

### 为什么机械判据注定抓不到

「完全取代」在**散文里**表达，而散文没有标记。上游靠的是
`dsh-archive-agent-notes` 这个 **skill**——它是「人判断 + 工具执行」，
不是「脚本自动判定」。

而本仓库现有的 45 篇笔记里**没有人写「本文取代 X」这种标记**，
所以：

| 方案 | 后果 |
|---|---|
| 靠措辞扫 | **3/3 误报**（实测） |
| 要求写新笔记时加机器可读标记 | 对现有 45 篇是**追溯性要求**，且增加每篇笔记的书写负担 |
| 什么都不做 | 现状 |

**若硬做第 2 条，那是引入一套新标记体系来防一件从未发生过的事。**

## Alternatives considered

- **做门禁，靠「已被取代」措辞扫描** — 最直接的补齐。**这是本篇最强的一条被否方案**，因为实测 **3/3 误报**。一条会误报的归档门禁比没有更糟：它会让人为了绕开它而**改措辞**，从而把真取代关系藏起来。
- **引入机器可读标记**（如 `Supersedes: ../x.md`）再据此检查归档 — 最可靠。**否掉因为成本不对等**：要追溯改 45 篇笔记（或声明豁免），为一件事没发生过的检查。**且它会把「取代关系」从「写给人看」变成「填给脚本看」，反而降低笔记的可读价值。**
- **只在 commit-msg 钩子里提示，不判红** — 折中。**否掉因为那与现状差别很小**：`notes-supersession.mjs` 已经在失败信息里写了「② 完全取代：同样加链接，并在旧笔记里注明已被本篇取代」。**提示已经在了，缺的是执行 —— 而执行需要可靠判据，现在没有。**
- **什么都不做** — **这是本篇的决定。**

## Consequences

- **收益**：避免了一个会误报的归档门禁。误报的归档门禁会逼人改措辞，把真取代关系藏起来 —— **那是净损失**。
- **收益**：记下了**上游那条规则的机制** —— 它靠 skill（人判断 + 工具执行），不是脚本判定。若将来要补，**应该补的是流程提示而非门禁**。
- **代价与已知上限**：**本仓库仍然没有「完全取代就要归档」的结构保障**。若将来真发生一次完全取代，那篇旧笔记会一直留在活跃区，与新篇并存。**这是已知的、已记录的差距**，写在这里是为了不被忘记。
- **代价与已知上限**：现有 45 篇里**是否真发生过「完全取代」我不知道** —— 因为没有标记，就无法判断。**这个「不知道」本身就是缺口的表征**：结构上无法回答这个问题。
- **重访信号**：
  - **若活跃区出现两篇笔记讲同一件事且结论相反** —— 那就是「完全取代」发生了但没归档。那时该做的不是加门禁，而是**归档那篇**，并考虑加标记。
  - **若笔记数量超过 ~100 篇** —— 主动检索的成本会超过自动检查的维护成本，那时加标记体系才划算。
  - 若本仓库将来引入 skill 机制（能承载「人判断 + 工具执行」），可以把这条规则做成 skill 而非门禁。
