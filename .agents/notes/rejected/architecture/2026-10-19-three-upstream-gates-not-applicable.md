# Agent Note: 已核查但不适用的三个上游门禁

Status: rejected — 本机实测无对应问题，且其中两项的实现方式会引入假绿

> 同属**上游比对**这条线，是 goal「逐项核查、明确写出不采纳理由」的那一半。
> 采纳的部分见
> [notes-coverage-gate](../../implemented/process/2026-10-18-notes-coverage-gate.md)（supersession 借鉴）
> 与 [notes-supersession-check](../../implemented/process/2026-10-18-notes-supersession-check.md)。

Independent: 本篇记录**明确不采纳**的三项，与已落地的门禁笔记（那些写的是
「做了什么」）分工不同 —— 这里写的是「查过了、为什么不采纳」。三者分属不同
机制，不冲突。

## Problem

上一轮把上游 200 个脚本、65 道 `verify-*` 过了一遍。其中这三项在初看时像是
「本仓库也该有」，逐一核查后判定**不适用**。

风险在于：**「我看了一眼觉得没用」不算理由**。它会在半年后被人重新提起，
而那时没人记得为什么。所以下文把判据做成**可重跑的脚本 + 具体数据**，
而不是一句主观判断。

## Proposal

曾考虑吸收上游的三道门禁，逐条列在这里以便日后重新评估：

1. **`verify-md-wrap`** —— 拦「一个 Markdown 段落被硬拆成多个物理行」，
   配套需引入 mdast（GFM AST）。上游的理由是 AST 能区分段落与多行结构节点。
2. **Markdown 锚点校验** —— 在 `tools/md-links.mjs` 里追加「`#fragment`
   必须对应某个真实标题」，同样需要与 GitHub 的 slug 算法逐字一致。
3. **`verify-agent-note-classification` 的旧路径封禁** —— 禁止笔记出现在
   `docs/rfc` / `docs/rfcs`，防止有人按旧习惯把决策记录写到那里。

三条都写进了 `npm run check` 的候选，理由分别是「中文排版需要折行」、
「零处使用锚点」、「五个仓库零出现」。**这三条理由本身都不够硬**，核查过程见下。

## Decision

### 一、`verify-md-wrap`（拦「段落被拆成多行」）—— 不适用

上游理由：GFM AST 能区分「段落」与「多行结构节点」。

**三条实测理由**（脚本：`.probe/tmp/eval-md-wrap.mjs` 与 `inspect-bold.mjs`）：

| 数据 | 值 | 含义 |
|---|---|---|
| 笔记数 / 非空行 | 30 / 2322 | 去掉围栏代码块后 |
| 表格续行 | 236 | 容易识别 |
| 列表项 | 462 | 容易识别 |
| 引用行 | 138 | 容易识别 |
| **缩进代码块** | **0** | 缩进在本仓库不承载语义 |
| 行首粗体（4.6%）中「独立段落」形态 | 52 | 全部是有意的段落首句加重 |

1. **没有需要 AST 才能分类的多行结构**—— 缩进代码块 0 处。行首空格在本
   仓库完全不承载语义，而那正是 AST 最有价值、最难用正则近似的场景。
2. **真正的目标形态几乎不存在** —— 那 52 处逐条看过，全是
   `**故障只在 CI 的运行环境里出现。**` 这种**段落首句加重**，不是被拆开的段落。
3. **中文排版本身依赖折行** —— 中文没有词间空格，窄栏硬折行是正常写法。
   本仓库里 `**上游其实有自动同步**，读源码能看到两处：` 这类折行是**刻意**的，
   上游那条规则会把它判成「段落被拆开」而误报。

**为什么不「用轻量方式近似」**：跳过围栏与结构行之后，段落内部的折行正是
规则要拦的东西 —— 而它在中文写作里合法。误报必然存在，而收益是 0 个真问题。
误报多的门禁会被绕过，之后连原本有效的门禁也一起失信。

### 二、Markdown 锚点（`#fragment`）校验 —— 不适用

上游 `verify-md-links` 会校验「锚点是否真的对应某个标题」。本仓库实测
**零处使用锚点**。

但按「完整流程需要什么」的判据，「当前零使用」不足以否决 —— 将来有人写
`[见上文](#注意事项)`，断链了没人知道。所以进一步评估了**可行性**
（脚本：`.probe/tmp/eval-anchor.mjs`，216 个标题）：

| 字符类别 | 占比 | slug 规则处理 |
|---|---|---|
| 含空格 | 36% | → 连字符 |
| CJK | 29% | 原样保留 |
| 冒号 | 14% | 删除 |
| 引号 | 5% | 删除 |
| 反引号 | 4% | 删除 |
| 括号 | 2% | 删除 |
| `/` `#` | 各 1% | 保留为字面量 |

**决定性理由是正确性，不是成本**：手写 slug 必须与渲染器（GitHub）**逐字
一致**，否则「校验通过」不代表「点得动」—— 门禁说锚点存在、浏览器里点了
跳不过去，那是**另一种假绿**，比没有门禁更坏。

要正确实现只有两条路：引一个成熟的 slug 库，或在真实 GitHub 页面上抓
渲染后的 `id` 属性。前者引入依赖，后者需要网络与浏览器。

### 三、`verify-agent-note-classification` 的旧路径封禁 —— 不适用

上游封禁 `docs/rfc`、`docs/rfcs`，防笔记从旧习惯搬回那里。

实测：本仓库 **git 全历史零出现**；本机已装本插件的 5 个仓库
（`ai-auto-repety-gawaty`、`dsh-web-inspect`、`route-deck`、`sourin-flutter-spike`
等）**全部用 `.agents/notes`**，无一例外。

而 `docs/` 在本仓库**已被 `notes-coverage` 有意豁免**，理由写在代码注释里：
「计划与排查记录是**过程**，不是**决策**」。加一条「`docs/` 里的决策记录不许
存在」会与那个已论证的设计冲突。

## Alternatives considered

- **给 `verify-md-wrap` 做轻量近似** — 见上，误报必然、收益为零。
- **引 `github-slugger`（GitHub 官方同款实现）再做锚点校验** — 这确实能解决正确性问题。**暂不做的理由不是「引依赖」**（github-slugger 几乎没有依赖树，见 [零依赖是我自设的枷锁](../../implemented/process/2026-10-19-zero-dep-was-my-own-self-imposed-shackle.md)），而是两点：一是**零处使用锚点 = 零个真问题**；二是**手写 slug 会造成另一种假绿** —— 门禁说锚点存在、浏览器里点了跳不过去，比没有门禁更坏。等真的出现第一个 `#fragment` 链接时立刻引，不能手写。
- **对旧路径封禁做个软提醒（⚠ 而非失败）** — 看起来两头兼顾。否掉因为它要么产生噪音，要么等于没拦；而「零出现」意味着连噪音都不会有，白加。
- **把这三条判定只写在对话里** — 省一篇笔记。否掉正是因为它们最容易被重新提起：半年后有人问「为什么不做 md-wrap」，答案必须在仓库里。

## Consequences

- **收益**：三项「看起来该做」的方向有了明确、可复现的判定依据，附可重跑的脚本与数据。后续任何人重新提起，脚本一跑就知道结论还成不成立（数据变了就该重评）。
- **收益**：顺带确认了 `docs/` 豁免、`notes-coverage` 的边界等既有设计**经得起追问** —— 核查过程没有推翻任何一条。
- **代价与已知上限**：三份核查脚本在 `.probe/tmp/` 下，**不入库**（本仓库约定探针不入库）。所以数据会随笔记树增长而变化，但结论的依据（脚本内容）也没入库。若将来要复核，需要重新写一遍脚本。**这是本篇的已知敞口** —— 若认为这些判定长期有效，应该把脚本也收进仓库。
- **代价与已知上限**：数据是 2026-10-19 的快照。笔记树继续增长后，比例会变（尤其「行首粗体占比」）。若它涨到 10% 以上，第一条的理由需要重新评估。
- **重访信号**：
  - **md-wrap**：开始大量用行内代码块表达「段落中间要断行」，且那确实造成过阅读困扰 —— 但届时正确做法是**改写作约定**（段落写成一行），而不是加门禁。
  - **锚点**：首次出现 `#fragment` 链接。届时引 `github-slugger`，成本才配得上收益。
  - **旧路径**：任一仓库真的在 `docs/` 下放了决策记录。那说明豁免规则需要收紧，而不是加路径封禁。

## Verification

核查脚本（按本仓库约定留在 `.probe/`，不入库）：

```sh
node .probe/tmp/eval-md-wrap.mjs      # 缩进代码块 0、行首粗体占比
node .probe/tmp/inspect-bold.mjs      # 行首粗体 107 处的实际分类
node .probe/tmp/eval-anchor.mjs       # 216 个标题的字符分布
```

这些脚本只读取仓库内容，不写盘、不联网。
