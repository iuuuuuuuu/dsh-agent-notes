# Agent Note: 上游的「杀进程树」机制在 Windows 上用不上

Status: rejected — 实测只杀父进程时孙进程也被连带清掉，且本仓库 23/29 测试起子进程却从未观察到残留

> 本轮系统读了缓存里 47 个上游脚本的摘要，挑出「名字看不出对应、但机制
> 可能值得吸收」的候选逐一深读。这是第三个被否的候选
> （另两个：[比代码块内容](./2026-10-19-code-block-parity-two-approaches-failed.md)、
> [取代就归档](./2026-10-19-supersession-archive-rule-not-mechanizable.md)）。

Independent: 本篇否决一个具体的上游机制，不改变任何门禁行为。

## Problem

缓存里有 `up-run-gates.ts`（1697 行），摘要第一句：

> Run local and CI quality gates with **bounded in-process scheduling**.

它的导出里有三个看起来很像「进程清理」的东西：

```ts
export function parsePidPpidLines(output: string): Array<[number, number]>
export function collectDescendants(root: number, rows): number[]
export function taskkillArgs(rootPid: number, descendants: number[]): string[][]
```

调用点显示它会杀**整棵子进程树**（`taskkill /PID <n> /T /F`，且**逐个 PID 杀**，
注释写明是因为「一次 `/T` 会先杀掉 taskkill 自己，导致子树漏杀」）。

**为什么这看起来该吸收**：

| 事实 | 值 |
|---|---|
| 本仓库会起子进程的测试文件 | **23 / 29（79%）** |
| 门禁形态 | `&&` **串行**，某步超时后子进程可能残留 |
| 本仓库的进程树清理机制 | **没有** |
| 上游实测的偶发红症状 | 文件级失败（`test failed` 无具体断言）——**崩在解析阶段，与残留进程的症状吻合** |

三项凑齐，像是真缺口。

## Proposal

曾考虑过以下做法，逐条列在这里以便日后重新评估：

1. **照搬「收集后代 + 逐个 `taskkill /T /F`」**
2. **加个超时清理，只在门禁超时时跑**
3. **什么都不做**
4. **收益**：避免了一套永远不会被触发的死代码。**死代码比没有更糟**

**但均不采纳** —— 理由见 Decision。

## Decision

**不吸收。** 实测证明本平台上不需要。

### 实测一：正常跑完，无残留

跑 `self-update.test.mjs`（它起 `sync-upstream`，后者再起 `git` 与网络请求）：

```
跑之前 node 进程数: 23
跑之后 node 进程数: 23
差值: 0
```

但**这个样本不足** —— 正常路径下子进程会自己退出，问题出现在**父被杀**时。

### 实测二：父被杀时，会不会有孙进程残留

造最小复现：父进程（node）起一个睡 120 秒的孙进程（node），
3 秒后只对父进程发 `SIGTERM`（**不杀树**），然后查孙进程是否还在。

```
孙进程活着标志:     存在 ✔        ← 先确认它真起来了（上一版就栽在这）
父 pid: 42380   孙 pid: 44592

父进程已 SIGTERM（未杀孙进程）
孙进程仍在进程表: 否             ← ★ 没残留
孙进程还没跑完:   是（符合预期，它在睡）
```

两个条件合起来说明**它是被杀的，不是自然结束**：

- 不在进程表 → 已死
- 标记文件没出现 → 没跑到 120 秒的 setTimeout

**所以 Windows 上只杀父进程，孙进程也会被连带清掉。**

## Alternatives considered

- **照搬「收集后代 + 逐个 `taskkill /T /F`」** — 上游的做法，看起来该学。**这是本篇最强的一条被否方案**，因为实测**证伪了它的必要性**。若照搬，本仓库会得到一套 1697 行里的三个函数，且**永远不会被触发**（没有场景需要它）—— **死代码比没有更糟**：它让人以为清理机制在起作用。
- **加个超时清理，只在门禁超时时跑** — 比照搬轻。**否掉理由同上**：实测证明本平台不需要，而 Ubuntu 上的行为**未验证**。
- **什么都不做** — **这是本篇的决定**。

## Consequences

- **收益**：避免了一套永远不会被触发的死代码。**死代码比没有更糟** —— 它让人以为清理机制在起作用。
- **收益**：记下了「筛选上游候选时，摘要看起来像 ≠ 机制真的有用」的第二个实例（第一个是 `paired-markdown-derivatives`，那个是名字像；这个是摘要像）。
- **代价与已知上限**：**Ubuntu 上的行为未验证。** Windows 会连带清理子进程，Linux 通常也会（进程组未设置时行为依实现而定），macOS 则不同。本仓库 CI 是 `ubuntu-latest`，**那里是否同样不残留，我不知道**。
- **代价与已知上限**：若将来本仓库的门禁改成**并发**跑（上游那样），那时残留进程会与其它 gate 抢 CPU，「杀进程树」才成为刚需 —— 那时要连**分组**一起吸收，只搬清理不够。
- **重访信号**：
  - **CI 上出现「门禁超时」或「跑完后还有 node 进程」** → 立刻在 Ubuntu 上重测本篇的复现脚本；若那里确实残留，则吸收 `collectDescendants` 那三个函数。
  - **门禁改为并发** → 同上。
  - **若某次并行测试偶发红且找不到跨测试干扰源** → 残留进程是候选之一，用本篇的复现脚本验，而不是先降并发。
