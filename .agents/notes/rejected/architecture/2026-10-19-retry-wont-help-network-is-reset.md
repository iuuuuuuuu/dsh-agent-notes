## Problem

本机网络反复断开，导致 `npm run check` 反复出现 3 个 `sync-upstream` 失败。

第一反应是「加重试」—— 这是处理间歇性网络故障的标准做法。但：

`tools/sync-upstream.mjs` 的 `fetch` **没有任何重试**：

```js
const response = await fetch(url);   // 一次失败就整个门禁失败
```

## Proposal

曾考虑给 `sync-upstream.mjs` 的 `fetch` 加重试与退避，逐条列在这里以便日后重新评估：

1. **立刻重试 3 次** —— 处理间歇性网络故障的标准做法。
2. **重试 + 指数退避**（100ms / 500ms / 2s）—— 应对服务端限流与连接池预热。
3. **换源**（jsDelivr → GitHub raw 直连）—— 避开被重置的那个端点。
4. **网络不可用时用「上次成功的清单快照」兜底** —— 让断网时仍能验点东西。
5. **把 `sync:check` 从 check 链移除** —— 不受影响就不会红。

理由分别是「标准做法」「更稳健」「换个源」「仍能验证」「消除噪声」。
**但五项全部不采纳** —— 前两项被实测否决，后三项各有更根本的问题。见下。
## Decision

**不加重试。** 因为实测证明重试在这台机器上**无效**。

### 实测过程（三步，每步都推翻一个假设）

**第一步：测失败率 → 「很稳定」**

18/18 全通（curl 与 node fetch 各测三轮）。

若就此下结论，会写成「网络稳定，重试无必要」。**那个结论是错的** —— 它只描述了
一个时间点。

**第二步：测失败的「成簇性」**

```
✗✗✗✗✗✗✓✓✓✓✓✓✓✓✓✓✓✓✓✓✓
```

**失败是成簇的**：开头连续失败 6 次，然后 14 次全成功。

这推翻了「重试能解决随机抖动」的默认假设：

| 失败形态 | 重试的效果 |
|---|---|
| **孤立**（成功、失败、成功） | 重试一次就够 |
| **成簇**（连着 6 次失败） | 同进程内立即重试**也会失败** |

**第三步：直接测「重试有没有用」**

```
第 1 轮: 首次失败(ECONNRESET) → 立刻重试两次都失败 ✘
第 2 轮: 首次失败(ECONNRESET) → 立刻重试两次都失败 ✘
第 3 轮: 首次失败(ECONNRESET) → 立刻重试两次都失败 ✘
第 4 轮: 首次失败(ECONNRESET) → 立刻重试两次都失败 ✘
第 5 轮: 首次失败(ECONNRESET) → 立刻重试两次都失败 ✘
第 6 轮: 首次失败(ECONNRESET) → 立刻重试两次都失败 ✘
第 7 轮: 首次失败(ECONNRESET) → 立刻重试两次都失败 ✘
```

**7/7 立刻重试全部失败，错误码统一是 `ECONNRESET`。**

那不是「抖动」，是**连接被对端重置**。重试解决不了。

## Alternatives considered

- **给 `fetch` 加 3 次重试 + 退避** — 标准做法。**这是本篇最强的一条被否方案**，而且否掉它花了三步实测：先测失败率（说「稳定」，但那是假象）→ 测成簇性（推翻「抖动」）→ 测重试（7/7 无效）。**如果只做第一步，我就会去实现一个证明无效的东西。**
- **换源（jsDelivr → GitHub raw 直连）** — 避开被重置的那个。**否掉因为源本身没有罪**：注释里写着「直连 raw.githubusercontent 在本机实测被重置（ECONNRESET），jsDelivr 可稳定访问」—— 作者早就测过并选了 jsDelivr。**换回去是倒退。**
- **网络不可用时用「上次成功拉到的 ref」比对** — 这是真正有价值的方向。断网时至少能验「内置副本与**已知**的 ref 是否一致」，而不是完全不验。**但本轮不做**：那需要缓存上次成功的清单快照，并定义「快照过期怎么办」，是设计而非补丁。见重访信号。
- **把 `sync:check` 从 check 链里移除** — 不受影响就不会红。**否掉因为那是把问题藏起来而不是解决**：它会让人以为「内置副本与上游一致」这件事有人在验，而实际上没有。**门禁消失比门禁红更糟。**

## Consequences

- **收益**：避免了一个「看起来该做、实测无效」的改动。若实现了它，`sync-upstream` 每次网络重置会多花 3 倍超时时间（而结果一样是失败）。
- **收益**：确认了 `sync-upstream` 选 jsDelivr 的决定是对的 —— 直连 GitHub 会被重置。
- **代价与已知上限**：**本机网络不可用时，check 仍然会红**（3 个用例）。这不是缺陷，是如实反映「本次没有完成对上游的校验」。
- **代价与已知上限**：错误信息虽然已经准确（「环境不可用，不是契约被破坏」），但**它仍然让 check 变红**。在 CI 上这意味着网络抖动会导致构建失败，需要重跑。**CI 上有重试机制吗？** —— 本仓库没有显式配置，那是一个未核查的点。
- **代价与已知上限**：本地那 3 个网络用例**在网络恢复前无法验证**。本轮多次确认过：网络恢复时它们全绿（5/5），断网时报「环境不可用」。所以它们的逻辑是对的，只是当前环境跑不了。
- **重访信号**：
  - **实现「用上次成功的清单快照兜底」** —— 那是真正能让 check 在断网时仍能验点东西的方案。触发条件：本机或 CI 上网络不可用的频率高到影响日常。实现时要想清「快照多久算过期」。
  - **给 CI 加重跑机制**（`continue-on-error` + 手动重跑，或第三方 action）—— 若 CI 因为网络抖动而频繁失败。**先查 CI 失败率再决定**，不要先加机制。
  - 若 `sync-upstream` 换了源或改用 git submodule，**重测「立刻重试是否有效」** —— 本篇结论只对「jsDelivr + node fetch」这个组合成立。
